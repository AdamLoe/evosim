# Mission: Documentation Overhaul (v1.8)

## Goal

Replace the current `docs/` folder (history-shaped narrative, growing forever, mixed concerns) with an LLM-optimized documentation tree that lets a fresh agent get full project context without reading the codebase or wading through 3000 lines of changelog. Decisions are recorded **declaratively by domain**, not chronologically by ship date. Architecture docs describe the *current* system in place — when the system changes, the docs get rewritten in place, not appended to. Git log is the chronological history; the docs are the snapshot.

## Why now

- The repo-root `DECISIONS.md` has grown to ~3500 lines and mixes "v1.6 shipped X" (history) with "the sim worker owns wasm and rayon" (current architecture). A fresh agent has to read all of it to learn the second thing.
- No single source of truth for current architecture exists. To learn how the sim/render decoupling works, a fresh agent reads `docs/plans/v1.6-plan.md` (already 470 lines), then `docs/plans/v1.6-implementer-guide.md` (already deleted), then walks the diff history. Most of that content is about how we got here, not where we are.
- Shipped planning docs (`v1.6-plan.md`, `v1.7-mission.md`) are still in `docs/plans/`. Some are deleted, some aren't. The signal-to-noise for "is this current state or historical context" is bad.
- The dev-server-prompt is one of several "operational" docs floating at the top level. A new agent doesn't know whether to read it.
- No mechanism keeps any of this in sync with the code. Drift is silent.

## What ships

A new `docs/` tree purpose-built for LLM consumption, with the current `docs/` renamed to `docs-old/` (tombstone — references to it stay broken; deleted in a later pass by the user). The tree has four functional zones (`architecture/`, `decisions/`, `agent-context/`, `prompts/`) plus three root-level entry-point files:

```
docs/
  index.md                          ← TOC + ownership map; the entry point
  overview.md                       ← system at a glance, ~1 page
  repository-layout.md              ← directory tree + per-dir purpose
  architecture/                     ← current-state STATIC FACTS, no history, no version numbers
    simulation-core.md              ← OWNS the Rust world/tick model: World, CreatureSoA, grass, NN
    worker-runtime.md               ← OWNS the Web Worker lifecycle: spawn, boot handshake, pacing, restart
    shared-memory-and-protocol.md   ← OWNS every message type + serialization format + SAB layout
    render-pipeline.md              ← OWNS the GL render path, camera, snapshot read
    profiler.md                     ← OWNS the four-tree shape + no-rollup rule
    build-and-deploy.md             ← OWNS the wasm-pack incantation, COOP/COEP, threaded-bundle invariants
    testing.md                      ← OWNS the test layout (what suites exist, what each covers)
  decisions/                        ← declarative, sectioned by architecture domain (NOT by date)
    sim.md
    render.md
    profiler.md
    build.md
    cross-cutting.md
  agent-context/                    ← PROCEDURAL "how to work on this repo"
    coding-style.md                 ← Rust + TS conventions specific to this repo
    repo-rules.md                   ← git rules, commit conventions, what not to do
    orchestration-workflow.md       ← multi-wave / mission / agent patterns
    testing-how-to.md               ← how to run / add tests (procedural)
    dev-loop.md                     ← inner loop: rebuild wasm, restart server, when to clear caches
    maintaining-docs.md             ← when you touch X, update Y (the rules below)
  prompts/                          ← reusable VERBATIM templates; PROMPTS OWN NO FACTS
    dev-server.md                   ← thin pointer to architecture/build-and-deploy.md; no incantation duplication
    fresh-chat.md                   ← what a fresh AI chat reads first
    check-docs.md                   ← prompt to run periodically to flag doc drift
  plans/                            ← in-flight mission docs; ephemeral, free to delete/archive
```

The repo-root `DECISIONS.md` moves with the rename: `git mv DECISIONS.md docs-old/DECISIONS.md`. Nothing canonical is left at repo root pointing at the old narrative — every reader is funneled into the new `docs/` tree.

The current `docs/` becomes `docs-old/` via `git mv`. We do **not** rewrite references that point into the old path — those break, and that's fine, because they were inside the now-tombstoned tree and the user will delete that tree later.

`CLAUDE.md`, `AGENTS.md`, and ad-hoc `.claude/` instruction files are explicitly **not** part of this system. Context is finite; putting global instructions in CLAUDE.md burns it on every conversation regardless of relevance. The single `docs/prompts/fresh-chat.md` prompt is the deterministic entry point; everything else loads only when the task needs it.

## Authoring rules (these go in `docs/agent-context/maintaining-docs.md`)

1. **Every doc has explicit ownership.** Each doc declares what it owns and what it may only reference. Examples:
   - `architecture/shared-memory-and-protocol.md` **owns** every message type, the discriminated-union shapes, the serialization format, and the SAB byte layout. `worker-runtime.md` may reference messages but must not redefine them.
   - `architecture/build-and-deploy.md` **owns** the canonical wasm-pack incantation, the threaded-bundle invariants, and the COOP/COEP requirement. `prompts/dev-server.md` and `agent-context/dev-loop.md` may reference and link, but must not redefine.
   - `architecture/profiler.md` **owns** the four-tree shape and the no-rollup rule. `decisions/profiler.md` records why; the architecture doc states what.
   - **Prompts own no facts.** Every prompt is either a verbatim template (`fresh-chat.md`) or a thin pointer (`dev-server.md` → `architecture/build-and-deploy.md`). If a prompt starts to accrete substantive content, that content belongs in `architecture/` or `agent-context/` and the prompt links to it.
   - The `index.md` carries the full ownership map as a small table so a fresh agent can find the canonical source for any concept in one hop.
   Without explicit ownership, two docs gradually duplicate the same content with subtle differences and drift sets in.
2. **Architecture docs describe what IS, not what changed.** No "v1.6 introduced…" framing. When the sim worker model gets replaced, `worker-runtime.md` gets rewritten in place. The change goes in `decisions/sim.md`; the architecture doc reflects current state only.
3. **Reference files by path; do not embed implementation code. Small interface snippets are allowed.** Code is authoritative for behaviour; docs are authoritative for *what's where and why*. Implementation excerpts rot the moment the code changes — banned. Interface snippets (a `pub fn` signature, a TypeScript discriminated-union shape, a SAB layout table) are contracts that change rarely and are useful to read inline — allowed when they help an agent understand the boundary without grepping. Rule of thumb: if the snippet would survive the next refactor, embed it; if it'd need to be edited every patch, link instead.
4. **Each architecture doc is one file, one subsystem, ~1–2k tokens.** Bigger = burns context on irrelevant info. Smaller = navigation tax. If a subsystem grows past ~2k tokens, split it.
5. **`decisions/` is sectioned by architecture domain, not by date.** One file per domain (`sim.md`, `render.md`, `profiler.md`, `build.md`, `cross-cutting.md`). Each entry has three **mandatory** fields:
   - `Decision` — one sentence stating what we believe.
   - `Why` — the reason. Even one line is fine.
   - `Applies to` — which architecture doc(s) this constrains, so the cross-link is bidirectional.

   And four **optional** fields, included only when they add real value:
   - `Alternatives considered` — only if there were nontrivial alternatives worth recording.
   - `Tradeoffs` — only if there are real tradeoffs a future reader needs to weigh.
   - `Code anchors` — `path → symbol_name` (NOT `path:line` — line numbers drift, symbol names are grep-stable and surface meaningful refactors). Include when a decision binds to a named symbol or constant that drift would silently break.
   - `Revisit when` — the trigger condition. Skip when there isn't a foreseeable one.

   **No** `Date:` field — the git log is the date authority. **Only carry forward decisions that still apply.** Superseded rationale stays in git and in `docs-old/DECISIONS.md`; don't re-litigate it here.
6. **Cross-link liberally.** Each architecture doc has a `See also` section pointing to related docs (especially the relevant `decisions/<domain>.md` and any `agent-context/` doc with procedural overlap). LLMs follow links cheaply; keyword search is expensive.
7. **Plans live in `docs/plans/`. They are ephemeral.** When a plan ships, the implementer (or the orchestrator) **must update architecture docs and the relevant `decisions/<domain>.md` to reflect the new current state** before the plan can be marked done. After that the plan is free to be archived to `docs/plans/archive/` or deleted; nothing depends on it.
8. **No `CLAUDE.md`, no `AGENTS.md`, no global `.claude/` instructions about this project's architecture.** All such context goes in `docs/`. Settings unrelated to project knowledge (permissions, hooks, etc.) stay where they are.

## What changes (high-level)

- `git mv docs docs-old` and `git mv DECISIONS.md docs-old/DECISIONS.md` — preserves history; references break (acceptable). After this, nothing canonical lives at repo root pointing at the old narrative.
- New `docs/` tree created with the ~22 files listed in the directory diagram above. Initial content is a current-state snapshot reflecting v1.7.1 (latest shipped).
- `docs/decisions/*.md` are populated by extracting **only the decisions that still apply** from `docs-old/DECISIONS.md` and the surviving v1.6/v1.7 plans, recasting them declaratively (with `Applies to` / `Code anchors` / `Revisit when` fields) and routing each to the right domain file. Superseded rationale stays in `docs-old/` and the git log.
- `docs/index.md` carries the ownership map (small table: concept → owning doc) so a fresh agent can find the canonical source for any concept in one hop.
- `docs/repository-layout.md` is the directory tree of the repo with one sentence per non-trivial path — fastest path to "where does X live?" without grepping.
- `docs/agent-context/maintaining-docs.md` is the authoring-rules doc above, written for an AI orchestrator to follow when shipping a feature.
- `docs/prompts/fresh-chat.md` is the entry-point prompt: ~10 lines telling an AI to read `docs/index.md` first, then `docs/overview.md`, then ask the user what they want to do. Resists self-containedness — points at the index instead.
- `docs/prompts/dev-server.md` is a thin pointer to `architecture/build-and-deploy.md`, NOT a copy of the wasm-pack incantation. The incantation has one canonical home.
- `docs/prompts/check-docs.md` is a prompt that walks the architecture docs and verifies more than path existence: named symbols, constants, and contracts (SAB byte offsets, the protocol version constant, the wasm build flags, the `pnpm` script names, the test command). Drift in any of those is the failure mode we care about. User runs it periodically.

## Non-goals

- **Migrating every line of historical context.** Most of the v1.3–v1.5 narrative is dead weight. Keep what informs current design; drop the rest.
- **Documenting every file in the codebase.** Architecture docs cover subsystems, not files. If you need to know what a specific file does, read the file.
- **Auto-generated docs from code (rustdoc-style).** Out of scope.
- **A pre-commit hook that enforces doc updates.** Discussed; rejected for now (false-positives on refactors → users start passing `--no-verify`). Manual `check-docs.md` prompt fills the gap.
- **Fixing references inside `docs-old/`.** The whole tree is tombstoned. User deletes it later.

## Success criteria

1. A fresh AI chat opens `docs/prompts/fresh-chat.md` (~10 lines), reads `docs/index.md`, reads `docs/overview.md`, and is **able to orient itself and route to the right subsystem doc** based on the user's first question — not full subsystem fluency. Bootstrap context budget: < 3k tokens.
2. Any single architecture doc loads in < 2k tokens, and each one has explicit `Code anchors` and `Update when` sections.
3. A grep across the new `docs/` tree shows zero "v1.6 introduced" / "Wave D added" / "as of v1.7" framing. Architecture docs and decisions are tenseless and version-less.
4. `docs/decisions/` is split by domain (`sim.md`, `render.md`, `profiler.md`, `build.md`, `cross-cutting.md`). Each entry is declarative; none has a `Date:` field; each carries `Applies to` / `Code anchors` / `Revisit when`.
5. `docs/index.md` contains the ownership map (concept → owning doc). Every concept that appears in more than one doc has a single canonical owner listed.
6. `docs/agent-context/maintaining-docs.md` exists and is referenced from every architecture doc's `See also`.
7. `docs/plans/v1.8-mission.md` (this file) lives in the new tree after the rename — same content, new home.
8. `docs/repository-layout.md` covers every non-trivial directory at the repo root with a one-sentence purpose.
9. Repo root holds no canonical narrative — `DECISIONS.md` has moved into `docs-old/`; only the standard `README.md` and project files remain.

## What I want from the implementer

This is mostly a content-creation pass, not a refactor. The implementer reads the current state (`docs-old/DECISIONS.md`, the surviving v1.6/v1.7 plans, the actual source) and writes the new tree from scratch. Net new prose, not surgical edits.

The hardest part is the `decisions/` tree. The current `DECISIONS.md` is chronological narrative; the new tree is a categorized belief system. The implementer needs judgment about which past decisions are still load-bearing (keep, recast declaratively, route to the right domain file) vs superseded (drop). When in doubt: include it with a brief "alternatives considered" note, because removing a decision later is cheaper than reconstructing why we believed it.

Each architecture doc should answer, in ~1–2k tokens:
- **What is this subsystem?** (one paragraph)
- **What does it own?** (the explicit ownership claim — concepts, types, files, boundaries)
- **What may it only reference?** (the explicit non-ownership claim — concepts whose canonical home is elsewhere)
- **How does it interact with neighbours?** (named interfaces, message kinds, function signatures — small interface snippets allowed when useful; point at `path → symbol` for implementation)
- **Code anchors** — bulleted `path → symbol_name` list for every named symbol, constant, or contract the doc claims. **No line numbers** — they drift; symbol names are grep-stable and surface meaningful refactors. `check-docs.md` reads these and greps for the symbols.
- **Update when** — bulleted list of conditions that require this doc to change (e.g., "the SAB layout changes", "a new message kind is added", "the worker boot handshake changes"). Future maintainers know when their commit touches a doc-load-bearing surface.
- **Why is it shaped this way?** (link to relevant `decisions/<domain>.md` anchors)
- **See also** (cross-links to neighbouring architecture docs, the relevant decisions file, and the relevant agent-context doc if any)

Each agent-context doc should answer, in ~1–2k tokens:
- **When does this apply?** (one paragraph framing the situation an agent finds themselves in)
- **What to do.** (procedural steps, command incantations, gotchas)
- **What NOT to do.** (specific anti-patterns, often the source of past regressions)
- **See also** (the architecture doc that owns the static facts this references)

Don't overbuild the agent-context tree in pass one. Six files is the target; if one of them is genuinely empty after a sincere attempt, drop it. Add it back later when the need is real.

## Budget

This is a one-pass current-state snapshot, not a flawless full migration. Goal is the best version we can produce in a single focused session: complete enough that a fresh chat can orient and route, correct on the load-bearing facts, and structured so future passes can refine in place. Some `decisions/` entries will be coarse. Some `Code anchors` will be incomplete. That's fine — they get tightened the next time someone touches the relevant subsystem.
