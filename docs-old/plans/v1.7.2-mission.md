# Mission: Profiler Hygiene + Status-Bar Fix (v1.7.2)

## Goal

Four small fixes that together close out the surprises v1.7 exposed:

1. The profiler's `calls` and `ms/call` columns are misleading for sum-of-workers nodes — they report one call per *tick* even though the underlying work fires per-chunk or per-creature. Make the call counts honest.
2. The sample window per node is invisible and varies silently. Show it.
3. The top-left status text in the canvas updates only every 200 ms — a stale throttle from the WorldHandle era. Drop it; update every RAF.
4. There's no discoverable TPS readout in the always-visible UI; the only one lives in the bottom-left perf widget that can scroll off-screen. Add TPS + FPS to the top-bar status.

Tight one-day pass. No architectural changes. No new spans. No new SAB layout.

## Current issues

### 1. `calls` and `ms/call` are misleading for sum-of-workers nodes

The v1.7 profiler implements sum-across-workers nodes (`nn.*`, `grass_step.*`) via per-worker atomic accumulators that get drained into one `record_under_root` call per tick. That gets the *time* right (sum of all worker contributions) but it pushes **one sample per tick** into the ring buffer — meaning `call_count` measures "ticks where this phase fired" not "individual worker-phase invocations."

Concretely, `nn.forward.call_count` at 60 TPS over a 60-second window shows ~3600 (one per tick) when the *real* count is ~3600 × creature_count (~5.4 million at pop 1500). The `ms/call` value is therefore wrong by 1500× — it shows per-tick cost instead of per-creature cost.

### 2. Sampling window is invisible

The per-node `VecDeque<(timestamp_ms, dur_us)>` ring buffer caps at `SAMPLES_PER_NODE = 4096`, clamped to a `WINDOW_MS = 60_000` ceiling. With per-tick aggregation (in P1 below), every node ends up at 60 samples/sec → 4096 / 60 ≈ 68 s → clamped to 60 s. Uniform window across the whole panel, but **nowhere in the UI is the window length displayed.** "tick.total_ms = 40 s" is meaningless without knowing whether the window is 17 s, 27 s, or 60 s.

### 3. 200 ms status-text throttle

`web/src/main.ts:228-233` throttles `#status.textContent` updates to once every 200 ms. At 30 TPS, 200 ms = 6 ticks, so the user sees the tick number jump by 4–8 at a time. The throttle dates from the WorldHandle era when reading tick was a wasm call; post-Wave-C it's a `view.getUint32` — free. The canvas itself is rendering at full FPS the whole time; only the text is throttled. Delete the throttle.

### 4. TPS isn't discoverable

The only TPS surface is `#perf-tps` in the bottom-left perf widget (`web/index.html:74`). At small viewports or with the right rail open it scrolls off-screen. There's no readout in the always-visible top status bar. Render FPS isn't shown anywhere at all.

## Target behavior

### Status bar (top-left)

```
seed: seed-1f3e…  ·  tick 12450  ·  pop 1182  ·  60 TPS  ·  60 FPS
```

Updated every RAF. TPS read from the per-frame SAB header (already free, no new poll). FPS computed on main from a 1-second rolling frame counter ("frames in the last 1 s," as games conventionally measure it — a counter, reset and sampled each second).

Boot state: before the first 1 s has elapsed, FPS shows `—` (em-dash). Same when paused or world-ended.

### Profiler panel

The single line `window: 60.0 s` appears at the top of the panel, above the four trees. Computed from `max(timestamp) - min(timestamp)` across the highest-sample-count node.

All four trees use the same window (consequence of per-tick aggregation in P1), so one value is sufficient.

Within each tree, `ms/call` and `calls` reflect honest per-work-unit counts:

| Node                          | call_count semantic                            |
|-------------------------------|------------------------------------------------|
| `tick.*`                      | 1 per tick                                     |
| `tick.nn` / `tick.grass_step` | 1 per tick (leaves, wall-clock wait)           |
| `nn` (root)                   | chunk_count per tick (per rayon dispatch)      |
| `nn.build_input`              | chunk_count per tick                           |
| `nn.build_input.other`        | creature_count per tick                        |
| `nn.proximity`                | creature_count per tick                        |
| `nn.proximity.creatures`      | creature_count per tick                        |
| `nn.proximity.grass`          | creature_count per tick                        |
| `nn.forward`                  | creature_count per tick                        |
| `nn.forward.l1/l2/l3`         | creature_count per tick                        |
| `grass_step` (root)           | 1 per tick                                     |
| `grass_step.dispatch`         | 1 per tick                                     |
| `grass_step.row_compute`      | GRASS_GRID_DIM per tick (row body invocations) |
| `grass_step.row_compute.body` | GRASS_GRID_DIM per tick                        |
| `grass_step.bitset_rebuild`   | 1 per tick                                     |
| `frame.*`                     | 1 per RAF                                      |

`ms/call` = `sum(combined_us) / sum(combined_call_count)` over the visible window → honest per-call cost regardless of how many work units fire per tick.

## What changes

### Rust

- `src/profiler.rs`: extend `Node.samples` from `VecDeque<(u32 timestamp, u32 dur_us)>` to `VecDeque<(u32 timestamp, u32 dur_us, u32 call_count)>`. Adapt `record_under_root` to take an additional `call_count: u32` parameter. The existing `push_root` / `push_root_named` / SpanGuard RAII paths record `call_count: 1` (RAII spans always represent one call). The JSON report's `total_us` accumulates `dur_us` per sample as today; `call_count` accumulates the new `call_count` field. `ms/call = total_us / 1000 / total_call_count`. Memory cost: +33% per sample = 16 MB worst case at 32k samples × 256 nodes — but at 4096 samples × 256 nodes it's 4 MB.
- `src/world/nn_stats.rs`: alongside each `tick_*_us: AtomicU64` accumulator, add a paired `tick_*_calls: AtomicU64` counter. Increment it inside the per-worker chunk loop wherever the corresponding `_us` accumulator is incremented. The drain into `record_under_root` passes both numbers.
- `src/world/nn.rs`: the per-chunk loop's `record_chunk_subphases` call (or whatever the post-tick drain is named) passes both `_us` and `_calls`. The per-creature accumulators (`forward_l{1,2,3}_us`) are paired with `forward_calls: u64`. The per-chunk accumulators (`build_input_total_us`, `proximity_total_us`) are paired with `build_input_calls`, `proximity_calls`.
- `src/world/mod.rs`: the post-tick drain into `record_under_root` passes `call_count` alongside `dur_us` for each path. For the `grass_step` accumulators, paired call counters in `src/grass.rs` get drained the same way.
- `src/grass.rs`: alongside `row_body_us` / `row_body_self_us` / `par_chunks_us` / `chunks_mut_us` add `row_body_calls`, `dispatch_calls` atomics. Each row body invocation increments `row_body_calls` and `row_body_self_calls`. Each dispatch increments `dispatch_calls = 1`.
- `src/wasm_api.rs::profile_report_json`: ensure the JSON shape exposes both `total_call_count` (new) and `total_us` per node so the TS panel can compute honest ms/call.

### TypeScript

- `web/src/main.ts`:
  - Delete the `lastStatusUpdate` + `if (now - lastStatusUpdate > 200)` throttle around the status-bar text update (lines ~176 + ~228-233).
  - Update `status.textContent` every RAF unconditionally.
  - Format: `seed: ${cachedSeed}  ·  tick ${header.tick}  ·  pop ${header.pop}  ·  ${tpsStr} TPS  ·  ${fpsStr} FPS${endedSuffix}`.
  - `tpsStr = header.tps.toFixed(0)` (rounded to int — header.tps is the f32 from the SAB).
  - FPS: maintain `let framesThisSecond = 0; let fpsWindowStart = performance.now(); let lastFps = -1;` in the closure. Each RAF: `framesThisSecond++`; when `now - fpsWindowStart >= 1000`, set `lastFps = framesThisSecond`, reset counter + window. Display `lastFps >= 0 ? lastFps.toString() : "—"`.
- `web/src/perf.ts`: the TS-side `span()` helper records `(timestamp, dur_us)` today. Extend to `(timestamp, dur_us, call_count)` with call_count defaulting to 1 (every TS span is one RAII call). Adapt the JSON report shape to carry call counts.
- `web/src/widgets/perf-panel.ts`:
  - Render `window: ${windowSec.toFixed(1)} s` at the top of the panel. Compute `windowSec = (maxTimestamp - minTimestamp) / 1000` across the highest-sample-count node. (Or just take whatever the Rust report includes — see `profile_report_json` below.)
  - Read `total_call_count` per node from the JSON; render `ms/call = total_us / 1000 / total_call_count` for both the Rust trees (`tick`, `nn`, `grass_step`) and the TS tree (`frame`).
  - The existing perf-widget `#perf-tps` readout stays — it's belt-and-suspenders, and the perf widget is still where heavy debugging happens.
- `web/index.html`: no changes — the existing `#status` div already accepts the longer text.

### `pnpm test:e2e` regression coverage

`web/tests/e2e/sim-bridge.spec.ts` already covers the message-dispatch path. Add no new e2e tests in this pass — the changes are display-only and the existing e2e suite would catch any regression where the status text stops updating (the `pause` test reads tick from `document.body.innerText`).

## What does NOT change

- The four-tree profile structure (frame, tick, nn, grass_step). Locked from v1.7.
- The `record_under_root` API name. Just gains a `call_count` parameter.
- The SAB layout. `header.tps` is already in the snapshot per v1.6 Wave C.
- The 1 Hz `request_profile_report` poll cadence.
- Profile-OFF default. Toggle works the same way.
- The perf-panel's bottom-left position. (`#perf-tps` stays there too — redundant with top-bar but useful when debugging.)
- The e2e test suite.

## Non-goals (v1.8+)

- End-to-end render latency / GPU + compositor timing.
- Worker utilization optimization (raising chunk size, parallelizing non-NN tick phases).
- Reconciling the in-app process-monitor widget's numbers against profile data. (Earlier analysis suggested the 38% reading IS accurate given the math; revisit only if it ever conflicts with profile data.)
- Flame-graph display.
- Persisted profile session export.
- Cross-tab profile diff.

## Success criteria

1. Status text in the top-left visibly updates every RAF — tick number advances by 1 per visible update when sim is at 60 TPS, by more when sim is at higher TPS (always reflecting the freshest SAB read).
2. Status text shows `TPS` and `FPS` numbers, each a positive integer at steady state.
3. Toggling sim TPS slider 60 → 1000 → 60 produces visible TPS changes within ~1 s, and FPS stays near 60 throughout (confirms render isn't sim-gated).
4. With profiler on at default settings, the panel shows `window: ~60.0 s` at the top.
5. `nn.forward.calls` at pop 1500 / 60 TPS shows ~5 million over a 60 s window (creature_count × ticks), not ~3600 (ticks only). `nn.forward.ms/call` shows microseconds per creature (e.g., 0.05 ms), not milliseconds per tick.
6. `grass_step.row_compute.calls` shows ~960 × ticks (GRASS_GRID_DIM × ticks); `ms/call` shows microseconds per row.
7. e2e suite (`pnpm test:e2e`) still passes — all 5 existing tests green.

## Budget

**Realistic: 1 focused day.**

- Most of the diff is mechanical: paired atomic counters next to every existing `_us` accumulator in Rust, paired `call_count` field in the TS sample tuple, paired argument on `record_under_root`. Touchpoints are well-scoped (see "What changes" file list).
- The display rewrite in `perf-panel.ts` is small — one new "window" row, one column-formula change for `ms/call`.
- The status bar fix is two-line: delete the throttle, format the new string.
- The FPS counter is a closure with a 4-variable state machine.

If anything stretches the budget, it's the JSON shape extension (`profile_report_json` carrying call counts) — but that's still tens of lines, not a structural change.
