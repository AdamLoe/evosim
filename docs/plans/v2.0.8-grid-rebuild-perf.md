# Mission: tick hot-path perf (v2.0.x)

## Goal

Cut the serial tick costs that dominate at large scale, measured via
`benches/tick_profile.rs`. Two waves:

- **Wave A — spatial-grid rebuild** (shipped): the rebuild ran 3× per tick at
  ~900–1000µs each and was the hidden bulk of BOTH `tick.grid.rebuild` and
  `tick.movement`. It is `O(hash_dim²)`, not `O(creatures)`: at the 9600u default
  the 960² grid held ~1500 creatures (0.0016/cell) → pure empty-cell array
  sweeping. Two levers took combined `grid.rebuild + movement` from ~2995µs to
  ~404µs/tick (7.4×) ≈ 2.2× in-app TPS.
- **Wave B — grass mip-pyramid refresh cadence** (this wave): once grid+movement
  were gone, `grass_step` + `pyramid_refresh` dominated at the user's large scale
  (19200 world, 3840²=14.7M grass cells, 8000 creatures: grass_step≈5500µs,
  pyramid≈2000µs of a 9000µs tick). `pyramid_refresh` was a FULL recompute every
  tick feeding only zoomed-out render (default zoom=1 reads L0=density directly,
  not the pyramid) + far-grass NN sensing — neither needs per-tick freshness.
  Refreshing every Nth tick (N=4) amortizes it ~4×. Measured: 3675→870µs at the
  dense 9600/full-grass regime.

## Scope

- **Lever 1 — `HASH_CELL` 10u → 20u** (`app/crates/evosim/src/constants.rs`). Matches the cell to
  `PROXIMITY_RANGE = 20u` (the widest grid query) → grid 960² → 480², a 4–5×
  cheaper rebuild. **Behavior-neutral**: coarser cells change only bucket
  granularity; the exact-distance filter returns the identical neighbor set.
  Test updates: `constants.rs` `default_world_dims_match_spec` (960→480),
  `grid.rs` `TEST_DIMS.hash_dim` (120→60, 1200u world at 20u cell).
- **Lever 2 — one grid rebuild per tick** (`app/crates/evosim/src/world/tick.rs`). Deleted the two
  rebuilds embedded in `apply_movement_and_repulsion` (post-integration and
  post-repulsion). Repulsion + attack + species mating now run on the step-1
  grid. Integration moves a creature ≤ `MOVE_SPEED_MAX` (5u) = 0.25 cell at
  HASH_CELL=20, so neighbor buckets are at most a quarter-cell stale vs the 3u
  repulsion/attack reach. **Safe-by-construction**: every post-movement grid
  consumer (`attack`, `handle_mating`) re-checks exact distance on *current*
  positions, so a stale bucket can only cause a benign *missed* target that tick
  — never a false hit, energy violation, or crash.
- **Diagnostic spans**: `apply_movement_and_repulsion` is now decomposed into
  `tick.movement.integrate` / `tick.movement.repulsion` / `tick.movement.apply`
  sub-spans (the rebuilds it used to dominate are gone). These are the spans that
  located the issue and let the win be confirmed in the live profiler.
- **Wave B — pyramid refresh cadence**: `GRASS_PYRAMID_REFRESH_PERIOD = 4`
  (`app/crates/evosim/src/constants.rs`); gate `self.grass.refresh_pyramid()` on
  `self.tick % PERIOD == 0` in `World::step` step 7b. The `tick.pyramid_refresh`
  span stays every tick (records ~0 on skipped ticks) so the profiler shows the
  honest amortized cost. Tick 0 is a refresh tick → pyramid valid from frame 1.
  **Fidelity tradeoff**: zoomed-out render + far-grass NN sensing lag ≤ N ticks
  (the pyramid already lagged NN 1 tick by construction; this widens it). Default
  zoom=1 render is unaffected (reads L0=density).
- **`benches/tick_profile.rs`** — native per-phase tick breakdown reproducing the
  in-app profiler numbers (threaded, population-pinned, env-tunable world/grass/
  full-grass/pop). Keep as the perf regression surface.

- **Wave C — two batched bug fixes** (this wave):
  - **"Any slider Apply wipes the world."** Root cause: the sim worker drains ALL
    `SLIDER_COUNT` SAB lanes on every control-epoch advance, but seeded lanes only
    from `initial_sliders` (built from dev-panel widgets). `max_population`'s
    control lives in the **perf panel**, so it was absent → lane 17 stayed 0 →
    the next Apply of *any* slider re-applied `max_population=0` →
    `apply_max_population` clamps to **cap=1** → `handle_births` culls the world to
    1. Reproduced natively (`benches/grass_spread_repro.rs`, `TICK_CULLBUG=1`):
    pop 4000→1 in one tick. Fix A: worker seeds every lane from
    `initial_sliders[name] ?? sliders_defaults_json()[name]` so no lane is ever 0
    (`web/src/sim-worker.ts`). Fix B: `currentSliderState()` injects
    `max_population` from settings so it's applied at boot AND seeds its lane
    (`web/src/widgets/devpanel.ts`) — also makes the persisted cap / low-core
    auto-lower actually take effect at boot. Regression guard:
    `sliders_defaults_json_covers_every_slider_name` (`app/crates/evosim/src/wasm_api.rs`).
  - **Snapshot `Float32Array` alignment crash** (`RangeError: start offset … multiple of 4`).
    The per-slot snapshot size `slot_bytes = 64 + creature_bytes + 2·win_axis²` is
    `≡2 (mod 4)` when `grass_dim` (hence `win_axis`) is **odd** (e.g. 19200/7 → 2743),
    so slot 1's f32 creature SoA starts at a 2-mod-4 byte offset and
    `new Float32Array(buffer, base + creatureOffset, …)` throws every other frame.
    Fix: pad `slot_bytes` up to a multiple of `SNAPSHOT_SLOT_ALIGN = 4` in both
    `SnapshotLayout::from_grass_cell_count` (Rust) and `makeSlotLayout` (TS, kept
    in lockstep). Even grass_dim (1920/3840 defaults) is already aligned → no-op.
    Regression guard: `snapshot_slot_bytes_4_aligned_for_all_grass_dims`. While
    fixing, also completed `sliders_defaults_json` (was missing `lod_bias` +
    `grass_multisight`) so Fix A's defaults-fallback covers every lane.
  - **Founder count capped at 32.** Three Rust clamps (`new_with_founder_count`,
    `apply_founder_count`, and the single-pool spawn loop in `World::new_with_sliders`)
    plus the UI slider max pinned founders to 32. Raised the Rust clamps to
    `MAX_POP_FOR_SIM` and the UI max to 8000 so single-pool worlds can seed 1000s
    of founders at tick 0. Color is genome-derived per creature (no palette), so
    no color-system change; the snapshot region is `MAX_POP_FOR_SIM`-sized so it
    fits. Verified: 6000 founders spawn at tick 0 (was 32).

## Non-goals

- **`grass_step` 10× — DEFERRED to the user's call.** At 14.7M fully-grassed cells
  it is at the O(occupied-cells) memory-bandwidth floor; the per-cell path is
  already optimal (fused RNG, stack freeze, active-tile frontier). A 10× requires
  an algorithmic change that trades fidelity/memory: cadence/throttle (menu §1),
  event-sampling with a live-cell list (menu §3), or coarser `grass_size`
  (free ~4×). User chose "pyramid cadence only for now." Levers recorded in
  `perf-optimization-ideas.md`.
- O(N) rebuild structure (touched-cell reset / hashed grid) — unnecessary once the
  grid is coarsened; parked in `perf-optimization-ideas.md`.
- `nn` / `attack` tuning.
