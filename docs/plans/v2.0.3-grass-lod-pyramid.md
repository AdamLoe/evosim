# Mission: grass LOD pyramid — one mip serving render, snapshot, and sensing

## Goal

Scale grass past the default grid by replacing "store + ship + render + sense
the **whole** field" with a single **u8 box-filter mip pyramid** (a clipmap).
The same bytes feed three consumers:

- **Render LOD** — upload only the viewport's slice of the coarsest mip that
  still fills the screen → a **constant ~budget² texels/frame regardless of
  world size**.
- **Snapshot** — publish only that window into the existing double-buffered
  snapshot slot.
- **NN sensing** — sample the mip whose texel ≈ the sense footprint → **O(1)
  per tap, independent of how many cells sit under a creature**.

This bounds the three **output** scaling walls that storage-only changes can't
(see below). Two framing points, given the project steer (CPU > memory, 1B is
*aspirational*):

- **It bounds OUTPUT, not COMPUTE.** Propagation + mip refresh stay O(cells) on
  the worker (refresh *adds* ~⅓ of a full pass), so the tick stays
  compute-bound. At 1B this delivers **renderable + sensible, not
  interactive-TPS** — 1B is likely unreachable at a decent tick rate either way
  (see v2.0.2's "Known floor"). The constant-budget² claim is for
  upload/snapshot/sense only.
- **The sensing piece has standalone value at *any* scale.** The multi-band
  (near/med/far) perception upgrade (Consumer 3) is a gameplay win independent
  of 1B; render-LOD + windowed-snapshot are the parts that are "scaling only."
  So this plan is part perception-upgrade (useful now), part aspirational
  scaling spine — not one monolithic 1B feature.

### Relationship to v2.0.2

Depends on [`v2.0.2-grass-scatter.md`](v2.0.2-grass-scatter.md) landing first
(the pyramid is a u8 box-filter; level 0 mirrors that plan's `AtomicU8`
density field). This plan **absorbs and supersedes v2.0.2's Phase 2**
("viewport-bounded snapshot" + biome-at-LOD tint) — the pyramid is the proper,
unified form of both. When this is adopted, slim v2.0.2 to Phase 1 only and
point its scaling section here.

## Why storage-only changes don't reach 1B (root cause, confirmed in code)

u8 density shrinks *memory*, but the binding constraints at scale are on the
**output** path, and storage doesn't touch them:

1. **Per-frame upload bandwidth.** The renderer uploads the entire grass
   texture every frame (full `texImage2D`/`texSubImage2D`, R8, no dirty-rect,
   [`render-gl.ts:980`](../../web/src/render-gl.ts#L980)). At 1B cells that is
   1 GB/frame × 60 fps = **60 GB/s** — ~10× over consumer GPUs. No storage
   choice fixes this; you must only upload the visible region.
2. **WebGL2 texture dimension.** Max ~4k–16k/axis; 1B cells is ~31.6k/axis →
   **cannot be one texture**. Needs tiled/streamed sampling, which the single
   fullscreen-quad → single grass texture design doesn't have.
3. **Per-creature sense cost grows with cell density — but only if cells
   shrink.** `compute_grass_density_sectors`
   ([`proximity.rs:351`](../../src/world/proximity.rs#L351)) scans a fixed
   *world-unit* radius. Today `GRASS_CELL_SIZE` is fixed at 5.0 and
   `grass_dim = world_size / 5` ([`constants.rs:183`](../../src/constants.rs#L183)),
   so "1B cells" means a **much larger world**, *not* finer cells — and a bigger
   world does **not** increase cells-under-a-creature, so this wall does **not**
   bite. It only bites if cell size becomes smaller / runtime-configurable (1B
   on a *small* map → ~10³ cells under one creature → O(creatures × 10³–10⁴)).
   So Consumer 3's *cost* motivation is conditional on a smaller-cell mode that
   doesn't exist yet — its *perception-upgrade* motivation is not.
4. **Address space — real, but accepted, not engineered around.** At 1B cells
   the working set is density (u8, ~1 GB) **+ the per-cell `capacity` array
   (`Vec<f32>`, [`grass.rs:153`](../../src/grass.rs#L153) → ~4 GB!) + the
   per-cell biome u8 (~1 GB)** — past wasm32's ~2 GB before the snapshot. We
   **keep the arrays** (resolved: array-only — CPU > memory, and `capacity_at()`
   in the scatter hot loop must stay one array read, not an O(blobs) recompute).
   So address space is the ceiling that *caps how large a world can get* —
   reached at roughly the same scale the compute floor already makes the tick
   unplayable. We **accept** wall #4 rather than fix it; only the windowed
   snapshot below trims the snapshot's own contribution.

The pyramid addresses the **three output walls** (upload, texture dim, sense):
the renderer + the snapshot only ever touch a windowed mip slice, and sensing
samples a mip texel instead of the cells beneath it. Wall #4 (address space) is
accepted as the practical world-size ceiling.

## The structure

`level[0]` **aliases the live density field** (the `AtomicU8` base — *not*
copied; only L1+ are owned by the pyramid). `level[L]` (L ≥ 1) is a rounded 2×2
box-downsample of `level[L-1]`, stored as an **average** density on the same
`0..=255` scale — i.e. a literal texture mipmap, directly GPU-uploadable. The
owned levels (L1+) cost ~**⅓** of the base (`¼ + 1/16 + … = 1/3`); a *copied*
L0 would be 4/3× — so the alias matters (~1 GB vs ~1.33 GB at 1B).

- **Non-power-of-two is the real case.** `grass_dim = round(world_size/5)` is
  **1920** by default (`2^7·15`, not a power of two,
  [`constants.rs:460`](../../src/constants.rs#L460)). So `dim >> L` is wrong;
  store **per-level dims** (`d_L = d_{L-1}.div_ceil(2)`) in a `Vec<usize>` and
  index that. The gather **edge-clamps**: a parent at a ragged (odd) border
  averages the 1–4 in-bounds children (matching the existing tile `.min(dim)`
  convention, [`grass.rs:449`](../../src/grass.rs#L449)).

## Refresh — gather, lock-free, time-stable (NOT "exact")

Build each level by **gather**: every parent texel is written once and reads
its (read-only) children. So a level parallelizes with **no atomics**, and
there is an implicit **barrier between levels** (level L depends on L-1).

- **Stable, not exact.** u8 averages-of-averages aren't the true base mean —
  ≤ ½ LSB rounding per level, a few /255 worst case at the depths we use.
  Noise for grass. The point vs the rejected *incremental delta-add* variant
  isn't exactness, it's that recompute's error is **bounded and the same every
  tick** (deterministic in the current field, no time-accumulation), whereas
  lossy incremental adds **drift unboundedly** and would need a rolling
  rebuilder. We keep u8 (GPU-native, 33% mem); u16/u32 sums would buy true
  averages at 2–4× the mip memory — not worth it for density.
- **Phase placement.** Refresh runs in its **own phase after `grass_step`**, so
  the field is quiescent — relaxed loads of the `AtomicU8` base are reading a
  settled field (no tearing — single byte — and no mixed-time issue).
- **Refresh must follow the propagation active set, not blindly full-O(N).** A
  full `O(N)·⅓` recompute every tick is fine and simplest **at default scale**
  (cheap). But at large scale it would **reimpose an O(N) floor that defeats
  v2.0.2's sparse-frontier win** — the point of the active-tile set is that
  quiet regions cost nothing, and a full mip rebuild would charge for them
  again. So the large-scale design **rebuilds only the dirty subtree** (dirty
  base tiles → their L1 parents → …, unchanged children stay valid), keyed off
  the *same* active/dirty tile set propagation already maintains. Decay's
  "living noise" makes the dirty set ≈ all *grassy* cells (not all cells), so it
  still tracks grass area, matching propagation. Start full at default scale;
  the active-set-aligned refresh is **required** for the aspirational large
  scale, not a speculative "only if profiling" extra.

## Consumer 1 — render LOD (clipmap)

Pick the coarsest mip whose visible span ≤ the upload budget (e.g. 2000²),
copy that level's viewport rows into the upload buffer, `texSubImage2D` into a
budget²-sized texture. Upload is **constant (~4 MB/frame at a 2000² budget)
regardless of world size**, and always fits one texture. Zoomed in → fine
levels; zoomed out → coarse levels (true mip behavior). Optional **trilinear**
(blend two adjacent levels) to avoid LOD popping on zoom.

## Consumer 2 — snapshot publish (slot coherence solved; the *protocol* is not)

The pyramid lives **worker-side**; main **never reads the live pyramid**. Each
tick the worker copies only the clipmap **window** into the double-buffered
snapshot slot, published via the existing `CTRL_SEQ`/slot-flip — so the
cross-thread *coherence* primitive is reused as-is. But "coherence solved" ≠
"done"; the protocol work is real and is the trickiest part of consumers 1+2:

- **The slot is fixed-shape today.** It is exactly `grass_dim²` bytes
  ([`wasm_api.rs:170`](../../src/wasm_api.rs#L170)), main builds a full-field
  view ([`main.ts:385`](../../web/src/main.ts#L385)), render uploads a full
  `dim × dim` texture ([`render-gl.ts:984`](../../web/src/render-gl.ts#L984)). A
  windowed mip snapshot needs **per-slot metadata** — mip level, window origin,
  window w/h, texture dims, wrap mode — plus the shader UV transform mapping the
  window back to world space.
- **The worker needs the camera, and there's no channel for it.** LOD level +
  window depend on camera/zoom, which live **main-side**, and since v1.10 the
  only surviving postMessage is the boot handshake (all control is SAB). So add
  a **camera lane to the control SAB** (main writes cx/cy/zoom/viewport, worker
  reads) — consistent with the all-SAB design.
- **Camera-only repaints break.** Today a pan/zoom repaints from the *same*
  snapshot with no worker tick; with windowing, a camera move needs a *new*
  window. Mitigate with a **generous margin** (publish a border beyond the
  viewport so small pans stay covered) and accept the window **lags the camera
  by ≥1 snapshot**.

This replaces v2.0.2's "viewport-bounded snapshot quantize."

## Consumer 3 — NN sensing (a multi-band *upgrade*, not just cheaper)

Sample the mip whose texel ≈ a given sense radius → **O(1) per tap,
independent of cell density**. The win isn't only speed: today the sense
collapses everything into *one* distance band — a single 1/d²-weighted scalar
per sector ([`proximity.rs:438`](../../src/world/proximity.rs#L438)). The mip
lets us hand the NN **near / medium / far grass density per direction** for
about the same cost — strictly *more* information, and a natural one (near vs
far gradients are perceived differently in nature). So this is a deliberate
sensor *upgrade*; the expected A/B direction is *better* foraging, not worse.

- **Still a sensor-semantics change → gate it on a behavioral A/B.** Dropping
  the single 1/d² band for multiple flat-per-band taps changes *what* the
  creature perceives. Keep the 1/d² path runnable for direct comparison and
  gate the swap on "forages at least as well." There is **no migration cost**:
  with no save/load (every page load is a fresh world) the NN input vector can
  be redesigned wholesale — the only cost is a slightly wider input layer (a
  few extra taps → a marginally bigger first matmul).
- **Coordinates must match the field convention.** Mirror
  `GrassGrid::bilinear_sample` ([`grass.rs:864`](../../src/grass.rs#L864)):
  `rem_euclid` when `dims.wrap_world`, clamp/ghost otherwise. Naive
  `(x/cell) as usize` saturates negatives to 0 (wrong for both wrap and walled).

## Biome at LOD — tint via the snapshot window (array stays)

Biome **stays a per-cell array** (resolved: array-only — CPU > memory; going
procedural would put an O(blobs) recompute in v2.0.2's per-spread hot loop, and
the array is trivial at default scale). The only LOD problem is the **render
tint**: the renderer tints grass by per-cell biome and uploads biome as its own
full texture today ([`render-gl.ts:944`](../../web/src/render-gl.ts#L944)), so a
zoomed-out view would have no coarse biome to sample.

**Resolved: bake biome into the windowed snapshot as a second channel.** When
the worker publishes the clipmap window (Consumer 2) it also writes the matching
biome window — **mode**-downsampled, not averaged (biome is categorical) — into
the slot. This reuses the snapshot-window machinery exactly, needs no new
texture path, and keeps biome in lockstep with the grass window. (A standalone
biome mip is the equivalent alternative; the snapshot channel is cleaner because
it piggybacks on the window that already has to exist.) No procedural biome.

## Generalizes to creature perception (downstream, own step)

The same structure extends to creature sensing, with a refinement that falls
out of *what creatures are*: **match the sensor to the entity type.**

- **Grass is a field** → density at every range (mip taps; near/med/far).
- **Creatures are discrete agents** → the nearby *individual* matters
  (reactive), the far *mass* matters (strategic). So creatures want **two
  different signals**, not one signal at two resolutions:
  - **`nearest_proximity` (near)** — the existing spatial-hash starburst
    ([`proximity.rs:220`](../../src/world/proximity.rs#L220)), unchanged. A
    small radius holds few neighbours regardless of population, so the hash is
    cheap *and* precise exactly where precision matters. A hash stores
    *entities* (∝ population), so it never blows up with world area the way a
    per-cell field does — its only blow-up is *query* cost at a large radius.
  - **`density` (medium / far)** — a **coarse N-channel creature mip** (one
    channel per species, N capped). Splat creatures into a *coarse* base each
    tick (∝ creatures) and downsample; a creature reads `channel[own]` = allies
    and `total − channel[own]` = enemies. O(1) per tap at any radius — exactly
    where the hash walk would explode. Coarse is fine: far creatures are a
    blurry mass anyway.

Because nearest and density are *different* signals, the bands need not be
disjoint (nothing to double-count) and the mip never has to resolve
individuals. Optional later: *near* creature density (crowding), which
`nearest` can't express. This is a **separate step** (own behavioral A/B);
it reuses the pyramid machinery with N channels + a coarse base.

## Scope

- `GrassPyramid` (L0 **aliases** the live density field; owns per-level `Vec<u8>`
  for L1+ and stored per-level dims), `new(dim)` building the chain, asserts
  (`density.len() == dim²`).
- `refresh(&density)` — phased after `grass_step`; gather build, edge-clamped,
  non-pow2 safe. Full recompute at default scale; **dirty-subtree keyed off the
  propagation active set** for large scale (preserves the sparse win).
- Snapshot protocol: per-slot window metadata (mip level, origin, w/h, tex dims,
  wrap) + a **camera lane in the control SAB** (main→worker) + margin policy.
- Render path: clipmap window extraction (Rust) + budget²-texture streaming
  upload (`render-gl.ts`); LOD selection from camera zoom; UV transform for the
  window; optional trilinear.
- Biome tint at LOD: **biome window baked into the snapshot slot** (mode
  downsample); array stays, no procedural biome.
- NN sensing (separate gated step): mip-sampled near/med/far sectors behind a
  **new `NnInputLayout` variant** (restart-required, A/B flag); wrap/walled
  coords; behavioral validation.

## Non-goals

- The scatter propagation mechanic (owned by v2.0.2).
- **1B at interactive TPS.** This plan bounds *output*, not the tick — the sim
  stays compute-bound (propagation + refresh are O(cells)). 1B is renderable +
  sensible, not playable; CPU, not this plan, is the 1B blocker.
- **Procedural biome/capacity.** Resolved against: arrays stay (CPU > memory);
  address space is the accepted world-size ceiling, not something we fix here.
- memory64 / going past the wasm32 ceiling (separate; the pyramid makes the
  *output* bounded, not the working store).
- Exact large-area integrals / summed-area tables (u8 mip averages are
  approximate by design — accepted).
- The creature-perception generalization (nearest-hash + density-mip) is a
  **downstream step**, not this plan — see the section above; here the pyramid
  serves grass only.

## Plan

1. **Pyramid core + tests.** `GrassPyramid::new` + `refresh` (gather,
   edge-clamped, per-level dims). Native first; test non-pow2 averaging,
   bounded-error vs a reference full-average, wrap/walled `sample`.
2. **Snapshot window + camera lane.** Per-slot window metadata + a camera lane
   in the control SAB (main→worker) + margin policy; publish the window into the
   slot; confirm coherence across the slot-flip and that camera-only pans stay
   covered. *(Low risk, pure plumbing — do before render.)*
3. **Render LOD.** Clipmap window extraction + budget²-texture streaming upload +
   zoom→LOD selection + UV transform. Verify constant upload size + correct
   zoomed-out picture. *(Low risk, zero behavior change.)*
4. **Biome tint at LOD.** Bake the mode-downsampled biome window into the
   snapshot slot; tint correct at every zoom. *(Array stays; no procedural.)*
5. **Mip-sampled sensing — separate, gated, can ship last or never.** New
   `NnInputLayout` variant (restart-required) feeding near/med/far sectors;
   behavioral A/B that foraging is *at least as good* vs the kept 1/d² path;
   tune the band/tap layout. The only behavioral change and only high-risk
   step — independently gated, not on the render/snapshot critical path.
6. **Measure at scale.** Synthetic large/dense grid: confirm bounded frame time
   zoomed out, O(1)-ish sense cost vs cell density, and the upload/texture walls
   are gone.
7. **Doc migration.** Rewrite `render-pipeline.md` + `simulation-core.md` +
   `shared-memory-and-protocol.md` (and `decisions/{render,sim}.md`); slim
   v2.0.2 Phase 2 to point here; delete this plan on ship.

## Verification

- `cargo test`: pyramid refresh (non-pow2 edge averaging; per-level dims;
  error within tolerance of a true full-grid average), `sample` wrap+walled,
  `viewport_window` bounds.
- Browser, default scale: render-via-pyramid is visually ≈ today; no
  regression with grass on.
- Browser, synthetic large/dense scale: upload size constant (~budget²)
  regardless of world size; frame time bounded when fully zoomed out; sense
  cost flat as cells-per-creature grows.
- Behavioral: creatures still forage effectively on the mip-sampled sense
  (longer-run check vs the current 1/d² sense).

  3. **Biome tint at LOD: snapshot biome channel vs standalone biome mip**
