# Red-team: v2.0.1 off-thread snapshot writer (concurrency/control review)

READ-ONLY adversarial review of `docs/plans/v2.0.1-writer-plan.md` against HEAD
`feat/v2.0.0` source. Payload/byte details (grass quantize, creature pack) are
explicitly OUT of scope per the mandate — this is a pure concurrency/control-flow
red-team. Code cross-referenced: `src/wasm_api.rs` (`write_snapshot` :551-641,
layout :169-189), `src/control_sab.rs`, `web/src/sim-worker.ts`
(`writeSnapshotToSAB` :421-431, `simLoop` :435-520, boot :246-249),
`web/src/main.ts` (`frame` :310-441, slot read :369-389), `web/src/sim-bridge.ts`
(`slotOffset` :159, `terminate` :545-562).

Verdict up front: **implementable as written, conditionally.** The core
producer/consumer skeleton is sound and matches the existing fabric. But there are
**two blocker-level gaps** the plan hand-waves, plus several should-fixes that must
be folded into Phase B before the high-risk step (landing-order step 4). Details
below.

---

## 1. Lost wakeup (futex) — SHOULD-FIX (plan is correct, but underspecified)

**Plan's claim:** writer re-checks `WRITER_REQ_SEQ` against `last_done` AFTER
deciding to wait and passes that exact value to `Atomics.wait`; wait returns
`not-equal` immediately if it already advanced.

**Verdict: the *pattern* is correct, but the plan describes it imprecisely and the
imprecision is dangerous.** The plan says the writer parks with
`Atomics.wait(WRITER_FUTEX, last_seen)` (§2 writer step 1) and *separately* reads
`WRITER_REQ_SEQ` (§2 writer step 2). That is a TWO-WORD design: it waits on
`WRITER_FUTEX` but the work signal is `WRITER_REQ_SEQ`. `Atomics.wait` only
compares the value of the **word it waits on**. If `WRITER_FUTEX` is a distinct
word from `WRITER_REQ_SEQ`, then the "pass the observed value into wait" mitigation
only closes the window if the value passed is the value of `WRITER_FUTEX` — not
`WRITER_REQ_SEQ`. The plan conflates the two.

**Concrete lost-wakeup interleaving (two-word design, naive):**
1. Writer finishes a pack, sets `last_done = REQ`.
2. Writer reads `WRITER_REQ_SEQ` == `last_done` → decides to sleep.
3. *(window)* Tick thread: stage; `add(WRITER_REQ_SEQ, 1)`; `notify(WRITER_FUTEX)`.
   The notify wakes nobody (writer not yet parked). `WRITER_FUTEX` value unchanged.
4. Writer calls `Atomics.wait(WRITER_FUTEX, futex_val_read_in_step_2)`. Because the
   tick thread only bumped `WRITER_REQ_SEQ`, NOT `WRITER_FUTEX`, the wait's value
   compare still matches → **writer sleeps forever with a pending request.** Lost
   wakeup. The existing `CTRL_FUTEX` pacing has the same shape but is benign there
   (it's a timed wait, `Infinity` only when paused and main always notifies on
   unpause).

**Fix (make it a ONE-WORD design):** the word the writer waits on MUST be the same
word that carries the request signal. Collapse `WRITER_REQ_SEQ` and `WRITER_FUTEX`
into a single atomic `WRITER_REQ_SEQ`:
- Tick thread: `Atomics.add(WRITER_REQ_SEQ, 1)` then `Atomics.notify(WRITER_REQ_SEQ)`.
- Writer: `let req = Atomics.load(WRITER_REQ_SEQ); if (req == last_done)
  Atomics.wait(WRITER_REQ_SEQ, req); ` — the value passed to `wait` is the
  just-observed `req`. Now the step-3 `add` changes the waited word, so the wait
  returns `not-equal` immediately and the wakeup cannot be lost.

This is the canonical single-word futex. The plan must state explicitly that the
wait-word == the signal-word; as drafted (two words) it is a latent blocker. Mark
this **should-fix** only because the plan's intent is right and the fix is a
one-line collapse — but it MUST be written down or an implementer will build the
two-word version and ship a lost-wakeup.

Note also: under wasm-bindgen-rayon the writer thread is a real Web Worker, so
synchronous `Atomics.wait` is legal there (same as the existing tick-thread pacing
wait at `sim-worker.ts:464,515`). Good — no `waitAsync` needed on the writer.

## 2. Torn snapshot / use-after-clobber (stage double-buffer) — BLOCKER

**Plan's claim (§3):** the sim-side stage is double-buffered; the tick thread writes
the stage the writer is NOT reading, indicated by a `STAGE_IN_USE` atomic the writer
sets while consuming and clears when done. If both stages busy, tick thread skips
staging (drop), sim still ticks.

**Verdict: a 2-entry stage with a single `STAGE_IN_USE` flag does NOT suffice and
the plan's own "skip if both busy" branch is unreachable as described — there is a
torn-stage race.** Walk it:

The writer holds stage A across its ENTIRE pack (the whole point — it reads the
stage during quantize/pack, which is the long operation). So while the writer packs
from A, the tick thread must stage T+1 into B. Fine. But now tick T+2 arrives while
the writer is STILL packing A (writer slower than tick — the regime the plan says
is normal under load). The tick thread wants to stage T+2. A is held by the writer.
B holds T+1, already staged but not yet consumed. The plan says "write the stage the
writer is NOT reading" → that's B. So the tick thread **overwrites B with T+2 while
B is the staged-but-unconsumed T+1.** That is fine ONLY if the writer has not yet
started reading B. But the writer, on finishing A, will next pick up "the latest
request" = B. Sequence:

1. Writer packing A (reads A).
2. Tick stages T+1 → B. `WRITER_REQ_SEQ` bumped.
3. Tick stages T+2 → **B again** (writer still on A). Overwrites T+1. OK so far
   (T+1 dropped, intended).
4. Writer finishes A, clears A's IN_USE, reads latest req → consumes **B**.
5. Tick stages T+3 → must pick "not the one the writer reads." Writer is on B, so
   tick picks **A**. Fine.
6. Tick stages T+4 → writer still on B → tick picks A again, overwrites T+3. Fine.

So with strict "writer always consumes the freshest staged buffer, tick always
writes the other," 2 stages + correct IN_USE tracking DO work — BUT only if
`STAGE_IN_USE` tracks **which specific stage index the writer holds**, not a single
boolean. The plan says "a `STAGE_IN_USE` atomic the writer sets while consuming" —
singular. A single boolean cannot tell the tick thread which of A/B the writer
holds, so the tick thread cannot reliably pick "the other one." **The race:** if
the tick thread guesses wrong (picks the stage the writer is mid-read on), it tears
the stage the writer is packing from → torn snapshot (payload-agnostic: the writer
reads a half-overwritten freeze).

**Concrete tear:**
1. Writer consuming B (single boolean IN_USE = 1, no index).
2. Tick thread wants to stage T+k. Reads IN_USE=1, knows writer is busy but NOT
   that it's on B. Plan's "write the one the writer is NOT reading" requires the
   index. Without it, implementer defaults to "write the inactive-by-last-write" =
   could be B. → tick writes B while writer reads B → **torn.**

**Fix (blocker):** the handshake must publish the writer's currently-held stage
INDEX as an atomic (`WRITER_STAGE_IDX`, 0/1), written by the writer BEFORE it begins
reading that stage, with a store-before-read fence. Tick thread reads
`WRITER_STAGE_IDX`, writes the OTHER index. AND the tick thread must never write the
index it is about to hand the writer next without confirming the writer released the
previous holder. Cleanest: a 3-state ownership word per stage (FREE / TICK_FILLING /
WRITER_READING) or a single `STAGE_OWNER` atomic with values {none, writerHoldsA,
writerHoldsB}. Specify the exact ownership protocol; "a boolean IN_USE" is
insufficient and is the most likely place an implementer introduces a tear.

Additionally: the plan's "if both stages busy, skip staging" branch — with only 2
stages and the writer holding at most 1, the tick thread can ALWAYS find a free
stage (the one the writer isn't holding), so "both busy" never happens with N=2 and
a single writer. The plan's drop-on-stage-full path is therefore dead code as
written; the real drop point is the *slot* side (§3 below), not the stage side. The
plan conflates stage-drop and slot-drop. Clarify: with 2 stages + 1 writer the stage
is never the back-pressure point; drop happens because the writer coalesces (skips
intermediate REQ values), which is fine, but the stage is always writable.

**Grass ping-pong (T+2 mem::swap):** the plan's RECOMMENDED mechanism (fast-stage:
copy dirty tiles into the private stage at handoff, on the tick thread, before
returning control) makes this safe and is correct — once the bytes are copied into
the writer's private stage, the tick thread's `mem::swap` at T+2 touches only its
own density/scratch buffers, which the writer no longer reads. **The fast-stage
approach eliminates the grass T+2 clobber entirely.** The plan's *alternative*
(writer reads `density` directly + 3-buffer reservation) is more fragile and
reintroduces a reservation back-pressure path; recommend the plan DROP the
alternative or mark it explicitly non-default. The recommended path is safe **only
if** the fast-stage copy completes on the tick thread before the tick thread does
anything that could swap/mutate density — i.e. the stage copy is the FIRST thing
after `step_n` and BEFORE the next iteration. The plan says this; keep it as a hard
invariant in the implementation (the copy must be synchronous on the tick thread,
not deferred).

## 3. Triple-buffer publish/read race — BLOCKER (the 2-vs-3 slot analysis is wrong)

**Plan's claim (§3):** 3 slots are REQUIRED because with 2 slots "main may be
reading slot `current` (RAF can hold a view across its paint), while the writer
needs a free slot" — the classic single-spare stall. It recommends 3 slots.

**Verdict: the premise is FALSE for this codebase, and the recommended 3-slot
change is the largest seam churn in the plan for a problem that does not exist as
described — OR, if the premise WERE true, 3 slots would still not fix it without a
seqlock retry on main. Either way the plan's reasoning is broken.**

**Evidence — main does NOT hold a view across paints.** In `main.ts` `frame()`
(:369-389), main reads `CTRL_SEQ`, then `CTRL_CURRENT_SLOT`, then builds
`Float32Array`/`Uint8Array` views over `wasm.memory.buffer`, then calls
`renderWorld` **synchronously within the same `frame()` call**, then returns. The
views are local consts; they are NOT retained across RAF callbacks. `renderWorld`
uploads to GL synchronously. So the window during which main "holds" a slot is
exactly one synchronous `renderWorld` call — bounded, single-threaded on main, and
over before the next `frame()`. There is no "RAF holds a view across its paint"; the
plan's stated justification for slot 3 is incorrect.

**But there IS a real race the plan misses — and it exists at 2 OR 3 slots:**
because the writer is now a SEPARATE thread from main, while main is mid-`renderWorld`
reading slot A (the freshly-published `CTRL_CURRENT_SLOT`), the writer can begin
packing the OTHER slot (B) and then PUBLISH B (store `CTRL_CURRENT_SLOT=B`, add
`CTRL_SEQ`). That publish does not touch A, so main's read of A is fine. The danger
is the FOLLOWING writer cycle: writer next packs A — the slot main is **still
rendering** — because after publishing B, the only "inactive" slot is A. With 2
slots: writer packs A while main reads A → **torn read of A on main.** This is real
and the plan's 2-slot fallback ("writer never packs the slot whose index ==
`CTRL_CURRENT_SLOT`") does NOT fix it, because `CTRL_CURRENT_SLOT` is now B (just
published), so A is fair game to pack — exactly the slot main is reading.

So the plan is RIGHT that 2 slots race, but for the WRONG reason, and its
2-slot-fallback mitigation is broken. 3 slots is the correct fix, but the invariant
must be stated precisely:

**Correct triple-buffer invariant (must be in the plan):** the writer must never
pack EITHER (a) the slot named by `CTRL_CURRENT_SLOT` (last published, may be the
one main is about to read) NOR (b) the slot main most-recently *started* reading.
With 3 slots the writer always has a third slot free. BUT main never publishes which
slot it is reading — so the writer cannot know (b). Two viable resolutions:

- **Option A (seqlock retry on main):** keep store-before-add publish; ADD a
  re-check on main: after building views and BEFORE/AFTER `renderWorld`, re-read
  `CTRL_SEQ`; if it advanced past the seq main read at frame start, the slot may
  have been recycled mid-render → main must re-read and re-render (or skip this
  frame). This is the standard seqlock consumer. With this, **2 slots suffice** (no
  seam change!) because a torn read is *detected* and discarded. The cost is an
  occasional redundant render, never a torn paint. **This is strictly cheaper than
  the 3rd-slot seam change** and is the recommended fix. Note: GL upload of a torn
  frame is wasted but not corrupting (it's overwritten next frame); the seqlock
  catches it.

- **Option B (3 slots + reader-publishes-its-slot):** main writes a
  `MAIN_READING_SLOT` atomic before `renderWorld` and clears after; writer avoids
  both `CTRL_CURRENT_SLOT` and `MAIN_READING_SLOT`. Requires 3 slots (the seam
  change the plan fears) AND a new control word AND main-side writes. Strictly more
  invasive than Option A.

**Recommendation: Option A (seqlock retry on main, keep 2 slots).** It eliminates
the plan's single biggest seam item (the `0|1`→`0|1|2` wire-format change across
`wasm_api.rs` `& 1`→`% 3`, `slotOffset`/`creatureSoAOffset`/`grassOffset` types,
`main.ts:326,370` clamp) and is the textbook solution for "single producer thread,
single consumer thread, freshest-only." The plan should be rewritten to drop the
3rd slot in favor of a main-side seqlock recheck, OR justify why the seqlock is
unacceptable. As written, the plan picks the more expensive option (3 slots) AND
still lacks the recheck needed to make even 3 slots fully safe against (b).

Severity: **blocker** — not because off-thread writing can't be made safe, but
because the plan's chosen mechanism (3 slots, store-before-add, no main recheck)
does NOT actually close the writer-vs-main torn-read race, and its 2-slot fallback
is wrong. Phase B must adopt a main-side seqlock recheck regardless of slot count.

## 4. Deadlock / back-pressure — SAFE (with one caveat)

**Plan's claim:** tick thread never waits on the writer; drops instead.

**Verdict: safe, given the §1 and §2 fixes.** Tracing every potential block:
- Stage availability (§2): with N=2 stages + 1 writer the tick thread always finds a
  free stage; never blocks. ✅ (Once the ownership-index fix from §2 is in.)
- Slot availability (§3): the tick thread does NOT touch slots at all in the new
  design — it only stages + bumps `WRITER_REQ_SEQ`. Slot selection moves to the
  writer. So the tick thread cannot block on slots. ✅
- Futex: the tick thread only `notify`s (never `wait`s on `WRITER_REQ_SEQ`). Its
  only `Atomics.wait` calls remain the pacing/pause waits on `CTRL_FUTEX`
  (`sim-worker.ts:464,515`), unchanged and unrelated to the writer. ✅
- Sustained writer-slower-than-tick: tick keeps ticking, `WRITER_REQ_SEQ` runs
  ahead, writer coalesces to the latest each cycle, intermediate snapshots dropped.
  Renderer only wants freshest → no harm. Sim never stalls → determinism preserved
  (it's the same tick stream regardless of writer speed). ✅

**Caveat (should-fix):** the boot handshake (§5 below) and the *pause* path. On
pause the tick thread parks on `CTRL_FUTEX`. If the writer is mid-pack when pause
hits, it finishes and publishes one final slot — fine. But verify the writer does
NOT also need to be woken on unpause (it doesn't, because the next real tick after
unpause bumps `WRITER_REQ_SEQ`). The plan states this; confirmed safe. One real
risk: if `targetTPS` is very high and the writer is persistently slower, the writer
thread spins through coalesced cycles with near-zero park time — that is CPU-correct
but means the writer never sleeps, competing with the tick thread and rayon pool for
cores. Not a deadlock, but a throughput/pacing concern worth a note: the writer
should be a low-priority consumer and the pool sized so writer + tick + rayon
workers don't oversubscribe (`TARGET_RAYON_WORKERS` vs `hardwareConcurrency` at
`sim-worker.ts:161` already mins against HW concurrency — adding a persistent writer
thread effectively consumes one more thread; account for it in the pool sizing).

## 5. Boot + restart + fallback — SHOULD-FIX (mostly safe; two gaps)

**Boot:** plan recommends running the boot snapshot INLINE (synchronously pack once
before starting the writer thread) — option (a). **Safe and correct.** Matches the
existing boot handshake (`sim-worker.ts:248-249` runs `step_n(1)` +
`writeSnapshotToSAB()` before `boot_ready`). Keeping the boot snapshot synchronous
avoids a boot-time wait-on-`WRITER_DONE_SEQ` deadlock window. The inline boot pack
must use the SAME `pack()` function the writer uses (the landing-order step 2 refactor
gives this) so boot and steady-state produce byte-identical slots. ✅

**Restart / terminate:** `sim-bridge.ts:561` `worker.terminate()` is a hard kill of
the worker AND its rayon runtime. The writer thread lives in that runtime → dies
with it. **No thread leak, no orphan, no cooperative join needed.** ✅ One verified
risk the plan flags correctly: the writer must not be holding anything that blocks
hard-termination — `Atomics.wait` does NOT block `terminate()` (terminate is not
cooperative), and the writer does no blocking I/O. ✅ Confirmed safe.

**Gap 1 (should-fix) — double-spawn / use-before-spawn.** The plan says spawn the
writer "during `WorldHandle` construction (or a dedicated `start_writer()` called
once in `handleBoot` after `initThreadPool`)." `WorldHandle.newWithFounderCount` is
called at `sim-worker.ts:185` — which is AFTER `initThreadPool` (:162). Good. But if
the writer is spawned in the constructor, then on the single-thread fallback path
(`!crossOriginIsolated`, `initThreadPool` skipped) the constructor would try to
`std::thread::spawn` with no threading runtime → spawn fails or panics. **The writer
spawn MUST be gated behind `rayonCurrentNumThreads() > 1`** (the plan says this, but
putting it in the constructor makes the gate awkward because the constructor doesn't
know the thread count cleanly). Recommend an explicit `start_writer()` called from
`handleBoot` ONLY when `rayonOk && rayonCurrentNumThreads() > 1`, NOT in the
constructor. Specify this; the constructor-spawn option in the plan is a foot-gun on
the fallback path.

**Gap 2 (should-fix) — publisher identity & main reader ordering.** The plan flags
that `CTRL_SEQ`/`CTRL_CURRENT_SLOT` publisher moves from tick thread to writer
thread, and claims main needs no change because the protocol (store-before-add,
seq-gate) is unchanged. **This is TRUE for the read protocol but FALSE given §3:**
moving the publisher to a thread that runs CONCURRENTLY with main (today the
tick-thread publisher and main never truly overlapped on slot recycling because the
tick thread also did the read-free packing inline and main's render was short
relative to tick cadence; now the writer can recycle a slot DURING main's render).
So the publisher-identity change is exactly what makes §3's torn-read race live. The
plan must NOT claim "main needs no logic change" — main needs the §3 seqlock
recheck. Flag corrected here.

**Fallback path correctness:** on `!crossOriginIsolated`, the design degrades to
inline `write_snapshot` on the tick thread (= today's behavior). Since today's
inline path already works and the landing-order step 2 keeps `writeSnapshotToSAB()`
as the inline fallback, this is safe **provided** the inline path also adopts the
new `stage()`+`pack()` split so there's only one pack implementation. The §3 seqlock
recheck on main is harmless on the inline path (seq just won't advance mid-render
because the single tick thread isn't concurrently recycling — but keeping the
recheck unconditional is simplest and safe). ✅

## 6. Determinism — SAFE (claim holds), one thing to assert

**Verdict: the "bit-identical writer on/off" claim is TRUE**, with the fast-stage
design. The writer reads ONLY its private stage (a frozen copy) and writes ONLY
`snapshot_buf` + control/seq words — none of which the sim reads. The sim's state
(`grass.density`, `grass.scratch`, creature SoA) is read/written exclusively by the
tick thread, exactly as today (`write_snapshot` at `wasm_api.rs:551` already only
*reads* `self.inner.grass.density` and creature data — it never mutates sim state;
moving that read off-thread onto a frozen copy changes nothing the sim observes).

**Hidden-read check:** the one thing that could break this is if the writer reads
any sim state DIRECTLY rather than from the frozen stage. The plan's *recommended*
fast-stage path is clean. The plan's *alternative* (writer reads `density` directly
via 3-buffer reservation, §2(a)) reintroduces a direct sim-state read by the writer
— still read-only so values don't change, but it makes the determinism proof depend
on the reservation handshake being airtight. **Recommend deleting the direct-read
alternative** so the determinism proof stays trivial (writer touches only frozen
copies). 

**Timing-dependent path:** the DROP/coalesce semantics mean *which ticks get
snapshotted* depends on writer speed (non-deterministic across runs). That is fine —
it does not affect sim VALUES, only which frames the renderer sees. The mandatory
determinism test (§5 of the plan: writer-on == writer-off, bit-identical sim state)
correctly targets sim state, not snapshot cadence. Keep that test scoped to sim
state (`grass.density` + creature SoA after N ticks), NOT to snapshot bytes. ✅

One assertion to ADD: a test that the inline-fallback pack and the writer-thread
pack produce byte-identical slots for the same tick (same `pack()` fn, different
caller) — guards against the two paths diverging.

## 7. Memory ordering — SHOULD-FIX (JS atomics are seq-cst; one Rust-side caveat)

**JS side (worker + main):** `Atomics.store`/`Atomics.add`/`Atomics.load`/`wait`/
`notify` are all **sequentially consistent** in the JS memory model. The
store-before-add publish (`Atomics.store(CTRL_CURRENT_SLOT, slot)` then
`Atomics.add(CTRL_SEQ, 1)`) and the consumer's load-seq-then-load-slot are correctly
ordered under seq-cst — no additional fence needed **on the JS side**. The existing
`writeSnapshotToSAB` (`sim-worker.ts:429-430`) relies on exactly this and is the
proven pattern. ✅

**Rust side (the new bit) — caveat:** the writer thread is RUST code (it runs inside
the wasm instance), and it writes the snapshot BYTES (non-atomic `copy_from_slice`
into `snapshot_buf`) and THEN does the atomic publish. For main to safely observe
the bytes after observing the bumped `CTRL_SEQ`, there must be a
release/acquire-or-stronger edge between "writer's non-atomic byte writes" and
"writer's atomic `CTRL_SEQ` add," AND between "main's atomic `CTRL_SEQ` load" and
"main's non-atomic byte reads."

- If the writer publishes via the SAME JS `Atomics.add` path (i.e. the publish is
  done in TS, or via a wasm `Atomics` intrinsic with seq-cst ordering), the seq-cst
  store provides the release edge over the prior plain byte stores **within the wasm
  shared-memory model** (wasm atomics are seq-cst and act as fences w.r.t. shared
  memory). This is the same guarantee today's tick-thread publish relies on. ✅
- **Risk:** if the writer does the byte packing in Rust but the *publish* is bounced
  back to TS (e.g. writer thread bumps `WRITER_DONE_SEQ`, and the TICK thread or main
  does the `CTRL_SEQ` publish), you split the byte-write and the publish across two
  threads with no enforced happens-before between the writer's byte stores and the
  publishing thread's atomic add. **That would be a real ordering bug.** The publish
  (`CTRL_CURRENT_SLOT` store + `CTRL_SEQ` add) MUST happen on the **same thread that
  wrote the slot bytes** (the writer), so the writer's own seq-cst publish provides
  the release edge over its own byte writes. The plan's §2 writer-step-4 does put the
  publish on the writer — good — but §4 also muses about `WRITER_DONE_SEQ` "or it
  hands the publish to itself." **Pin it down: the writer publishes its own slot;
  never hand the `CTRL_SEQ` publish to another thread.** Make this an explicit
  invariant.
- Use `Atomics.add`/`store` (seq-cst) for the publish, not relaxed wasm atomics. The
  plan inherits the existing seq-cst JS atomics, so as long as the publish stays on
  the JS/seq-cst path this is fine.

**Main-side acquire:** main's `Atomics.load(CTRL_SEQ)` (seq-cst, `main.ts:315`)
before reading bytes provides the acquire edge. With the §3 seqlock recheck added,
main also re-loads `CTRL_SEQ` after building views — that second seq-cst load is the
seqlock validation. ✅

No missing fence on the JS path; the only ordering hazard is the cross-thread
publish split, which the must-fix list pins down.

## VERDICT

**Implementable as written? NO — not safely as drafted. YES with the must-fix list
folded into Phase B.** The architecture (persistent parked writer in the rayon
runtime, fast-stage on the tick thread, store-before-add publish, freshest-only
consumer) is the right shape and matches the existing fabric. But the plan as
written contains two blocker-level concurrency gaps (stage ownership; the slot
race + broken 2-slot fallback) and several underspecified handshakes that an
implementer would get wrong.

### Prioritized MUST-FIX list for Phase B (before landing-order step 4)

1. **[BLOCKER] Slot race + main-side seqlock (§3).** Adopt a main-side seqlock
   recheck: re-read `CTRL_SEQ` after building views; discard/re-render if it
   advanced. With the recheck, **keep 2 slots and DROP the 3rd-slot seam change**
   (eliminates the plan's single biggest seam item). Do NOT ship the plan's 2-slot
   "never pack `CTRL_CURRENT_SLOT`" fallback — it does not close the race. Correct
   the plan's claim that "main needs no logic change."

2. **[BLOCKER] Stage ownership protocol (§2).** Replace the single boolean
   `STAGE_IN_USE` with an explicit writer-held-stage-INDEX atomic
   (`WRITER_STAGE_IDX`, written before the writer begins reading, seq-cst). Tick
   thread writes the other index. Specify the full 2-stage ownership state machine;
   a boolean is insufficient and will tear.

3. **[SHOULD-FIX] One-word futex (§1).** Make the wait-word == the signal-word:
   writer `Atomics.wait(WRITER_REQ_SEQ, observed_req)`; tick thread
   `Atomics.add(WRITER_REQ_SEQ,1)` + `Atomics.notify(WRITER_REQ_SEQ)`. State
   explicitly. The two-word design in the plan has a latent lost-wakeup.

4. **[SHOULD-FIX] Publish stays on the writer thread (§7).** The slot byte-write and
   the `CTRL_CURRENT_SLOT`/`CTRL_SEQ` seq-cst publish MUST be on the same (writer)
   thread for the release edge. Forbid bouncing the publish to another thread.

5. **[SHOULD-FIX] Writer-spawn gating (§5).** Spawn via an explicit
   `start_writer()` from `handleBoot`, gated on `rayonOk &&
   rayonCurrentNumThreads() > 1` — NOT in `WorldHandle`'s constructor (foot-gun on
   the single-thread fallback). Keep boot snapshot inline (option a). Account for the
   extra persistent thread in pool sizing vs `hardwareConcurrency`.

6. **[SHOULD-FIX] Single `pack()` implementation (§5/§6).** Inline-fallback and
   writer-thread paths must call the identical `pack(stage→slot)` fn; add a test
   asserting byte-identical slots from both callers.

7. **[NIT] Delete the direct-`density`-read alternative (§2a/§6).** Keep only the
   fast-stage (private frozen copy) so the determinism proof stays trivial (writer
   touches only frozen copies, never live sim state). Mark the 3-buffer grass
