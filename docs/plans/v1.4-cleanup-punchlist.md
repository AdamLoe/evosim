## Inconsistencies (need orchestrator decision)

### A. `scav` ring flag and `RING_COLORS.scav` still drawn in render.ts

The `creatures_buffer` always emits `off+8 = 1.0` (constant scav flag). `render.ts` reads it and draws a brown ring on every creature. This is not a rendering bug — the ring is always drawn — but it does mean every creature visually shows a "scavenge" ring from a deleted action. Decision needed: remove the scav slot from the creature stride (saves 1 float, requires stride bump from 11 to 10 + all consuming TS code updates), or keep it as a vestigial decoration until a future ring use is found. See §6 above.

### B. Inspector `ins-id` / `ins-pos` rows in HTML

`web/index.html:31–32` has `<dt>ID</dt><dd id="ins-id">` and `<dt>Pos</dt><dd id="ins-pos">`. Neither is written by `inspector.ts::renderInspector`. The creature `id` and `x`/`y` ARE available in `CreatureInspectJson`. Either wire them up (trivial) or remove the rows. Recommend wiring them since they are useful debugging info.

### C. `mean_nose_count` / `mean_eye_count` wasm exports

Both return constants (0.0 and 24.0 respectively). They are never called from the live TS (perf-panel.ts was updated per D3 to drop them). However their tests (`wasm_api.rs:654–669`) exercise the wasm-side API. Decision: delete the wasm exports and their tests (the constants are guaranteed by D3 design), or keep as documentation that D3 removed genome-driven variation. Given they add zero simulation value, delete is the cleaner choice.

### D. `POPULATION_MILESTONES` / milestone bitset

Three World fields (`first_move_fired`, `first_eat_fired`, `population_milestones_fired`) track events that no downstream consumer reads. In v1.3 the event system was deleted (D4). These tracking fields still run every tick. Decision: remove entirely (clean, saves a few loop iterations), or keep as hooks for a future events/observability system. If kept, add a comment that they're reserved for future use.

### E. Worktree branches and dirs

16 `worktree-agent-*` branches exist in the local repo. 16 corresponding worktree dirs exist under `.claude/worktrees/` and are marked "locked" (the Claude process holds the lock). Once the locking process releases them, run:
```
git worktree prune
git branch -D worktree-agent-<hash> ...  (for each)
```
Cannot be done during this session; flag for orchestrator cleanup after the next Claude session restart.
