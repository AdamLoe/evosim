# v1.6 Plan Review

Reviewer: orchestrator-level read of [`docs/plans/v1.6-plan.md`](docs/plans/v1.6-plan.md) against [`docs/plans/v1.6-mission.md`](docs/plans/v1.6-mission.md), [`docs/plans/v1.6-mission-review.md`](docs/plans/v1.6-mission-review.md), and repo HEAD `e29c94d`.

---

## Executive verdict

**Rework Step D, ship the rest with edits.**

The plan does the orchestration job well: every "must do" from the mission review is folded into a locked decision; conflict map, wave order, and per-step prompts mirror the v1.5-plan shape; ambiguities are surfaced rather than buried. As an *orchestration* document this is in good shape.

But there is **one show-stopper in Step D** that no amount of polish later can paper over, plus several smaller specification gaps the implementer will hit on contact:

1. **`Atomics.wait` inside a synchronous `while` loop blocks the worker's message queue.** Step D's pacing pseudocode (`v1.6-plan.md:347-367`) has `drainMessages()` at the top of the loop, but `drainMessages` cannot drain anything: `self.onmessage` callbacks only fire when the worker's event loop runs, which it doesn't while the worker is parked in `Atomics.wait`. The result: sliders, pause, restart, inspector clicks — none reach the worker until the wait times out, *and even then they don't*, because the worker re-enters the loop without ever returning to the event loop. The plan needs `Atomics.waitAsync` + an `await`, not `Atomics.wait`.
2. **`tick.snapshot.write` profile span is opened outside any `tick` parent.** Step C puts it inside `WorldHandle::write_snapshot_to` — a wasm-bindgen entry point called from JS (sim-worker), not from inside `World::step`. The current `Profiler` uses an RAII stack; with no parent on stack, the span is an orphan node, not a child of `tick`. Either move the span TS-side (`web/src/perf.ts`) or rename it `worker.snapshot.write` so the parent-less tree shape is intentional.
3. **`cross_origin_isolated()` Rust export is dead weight.** Main thread already reads `globalThis.crossOriginIsolated` directly in TS ([`web/src/main.ts:95`](web/src/main.ts#L95)); the sim worker can do the same with `(self as any).crossOriginIsolated`. No `js_sys`/`web-sys` plumbing, no `Cargo.toml` feature addition, no new wasm-bindgen export.
4. **Step A1's stride-6→8 leaves the dev build runtime-broken between A1 landing and B landing.** Acknowledged in the plan, but `pnpm typecheck && pnpm build` passes anyway because the stride guard is a runtime throw. Acceptable for orchestrator merge-then-test, *not* acceptable if A1 and B aren't landed in the same session.
5. **Boot-handshake first-paint race.** Step B has main install the render loop after `boot_ready` arrives but before the worker has written a snapshot. The renderer will read `pop=0` (zero-initialized SAB / no postMessage'd payload yet) for ~1 frame. Step B doesn't say what main paints during that window.

Items 1 and 3 are tractable rewrites. Item 2 is a one-line decision. Items 4 and 5 are spec gaps. **No structural rework of waves required.**

**Time budget:** the plan claims 2.5–3 days. Realistic given the locked decisions, but Step B alone is closer to 1.5 days (the message-protocol fan-out across `main.ts`, `sim-worker.ts`, `render-gl.ts`, `devpanel.ts`, `worker-stats.ts`, `perf-panel.ts`, `inspector.ts`, `rail/stats.ts`, plus the `SimBridge` runtime class with request-id correlation), and Step C is 1 day if the SAB write-path debugging goes smoothly. Add a half-day for Step D once the `Atomics.waitAsync` rework lands. **3–4 days, not 2.5–3.**

## Critical issues (must address before any Wave starts)

### C1. Step D's `Atomics.wait` pacing is incompatible with `onmessage` delivery

**Source:** `v1.6-plan.md:347-367` (Step D pseudocode).

The pseudocode:
```
while (!terminated) {
  drainMessages();
  ...
  world.step_n(batch);
  writeSnapshotToSAB();
  ...
  Atomics.wait(ctrl, CTRL_FUTEX, before, sleepMs);
}
```

This cannot work as specified. In a Web Worker, `self.onmessage` callbacks are scheduled as event-loop tasks. As long as the worker is executing synchronous code — including blocking in `Atomics.wait` — the event loop never runs, and `onmessage` callbacks never fire. There is no message queue inside the worker that JS code can poll; messages from main go directly to the worker's event-loop task queue and stay there until JS yields.

`drainMessages()` at the top of the loop cannot drain anything because `onmessage` has never been invoked since the previous iteration. The only messages it can ever see are the ones that arrived *before* the loop started (and even those only if they were buffered by an `onmessage` that ran during boot). After the first `Atomics.wait`, the worker is dark to main forever.

Symptoms the user will see: sliders don't take effect; pause/play does nothing; restart works (terminate is OS-level); inspector clicks send `inspect_at` but no reply ever comes back. Worst case it looks like the worker has crashed; best case it looks frozen.

**Fix:** use `Atomics.waitAsync` (returns `{async: true, value: Promise}` or `{async: false, value: "not-equal"}`) and `await` the promise. The `await` yields to the event loop, `onmessage` callbacks fire and push into a JS-side queue, then `drainMessages` reads from that queue on the next iteration.

```js
const messageQueue = [];
self.onmessage = (e) => messageQueue.push(e.data);

async function simLoop() {
  while (!terminated) {
    drainMessages();                // reads from messageQueue
    // ... compute batch, step_n, writeSnapshotToSAB ...
    const before = Atomics.load(ctrl, CTRL_FUTEX);
    const r = Atomics.waitAsync(ctrl, CTRL_FUTEX, before, sleepMs);
    if (r.async) await r.value;     // event loop runs here → onmessage runs → queue fills
  }
}
```

Browser support for `Atomics.waitAsync`: Chrome 87 (Nov 2020), Firefox 119 (Oct 2023), Safari 16.4 (Mar 2023). All within the v1.6 target.

**Document this in the plan**, with the queue + `await` pattern, not just "use `Atomics.wait`."

### C2. `tick.snapshot.write` will be an orphan span unless retargeted

**Source:** `v1.6-plan.md:209` (Step A1 says open span inside `World::step`), `v1.6-plan.md:321` (Step C says "Add the open/close around the Rust body of `write_snapshot_to` in `src/wasm_api.rs` instead").

The plan eventually settles on the wasm_api.rs location. But `write_snapshot_to` is called from JS (sim-worker), *after* `World::step` has returned. The Rust `Profiler` uses a thread-local RAII stack ([`src/profiler.rs`] — `profile_span!` macro). With no parent on the stack at entry, the snapshot span becomes a top-level root (sibling to `tick`), not a `tick.*` child. The profile panel's tree view will show it at the wrong nesting level.

Two clean options:

- **(preferred) Move the span TS-side.** Open `worker.snapshot.write` via [`web/src/perf.ts`]'s `span()` helper in the sim-worker, wrapping the `world.write_snapshot_to(...)` call. The TS-side `frame` tree already handles non-Rust spans (e.g., `grass.upload.gpu`); this is the same pattern.
- **(acceptable) Keep Rust-side, rename to `worker.snapshot.write`** and document that it intentionally sits at root level. Update the profile panel's tree-walker to handle root-level worker spans.

Step A1's "inert wrapper" instruction (`v1.6-plan.md:209`) becomes moot under either option — delete it.

### C3. `cross_origin_isolated()` Rust export is unneeded ceremony

**Source:** `v1.6-plan.md:208` (Step A1 adds the export); `v1.6-plan.md:269-270` (Step B calls it from the worker).

`globalThis.crossOriginIsolated` is a JS-level property that already works on both `Window` and `WorkerGlobalScope`. Main reads it directly today ([`web/src/main.ts:94-95`](web/src/main.ts#L94-L95)). The sim worker can read it the same way: `(self as unknown as { crossOriginIsolated?: boolean }).crossOriginIsolated ?? false`.

Adding a Rust export requires a new dependency on `web-sys`'s `WorkerGlobalScope` feature, a wasm-bindgen export, and a rebuild — all to read a one-line JS global. Drop it.

This also removes the only WASM-API change in Step A1 that isn't strictly the stride bump. Worth doing.

### C4. Step A1 leaves the dev build runtime-broken; gate language is permissive

**Source:** `v1.6-plan.md:213` ("Acceptable to leave the dev build temporarily broken between Wave A landing and Wave B landing").

`pnpm typecheck && pnpm build` will pass A1 because [`web/src/render-gl.ts:330`](web/src/render-gl.ts#L330) is `if (stride !== 6) throw new Error(...)` — a runtime check, not a type error. Wave A1's gates therefore pass with the app's render path broken.

Two issues:
1. If anyone (orchestrator, user, future Claude) runs the dev server between A1 landing and B landing, the app will boot, hit the stride throw on the first highlight pass, and surface as a generic "creature_stride mismatch" error in the console.
2. The plan's "Common gates" claim acceptance via build success — A1 cannot be runtime-verified in isolation.

**Fix:** make A1 + B a single landed unit on `main`. Either (a) require Wave B reconciliation to immediately follow A1 with no intervening dev-server run, or (b) have A1 bump the renderer's stride guard to `if (stride !== 6 && stride !== 8)` — gives a one-commit transition window where both stride values are tolerated. (b) is the safer pattern for an external user who pulls main mid-wave.

### C5. Boot-handshake first-paint window is unspecified

**Source:** `v1.6-plan.md:277` (Step B: "Wait for `boot_ready`. Then `installRail()`, …").

Sequence:
1. Main spawns worker, posts `boot`.
2. Worker awaits wasm init, initThreadPool, constructs World, posts `boot_ready`.
3. Main receives `boot_ready`, installs UI, starts render loop.
4. Render loop reads "latest snapshot" — which has never been posted (Stage 1) or written (Stage 2).

In Stage 1, `latestSnapshot` is `undefined`; the renderer needs a guard or skip-frame. In Stage 2, the SAB stats header reads `pop=0`, `tick=0`, `world_ended=false` (zero-initialized) — the renderer paints an empty world for one frame. Acceptable but should be intentional.

**Fix:** have the worker run *one tick* and write *one snapshot* (Stage 1) or *one SAB write* (Stage 2) *before* posting `boot_ready`. Then main is guaranteed a valid first frame. Cost: one tick of latency at boot, imperceptible.

## Important issues (should address before shipping)

### I1. `Atomics.wait` timeout-type comment vs `sleepNs` dead variable

**Source:** `v1.6-plan.md:363-365`:
```
const sleepNs = Math.max(1, Math.floor(sleepMs * 1_000_000));   // ns floor for Atomics.wait
const before = Atomics.load(ctrl, CTRL_FUTEX);
Atomics.wait(ctrl, CTRL_FUTEX, before, sleepMs);  // timeout is ms
```

`sleepNs` is computed but never used; the comment claims "ns floor for Atomics.wait" but `Atomics.wait`'s timeout is in milliseconds. Probably leftover from a draft. The implementer will copy-paste it and wonder. Strike `sleepNs`.

### I2. `MAX_POP_FOR_SAB` cross-language sync mechanism is half-specified

**Source:** `v1.6-plan.md:207, 231`. Rust constant in `src/constants.rs`, TS constant in `web/src/sim-bridge.ts`. Plan §4 #2 says "Wave A2 runtime-asserts both consts agree" — but doesn't say how (the TS const can't import the Rust const at build time).

Two viable patterns:
- `boot_ready` carries `max_pop_for_sab: number` from Rust; main asserts it equals the TS const at handshake time.
- Both sides include the constant in their respective unit tests + a hand-eyeballed convention. Simpler, brittler.

Pick the first; mention it in either Step A1 or Step B.

### I3. `rail/index.ts::installRail(world)` is missing from the conflict map

**Source:** `v1.6-plan.md:91-110` conflict map. `rail/index.ts:48` is `export function installRail(_world: WorldHandle): RailState`; `pollRail(world)` calls `maybeSampleStats(world)` and `refreshInspector(world, rail)`. Both `world` params get replaced by `simBridge` and a `SnapshotHeader` in Step B.

Add `web/src/rail/index.ts` to the conflict map under Wave B with the structural signature change. Otherwise the implementer hits it mid-diff and has to invent.

### I4. `tps_q16` encoding wastes a clean opportunity

**Source:** `v1.6-plan.md:79, 204`. The plan packs `tps` as `(tps * 65536) as u32`.

`f32::to_bits(self.tps()) as u32` (Rust) + `new Float32Array(buf, off, 1)[0]` (TS) round-trips exact, no encoding decision to document, no precision math. Same 4 bytes. Recommend.

Same goes for `world_ended` as `u32 (0/1)` — fine, but the 4 bytes could carry both `world_ended` and a `paused` mirror as a bitfield. Minor; raise only if the stats block grows further.

### I5. `worker.terminate()` mid-`step_n` rayon-pool leak risk

**Source:** `v1.6-plan.md:417` (§4 #13: "Mission silent; no special handling needed").

The plan is right that `worker.terminate()` cascades to child workers. But rayon's `THREAD_POOL` is a global static inside `wasm-bindgen-rayon`. The terminated worker's `THREAD_POOL` *and* its rayon spawn-handles are dropped along with the JS heap when the worker is GC'd. That part is fine.

What's not fine: in some browsers (historically Firefox; less clear today) the parent's child-worker termination can race the WASM thread pool's join. If `worker.terminate()` hits mid-tick during a `step_n(batch)`, rayon's worker threads are forcibly terminated mid-spawn; the wasm-bindgen-rayon code path may emit a console error. Likely harmless; should be observed once during Wave E.

**Recommendation:** Wave E checklist (a) needs an explicit "restart 5 times in 5 seconds; expect no red console errors." That's the test that surfaces the race if it exists.

### I6. Step B's slider message type loses ints vs floats

**Source:** Mission/plan: `set_slider` payload is `{name: string, value: number}`. But [`src/wasm_api.rs:568-575`](src/wasm_api.rs#L568) has u32 sliders (`grass_bites_per_block`, `digestion_cooldown`, `max_age`, `founder_count`, `curriculum_min_pop`, `curriculum_max_pop`) that get `value.max(0.0) as u32` round-tripped. Today main.ts does `world.set_<u32 slider>(value)` and the wasm-bindgen glue handles the conversion.

Post-decoupling, the message protocol's `number` becomes a JS f64 over the wire; the worker dispatches via `world.set_slider(name, value)` which goes through `try_set_slider`'s `value.max(0.0) as u32` — same path. So it works. But: the existing per-type setters (`set_max_age(u32)`, etc.) become unused. Plan should explicitly say the worker dispatches everything through the `set_slider(name: &str, value: f32)` name-dispatcher, and the per-type setters get deleted in Wave C alongside the buffer exports.

### I7. `installRestartButton` / restart-hotkey path through `boot` payload

**Source:** `v1.6-plan.md:278` (Step B restart description).

Restart needs to send the *current* slider values, not the persisted ones. `currentSliderState()` (mentioned in plan) lives in `devpanel.ts` and snapshots in-memory state. But: today's `reapplyDevSliders` reads from `getSettings()` (localStorage), not from in-memory slider widget state. Are they always equal? At steady state yes; mid-drag no. If the user is dragging a slider and hits `r`, the boot payload should carry the current dragged value, not the last-saved one.

Step B should say "`currentSliderState` reads in-memory widget state, not localStorage" — or document the chosen semantics.

### I8. `Stage 1's structured-clone of typed-array views may detach them`

**Source:** `v1.6-plan.md:274` ("`creatures: world.creatures_buffer()`, `grass: world.grass_buffer_u8()`, `ids: world.creature_ids_buffer()`").

Two of those (`creatures_buffer`, `creature_ids_buffer`) return `js_sys::Float32Array::view(&self.buf)` — views over wasm linear memory. The third (`grass_buffer_u8`) returns `Uint8Array::from(&self.grass_buf_u8[..])` — a heap-allocated copy.

`postMessage`'ing a typed-array view does a structured clone (cloned by data; the destination gets a fresh `ArrayBuffer`). Fine, but: the next tick's `step_n` mutates the wasm-side `creature_buf`, which the *view* aliases. If postMessage's clone is lazy / asynchronous on the destination side, the data could be already-mutated by the time main receives it.

In practice Chrome and Firefox both eagerly serialize at `postMessage` call time, so this is safe. Worth one line in Step B noting "snapshot view is cloned eagerly at postMessage; safe to mutate wasm memory immediately after."

### I9. Plan §4 #10 ("orchestrator may skip Stage 1 acceptance") undermines staged landing

**Source:** `v1.6-plan.md:414`.

"If during Wave B's acceptance the user reports unacceptable behavior at pop > 4000, orchestrator may decide to skip Stage 1 acceptance gates and proceed straight to Wave C."

This breaks the staging guarantee. If Wave B lands on `main` and Wave C is then bundled in to mask Wave B's regression, the bisect surface for "when did sim worker decoupling break X?" is now two waves wide. Better:

- Cap Stage 1 acceptance at pop ≤ 1500 (matches mission success criterion #1). Above 1500, the plan documents "Stage 2 closes this gap."
- Don't permit landing Wave B on main if pop=1500 isn't usable. Either fix Stage 1 or fast-forward to Wave C *on a single branch* and land C as the unit-of-merge.

### I10. `stats_sample` deletion is implicit

**Source:** `v1.6-plan.md:320` (Step C deletes `creatures_buffer`, `grass_buffer_u8`, `creature_ids_buffer`, `pack_render_buffer`, `creature_stride()`, `grass_buffer`).

`WorldHandle::stats_sample` ([`src/wasm_api.rs:729`](src/wasm_api.rs#L729)) is still listed in the delete-set neither in Wave B nor in Wave C. Wave B's `rail/stats.ts` change makes it dead. Wave C should explicitly list it. Same with the per-typed slider setters (I6).

## Lesser issues + polish

- **Step D `Atomics.add(controlI32, CTRL_FUTEX, 1)` eventually wraps at u32 max** (`v1.6-plan.md:373`). At 1 add per slider event, this is ~4 billion sliders; not a practical concern. Worth a one-line comment ("wraparound is harmless; futex value is opaque").
- **`paused` while still writing snapshots** (`v1.6-plan.md:416`). Mentioned. Fine. But: paused worker spinning at 60 Hz snapshot rate burns wasm-bindgen overhead for nothing. Consider `Atomics.wait(ctrl, CTRL_FUTEX, before, /*forever*/ Infinity)` when paused, woken by `set_paused(false)` notify. Saves idle CPU.
- **Restart blip budget 500 ms** is on the optimistic side. Initial `init()` + `initThreadPool(N)` was ~200–400 ms in v1.5 telemetry; spawning the new worker, parsing wasm, registering thread pool, and writing the first snapshot is realistically 400–600 ms. Lock at 500 ms is a stretch goal, not a guarantee.
- **`web/src/perf.ts` says "unchanged topology" in the conflict map** (`v1.6-plan.md:106`). True at the architecture level; gains a new TS-side `frame.snapshot.read` span name in Wave C (`v1.6-plan.md:322`). Reflect in the map.
- **`tps_q16` ↔ snapshot stats block layout.** Plan §A2 specs `SNAPSHOT_HEADER_BYTES = 32` (5 × u32 stats + 12 B padding to 32-byte align). Why 32-byte align? Creature SoA stride is 32 bytes (8 f32), so each creature is 32B-aligned only if the SoA *starts* 32B-aligned. The padding choice is good; explain it in the plan's SAB layout block so an implementer doesn't trim the pad to "save 12 bytes."
- **`stats.ts::maybeSampleStats` 10-tick gating** (Step B description). Today's sampler runs every 10 sim-ticks. Post-decoupling, snapshots arrive once per *batch*, which at high TPS may skip many tick-mod-10 boundaries. Recommend `snapshot.tick - lastSampledTick >= 10` rather than `snapshot.tick % 10 === 0`. Otherwise sparse sampling at high TPS.
- **`request_id` overflow**. u32. At 750 ms cadence for `request_nn_stats` it overflows in ~100 years. Even if the inspector hits a 60Hz `inspect_id` flood it's 2+ years. Fine. Add a `>>> 0` mask to avoid signed-int surprises in TS arithmetic.
- **`SimBridge` class shape**. Plan says "Map<requestId, resolve>". Worth documenting: replies that arrive with no entry in the map (stale, late-by-multiple-frames) are silently dropped. Stale replies are common with rapid inspector clicks; without this the map leaks.
- **`web/src/widgets/perf-panel.ts` not in the file list in Wave A** (no change in A), but plan §I8 / I4 wants snapshot stats + 1-Hz polling. Wave B is the right place; conflict map agrees. Worth confirming in the prompt that perf-panel.ts is part of the Wave B blast radius.
- **Sim worker `console.log` lines via DevTools panel** (`v1.6-plan.md:288`). Chrome's "Threads" pane is under DevTools → Sources → Threads/Workers (not "Sources / Threads"). Firefox is `about:debugging` for workers in some versions. Worth one screenshot's worth of words in `docs/dev-server-prompt.md`.
- **`(window as unknown as { __world: WorldHandle }).__world = world`** ([`web/src/main.ts:128`](web/src/main.ts#L128)). Used by headless probes today. Post-decoupling, `__world` doesn't exist on main. Either expose `__simBridge` (some uses) or drop. Plan silent; recommend dropping and noting in commit body so anyone with a probe knows.
- **`set_target_tps` does not update the `world.tps` rolling window**. Today the rolling-TPS is automatically a function of step durations. Slider change ⇒ next batch reflects new pacing. Fine, but the rolling-average lags by ~60 ticks. Inspector readout shows "actual," not "target," which is the correct semantic. Mention nowhere; nothing to fix.

## Final word

This is a competent plan with one critical implementation-detail miss that would have killed Step D the moment a slider was dragged. The other issues are smaller — span placement, a dead Rust export, a renderer stride guard window, a boot-handshake first-paint — and each can be folded into the existing step prompts without disturbing the wave structure. The plan's bones (locked-decisions, message protocol, SAB layout, conflict map) are sound; the rework is at the leaves.

Single highest-leverage edit: **change Step D's pacing primitive to `Atomics.waitAsync` and add the `messageQueue` + `await` pattern.** Everything else is polish.
