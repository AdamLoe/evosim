# v2.0.1 — Off-thread snapshot writer (move `write_output_sab` off the tick thread)

Read-only design against `src/` + `web/` (HEAD `feat/v2.0.0`). No source edited by
this doc. Composes with `docs/plans/v2.0.1-grass-plan.md` (grass perf) and
`docs/plans/v2.0.1-recon-grass-perf.md` (recon). The grass plan lands FIRST; this
plan builds on what it provides (u16 internal grass, ping-pong buffers,
dirty-tile snapshot writes, u8 `grass_dim²` snapshot region UNCHANGED).

**Mandate (from the lead, committed):** move the per-tick snapshot production —
`write_snapshot` / `write_output_sab` (quantize grass + pack creature SoA + stats
header into a slot) — OFF the tick thread, so the tick loop hands off tick T's
finished world state and immediately starts tick T+1 while the snapshot for T is
produced concurrently. The write is read-only w.r.t. sim state, so determinism is
structurally unaffected; the entire problem is the read/write hazard and the
publish handshake.

## 0. Verified ground truth (against `src/` + `web/`, HEAD `feat/v2.0.0`)

**Control SAB layout — authoritative in `src/control_sab.rs`** (mirrored to
`web/src/generated/control-sab.ts` by `cargo run --bin gen-bindings`):
- `CTRL_CURRENT_SLOT = 0` — active snapshot slot index (0 or 1).
- `CTRL_SEQ = 1` — publication counter, bumped after each slot flip.
- `CTRL_FUTEX = 2` — the word the worker `Atomics.wait`s on (pause + pacing).
- i32 region is `CTRL_I32_REGION_LEN = 256` slots; there is **free space** between
  the species-table block (`...113`) and slot 256 — new control words can be added
  with NO byte-region shuffle, but adding one still regenerates `control-sab.ts`
  (a seam touch — see §4).

**Snapshot buffer — `src/wasm_api.rs`:**
- Lives inside `WorldHandle::snapshot_buf: Vec<u8>` in wasm linear memory
  (`wasm_api.rs:200`), exposed to main via `snapshot_buf_byte_offset()` /
  `snapshot_buf_byte_len()` over `wasm.memory.buffer`.
- **Exactly 2 slots:** `buf_bytes = 2 * slot_bytes` (`wasm_api.rs:174`); slot
  selected by `slot_idx = (slot as usize) & 1` (`wasm_api.rs:561`).
- `slot_bytes = HEADER(32) + CREATURE_SOA(MAX_POP*32) + grass_bytes(grass_dim²)`.
- `write_snapshot(slot)` (`wasm_api.rs:551-641`): packs creatures
  (`write_creatures_each_into`), writes the 20-byte stats header, then
  `quantize_grass_into(&self.inner.grass.density, grass_region)` — currently the
  full 3.69 M-cell f32→u8 scan.

**Worker control path — `web/src/sim-worker.ts`:**
- `simLoop()` (`:435-520`) is a tight **synchronous** loop: `readControlSab()` →
  (park if paused) → `world.step_n(1)` → `writeSnapshotToSAB()` → side reports →
  pacing `Atomics.wait(ctrlI32, CTRL_FUTEX, before, remainingMs)`.
- `writeSnapshotToSAB()` (`:421-431`): reads `CTRL_CURRENT_SLOT`, computes the
  `inactive` slot, calls `world.write_snapshot(inactive)`, then **store-before-add**
  publish: `Atomics.store(CTRL_CURRENT_SLOT, inactive)` then
  `Atomics.add(CTRL_SEQ, 1)`. This ordering is the existing torn-snapshot guard.
- Threads: `initThreadPool(workers)` from **wasm-bindgen-rayon**, called inside the
  worker during `handleBoot` (`:159-163`), only when `crossOriginIsolated`. The
  rayon worker pool shares the same `WebAssembly.Memory` (shared SAB). Rebuilds
  require `--features threads` or the pool collapses to 1 (see MEMORY).
- Boot handshake: worker runs one `step_n(1)` + `writeSnapshotToSAB()` BEFORE
  posting `boot_ready` (`:248-249`) so main's first RAF sees a live slot.

**Main reader — `web/src/main.ts`:**
- RAF `frame()` (`:310`) seq-gates: `seq = Atomics.load(controlI32, CTRL_SEQ)`; if
  `seq === lastPaintedSeq` it skips (paints only freshest, never the same snapshot
  twice). On a new seq it reads `CTRL_CURRENT_SLOT` and builds views at
  `slotOffset(layout, slot)`. **Main only ever wants the freshest snapshot.**
- `slotOffset(layout, slot: 0 | 1)` (`sim-bridge.ts:159`) — the slot type is
  literally `0 | 1`. A 3rd slot is a TS type + layout change (seam touch).

**Restart — `web/src/{main,sim-bridge}.ts`:**
- `restart()` → `oldBridge.terminate()` → `worker.terminate()` (`sim-bridge.ts:561`)
  → spawn a fresh `new Worker` with **new wasm memory** each time. Terminate is a
  hard kill of the worker thread; the rayon pool dies with it. Any new long-lived
  writer thread MUST also die on terminate (it does, if it lives inside the same
  worker's wasm/rayon runtime — see §1).

**Determinism invariant (must hold):** single-thread == rayon, bit-identical for a
fixed seed (the grass plan relies on this too). The snapshot write touches NO sim
state (it only reads `density` + creature SoA and writes `snapshot_buf`), so moving
it off-thread cannot change sim values — *provided* the writer's reads never race a
mutating tick (§2). This is the one thing to prove.

## 1. Mechanism — what is the writer?

Three candidates evaluated against how threads actually exist today (a single
wasm-bindgen-rayon pool inside the sim Web Worker, all sharing one shared
`WebAssembly.Memory`):

| Option | What it is | Feasibility here | Determinism | Lifecycle/terminate | Verdict |
|---|---|---|---|---|---|
| **A. rayon `spawn` background task** | `rayon::spawn(move || world.write_snapshot(slot))` from the tick thread each tick | Pool already exists; zero new boot wiring. BUT borrows: `write_snapshot(&mut self)` needs `&mut snapshot_buf` + `&grass.density`; a `'static` rayon task can't borrow `&mut self`. Requires splitting snapshot state out of `WorldHandle` into an `Arc`-shared struct with interior mutability, and `spawn` gives no back-pressure/handle to know when it finished (needed for publish). Re-dispatch churn per tick. | OK (read-only) | Dies with pool on terminate ✅ | **Rejected** — borrow/ownership fight + no completion signal + per-tick dispatch overhead. |
| **B. Dedicated long-lived Web Worker sharing wasm memory** | A second `Worker` that imports the same wasm module, attaches the shared `WebAssembly.Memory`, parks on its own futex | Memory is shareable (already round-trips via postMessage). BUT a second worker needs its **own** wasm instance over the **same** memory; wasm-bindgen-rayon's pool init + the `WorldHandle` Rust object (with its `Vec` pointers) is NOT trivially addressable from a second instance — the `snapshot_buf`/`density` are Rust heap objects reachable only through the owning instance's allocator view. Cross-instance pointer sharing is fragile and outside the patterns this codebase uses. Adds a second boot/terminate path. | OK | Needs explicit terminate wiring (2nd worker) ⚠️ | **Rejected for now** — highest blast radius, new seam-ish boot path, fragile cross-instance Rust object access. |
| **C. Persistent writer thread inside the existing rayon runtime, parked on its own futex** ✅ | One long-lived thread spawned at boot via the wasm-bindgen-rayon thread machinery (same shared memory, same allocator/instance as the tick thread). It owns the snapshot stage + quantize; sleeps on a dedicated futex word; tick thread wakes it after each tick handoff. | Lives in the same wasm instance → can hold an `Arc<SnapshotShared>` to the staged buffers + `snapshot_buf` with proper sync. Reuses the existing shared-memory + atomics fabric. One spawn at boot, parks (zero CPU) when idle. Completion signaled by a seq the tick thread/main can observe. | OK (read-only) | Dies when the worker is `terminate()`d (same runtime) ✅ | **RECOMMENDED.** |

**Recommendation: Option C — a single persistent writer thread, spawned at boot
inside the worker's wasm runtime, parked on a dedicated futex.** It matches the
existing concurrency fabric (shared memory + atomics + a rayon-spawned thread),
needs no second Web Worker boot/terminate path, dies correctly on
`worker.terminate()`, and gives a clean producer/consumer handshake with a
completion signal the publish step needs.

**Spawn detail.** Spawn it from Rust during `WorldHandle` construction (or a
dedicated `start_writer()` called once in `handleBoot` after `initThreadPool`),
using `std::thread::spawn` — under `--features threads` wasm-bindgen-rayon wires
`std::thread` onto Web Workers, so this lands as a real parked OS/web thread in
the pool's runtime. It must be created AFTER `initThreadPool` so the threading
runtime exists; if `crossOriginIsolated` is false (single-thread fallback), the
writer path must degrade to **inline** `write_snapshot` on the tick thread (no
writer thread) — same code, just called synchronously. Gate the whole thing behind
the same `--features threads` / `rayonCurrentNumThreads() > 1` condition.

## 2. The read/write hazard — the crux

The writer reads tick T's world state to produce snapshot T while the tick thread
mutates state for T+1. We must guarantee the writer's reads are never torn by a
concurrent mutation, with ZERO change to sim values.

### What the writer reads, and why each is safe

**(a) Grass density — exploit the grass plan's ping-pong.**
Post grass-plan, propagation reads `density`, writes `scratch`, then `mem::swap`
(per tick). After tick T completes, `density` holds the just-finished T field and
`scratch` holds T−1 (about to be overwritten as T+1's write target). The writer
wants to read the **T `density` buffer**. The hazard: tick T+1 reads that same
buffer (as its input) — reads don't conflict — but tick T+2's `mem::swap` would
make it the write target again, clobbering it while the writer is still reading.

> **Rule:** the writer reads the T `density` buffer; the tick thread must not let
> T+2's propagation write into that buffer until the writer has released it.

Because grass already ping-pongs, the cheapest safe design is a **3-buffer grass
rotation** (add ONE more `grass_dim²` u16 buffer, Rust-internal, no seam): at any
time one buffer is "T published-readable" (writer owns), one is "current"
(tick-thread input), one is "scratch" (tick-thread output). The tick thread only
ever swaps between the two it owns; it may not reclaim the writer-owned buffer
until the writer signals done. If the writer is still busy at T+2 swap time, the
tick thread **does not block** — it drops the older readable buffer's reservation
only when free, and the writer simply produced a now-stale snapshot for an earlier
T (drop semantics, §3). This keeps the tick loop non-blocking.

*Cheaper alternative if a 3rd grass buffer is unwanted:* the writer consumes only
the grass plan's **dirty-tile list** for tick T (the frontier is small), copying
just the changed tiles' u16 high-bytes out of `density` immediately at handoff,
into the writer's private stage, BEFORE returning control to the tick thread. That
"fast stage" is a small bounded copy (frontier-sized) the tick thread pays, after
which the writer works purely on its private stage and the tick thread is free to
swap. **This is the recommended primary mechanism for grass** (see "fast-stage"
below): it bounds the on-tick-thread cost to the dirty set, needs no 3rd grass
buffer, and removes the reservation/back-pressure entirely.

**(b) Creature SoA — fast-stage on the tick thread (recommended) vs double-buffer.**
Creatures are a small SoA mutated in place every tick; there is no ping-pong.
Options:
- *Double-buffer the creature SoA:* full second copy of the live creature arrays,
  swapped each tick. Cost: a full creature-array copy every tick on the tick
  thread, plus memory. Simpler isolation but pays the copy unconditionally.
- *Fast-stage (recommended):* at handoff the tick thread does a single bounded
  `copy_from_slice` of the raw creature SoA (positions/ids/genome-color inputs)
  into the writer's private stage, then returns. The writer does the expensive
  part off-thread: HSV→RGB color compute, species lookup, bit-packing into the
  32 B records (the actually-costly `write_creatures_each_into` work). The cheap
  memcpy stays on the tick thread; the CPU-heavy packing moves off it.

**Recommendation:** fast-stage BOTH (grass dirty-tiles + creature raw SoA) at
handoff. The tick thread's added cost is two bounded memcpys (frontier-sized grass
+ pop-sized raw SoA), after which writer and tick thread share NO mutable state —
the writer owns its private stage + the target `snapshot_buf` slot exclusively.
This makes the hazard analysis trivial (no shared mutable state during the
concurrent window) and keeps determinism obviously intact (sim reads/writes its
own buffers exactly as before; the stage copy is read-only w.r.t. sim).

### The handshake (atomics/futex/seq)

Add a small writer control block (in the control SAB free region, OR a private
`Arc<AtomicI32>` set — either works; SAB chosen so main/tests can observe state):

- `WRITER_REQ_SEQ` — bumped by the tick thread after it has fast-staged tick T and
  chosen the target slot. This is the "go" signal.
- `WRITER_DONE_SEQ` — bumped by the writer after it finishes packing the slot,
  immediately BEFORE it publishes (or it hands the publish to itself, see §3).
- `WRITER_FUTEX` — the writer parks on this with `Atomics.wait`; the tick thread
  `Atomics.notify`s after bumping `WRITER_REQ_SEQ`.

Per-tick sequence on the **tick thread**:
1. `step_n(1)` (mutates sim for T → state is now "T complete").
2. Fast-stage: memcpy grass dirty-tiles + creature raw SoA into the writer stage
   for the chosen target slot. (Bounded, on tick thread.)
3. `Atomics.store(WRITER_TARGET_SLOT, slot)`; `Atomics.add(WRITER_REQ_SEQ, 1)`;
   `Atomics.notify(WRITER_FUTEX)`.
4. Continue immediately to pacing / next tick. **Never blocks on the writer.**

On the **writer thread**:
1. Park: `Atomics.wait(WRITER_FUTEX, last_seen)`.
2. On wake, read `WRITER_REQ_SEQ`; if it advanced past `last_done`, coalesce to the
   **latest** request (skip intermediate ticks — §3), take `WRITER_TARGET_SLOT`.
3. Quantize + pack from the private stage into the target slot of `snapshot_buf`.
4. Publish (store-before-add): `Atomics.store(CTRL_CURRENT_SLOT, slot)` then
   `Atomics.add(CTRL_SEQ, 1)`; bump `WRITER_DONE_SEQ`. Loop to (1).

**Determinism statement (must hold and does):** every write the writer makes is to
`snapshot_buf` (an output buffer never read by the sim) and to control/seq words.
It reads only the frozen private stage. The sim's own state (`grass.density`,
`grass.scratch`, creature arrays) is read/written exclusively by the tick thread
exactly as it is today. Therefore **single-thread == rayon == writer-on/off is
bit-identical for sim state** — the writer is observationally pure w.r.t. the sim.
The only thing that changes is *when* a snapshot appears and possibly *which* ticks
get snapshotted (drop semantics), never any sim value. This is the property the
mandatory tests assert (§5).

## 3. Snapshot cadence + drop semantics

The renderer only wants the freshest complete snapshot (main already seq-gates and
refuses to paint the same snapshot twice). So:

- **Coalesce/skip, never block.** If the writer is mid-pack when the tick thread
  bumps `WRITER_REQ_SEQ` again, the tick thread does NOT wait. When the writer
  finishes its current slot, it reads the latest `WRITER_REQ_SEQ` and jumps
  straight to the newest staged tick, dropping the intermediate ones. The renderer
  loses nothing it wanted (it only paints freshest anyway).
- **Half-written slots are never published.** The publish (`CTRL_CURRENT_SLOT`
  store then `CTRL_SEQ` add) happens ONLY at the end of the writer's pack, on the
  writer thread, after the slot bytes are fully written — identical store-before-add
  ordering to today's `writeSnapshotToSAB`. Main reads `CTRL_SEQ` first then the
  slot, so it can only ever observe a fully-packed slot. **No change to main's
  read protocol.**
- **The fast-stage must be coalesce-safe.** Because the tick thread overwrites the
  writer stage each tick it stages, staging into a buffer the writer is still
  reading would tear. Fix: the stage is itself **double-buffered** (`stage[0]`,
  `stage[1]`), tick thread writes the one the writer is NOT reading, indicated by a
  `STAGE_IN_USE` atomic the writer sets while consuming and clears when done. If
  both stages are busy (writer slow), the tick thread skips staging this tick (the
  snapshot for this T is dropped) but the SIM STILL TICKS — drop is snapshot-only.

### Do we need a 3rd snapshot slot?

**Yes — recommended: go to 3 snapshot slots.** Reasoning, given concurrency:
- With the current 2 slots, main may be reading slot `current` (RAF can hold a view
  across its paint), while the writer needs a free slot to pack the next snapshot.
  The writer must not pack into the slot main is reading. With only 2 slots,
  "the slot main is reading" + "the slot the writer is packing" can collide the
  moment the writer overtakes — the classic single-spare-buffer stall.
- **3 slots** lets: main read slot A, writer pack slot B, and slot C be the
  last-published-but-not-yet-read freshest — so the writer always has a non-main,
  non-just-published slot to work in without blocking and without overwriting what
  main might still be reading. This is the standard triple-buffer for
  "producer never blocks, consumer always sees freshest complete."
- The fast-stage double-buffer (§ above, on the SIM-SIDE stage) is separate from
  the SNAPSHOT-SIDE slots; both are needed. (Stage = sim-input freeze; slots =
  packed-output the renderer reads.)

**Cost of the 3rd slot:** `buf_bytes = 3 * slot_bytes`, slot index `% 3` instead of
`& 1`, and the TS `slotOffset(layout, slot)` type widens `0|1` → `0|1|2`. This
**crosses the Rust↔TS seam** (see §4). It is the single largest seam item in this
plan. If the lead wants to avoid the seam churn, a viable fallback is **2 slots +
the writer never packs the slot whose index == `CTRL_CURRENT_SLOT`** (i.e. always
pack `inactive`, exactly as today) AND main copies-out the slot it reads at RAF
start so it never holds a long-lived view — but that adds a per-frame full-snapshot
copy on main (expensive: 3.69 MB). **Triple-buffer is the cleaner, recommended
choice; the 2-slot fallback trades seam churn for a main-thread copy.**

## 4. Worker control-path impact (and what crosses the seam)

**Inside the worker (`sim-worker.ts`), Rust-internal otherwise:**
- `simLoop()` changes from `step → write_snapshot(inactive) → publish` to
  `step → stage(slot) → notify writer → pace`. The publish (`CTRL_CURRENT_SLOT` /
  `CTRL_SEQ`) MOVES from `writeSnapshotToSAB()` (tick thread) to the writer thread.
  `writeSnapshotToSAB()` is gone in the threaded path (replaced by stage+notify);
  kept as the inline fallback for the single-thread case.
- The **boot first-paint handshake** (`sim-worker.ts:248-249`) must still produce a
  live slot before `boot_ready`. Either (a) run the boot snapshot **inline**
  (synchronously call the writer's pack once before starting the writer thread), or
  (b) start the writer, request tick-0's snapshot, and `Atomics.wait` on
  `WRITER_DONE_SEQ` once before posting `boot_ready`. Option (a) is simpler and
  avoids a boot-time deadlock window — recommend (a).
- **Pause path** (`:462-466`): when paused the tick thread parks on `CTRL_FUTEX`.
  The writer should also park (no requests arrive). No change needed beyond making
  sure a pause doesn't strand a request: stage+notify only happens after a real
  tick, so a paused worker never leaves a pending writer request.
- **Terminate/restart** (`sim-bridge.ts:561`): `worker.terminate()` hard-kills the
  worker and its rayon runtime, so the writer thread dies with it — no new teardown
  code needed, BUT the writer thread MUST NOT hold a lock or be mid-`Atomics.wait`
  in a way that blocks termination (it won't — `terminate()` is a hard kill, not a
  cooperative join). Confirm the writer never does blocking I/O. New worker on
  restart re-spawns a fresh writer at boot. ✅

**Crosses the Rust↔TS seam (must be coordinated as one wave):**
1. **The 3rd snapshot slot (§3):** `buf_bytes = 3*slot_bytes` and `% 3` in
   `wasm_api.rs`; `snapshot_buf_byte_len()` grows; TS `makeSlotLayout` /
   `slotOffset(layout, slot)` slot type `0|1` → `0|1|2`; main's
   `Atomics.load(CTRL_CURRENT_SLOT)` clamp (`main.ts:326` `rawSlot === 1 ? 1 : 0`)
   must accept 0|1|2. **This is the one wire-format change.**
2. **New control words** (`WRITER_REQ_SEQ`, `WRITER_DONE_SEQ`, `WRITER_FUTEX`,
   `WRITER_TARGET_SLOT`, `STAGE_IN_USE`) added to `src/control_sab.rs` in the free
   i32 region (below slot 256) → regenerate `web/src/generated/control-sab.ts` via
   `gen-bindings`. These are added below the existing fields so NO byte-region
   shuffle; still a generated-file regen (seam touch, low risk).
3. **`CTRL_SEQ`/`CTRL_CURRENT_SLOT` publisher identity changes** from "the worker's
   tick thread" to "the writer thread." The *protocol* (store-before-add, seq-gate)
   is unchanged, so main needs no logic change beyond the slot-clamp widening in
   (1). Flag this explicitly: the bytes main reads are identical; only the producer
   thread differs.

**Does NOT cross the seam:** the writer mechanism itself, the fast-stage buffers,
the grass triple-rotation (if used instead of dirty-tile staging), the creature
fast-stage — all Rust-internal. The grass snapshot region stays u8 `grass_dim²`
(grass plan invariant, preserved).

## 5. Risk + tests (Atomics/`waitAsync` regression class)

This is the lost-wakeup / torn-snapshot / deadlock family. Mandatory coverage:

**Correctness tests:**
- **Determinism: writer-on == writer-off, bit-identical sim state.** Run N ticks
  with the off-thread writer enabled and with it forced inline; assert
  `grass.density`, creature SoA, and all sim state are bit-identical for a fixed
  seed. (The whole safety claim — the writer must be observationally pure.)
- **Single-thread == rayon == writer-thread.** Extend the grass plan's
  single-thread==rayon determinism test to also run with the writer thread active;
  bit-identical density + creatures.
- **No torn snapshot.** A test/instrumented run where main reads a slot the instant
  `CTRL_SEQ` advances and validates the slot is internally consistent (header tick
  matches creature/grass content for that tick — embed the tick in the staged data
  and assert the published slot's header tick == its grass/creature tick). Run
  under load (writer deliberately slowed) to force overtaking.
- **Drop/coalesce correctness.** Slow the writer so it can't keep up; assert (a) the
  sim keeps ticking at full rate (drop is snapshot-only, sim never stalls), (b)
  every published `CTRL_SEQ` corresponds to a complete slot, (c) the published tick
  is monotonically non-decreasing and always the freshest the writer could reach.
- **Both/all snapshot slots valid after publish** (compose with grass plan's
  "both slots valid after dirty-only writes" test — now 3 slots): read each slot
  after a publish cycle; each published slot must equal a full reference snapshot of
  its tick.
- **Boot first-paint.** Assert a complete slot + valid `CTRL_SEQ` exists before
  `boot_ready` (no first-RAF-sees-empty-slot regression).
- **Restart teardown.** `restart()` mid-pack: assert no orphaned writer thread, no
  hang, fresh worker boots clean (the writer must die with `worker.terminate()`).

**Red-team focus (the bugs to hunt):**
- **Lost wakeup.** Tick thread bumps `WRITER_REQ_SEQ` and `notify`s in the window
  after the writer checked the seq but before it `Atomics.wait`s → writer sleeps
  forever holding the freshest request. Mitigation + test: writer must re-check
  `WRITER_REQ_SEQ` against `last_done` AFTER deciding to wait and pass that exact
  value to `Atomics.wait` (wait returns `not-equal` immediately if it already
  advanced). This is the canonical futex lost-wakeup pattern — test it by injecting
  a notify in that window.
- **Deadlock on stage back-pressure.** If both stages are `IN_USE` and the tick
  thread is designed to wait → deadlock if the writer is also waiting. Mitigation:
  the tick thread NEVER waits on the stage — it drops the snapshot for that tick.
  Test: hold both stages busy and assert the tick loop keeps advancing.
- **Torn grass via T+2 clobber.** If the dirty-tile fast-stage is skipped and the
  writer reads `density` directly, a T+2 `mem::swap` can clobber the buffer
  mid-read. Mitigation: use the fast-stage (private copy) OR the 3-buffer
  reservation; test the reservation path with a deliberately slow writer to force
  the T+2 swap to find the buffer reserved.
- **Publish/read race on the 3rd slot.** Writer packs the slot main is currently
  reading. Mitigation: triple-buffer invariant (writer never targets
  `CTRL_CURRENT_SLOT` nor the slot main last read). Test by overlapping a long main
  read with rapid writer cycles.
- **Single-thread fallback path** (no `crossOriginIsolated`): the writer must
  degrade to inline and still publish correctly — easy to forget. Test the inline
  path explicitly.

## Recommended landing order (sequenced RELATIVE TO the grass plan)

The grass plan and this plan BOTH edit `write_snapshot` + `simLoop`. To avoid
collision they implement as **one coordinated wave**, grass first:

1. **Grass plan §1–§3 land first** (separable kernel, active-tile frontier, u16
   internal + dirty-tile snapshot writes, u8 `grass_dim²` snapshot UNCHANGED). This
   gives the writer plan its enablers: the **dirty-tile list** (bounds the grass
   fast-stage), **u16 density** (snapshot becomes a high-byte copy — cheap to do
   off-thread or even partly inline), and ping-pong buffers. **Do NOT refactor
   `write_snapshot` twice** — the grass plan's dirty-tile snapshot rewrite and this
   plan's writer-thread move must be designed together so `quantize_grass_into`
   becomes "writer reads dirty-tile high-bytes from the stage" in one edit.
2. **Writer plan step 1: introduce the fast-stage + private snapshot pack on the
   tick thread, still synchronous (no writer thread yet).** This restructures
   `write_snapshot` into `stage()` + `pack(stage → slot)` without concurrency —
   pure refactor, behavior-identical, fully tested by the existing snapshot tests.
   Lands the seam-free plumbing.
3. **Writer plan step 2: add the 3rd snapshot slot (the one seam change) +
   `control_sab.rs` writer words + regen `control-sab.ts`.** Wire main's slot clamp
   to accept 0|1|2. Still synchronous publish from the tick thread. This isolates
   the wire-format change in one reviewable step with no concurrency risk yet.
4. **Writer plan step 3: spawn the persistent writer thread; move pack + publish
   off the tick thread; tick thread does stage+notify only.** Land all §5 tests
   here (determinism, lost-wakeup, drop, torn-snapshot, restart). This is the
