## Area 1 — Toroidal World Tiling on Zoom-Out

### How creature wrapping is done (current behavior)

**File:** `web/src/render-gl.ts` — function `renderWorldImpl`, lines ~1062–1192.

At the start of the body-pack loop, the frustum is computed in world-space:

```
minX = cam.cx - halfW;  maxX = cam.cx + halfW;
minY = cam.cy - halfH;  maxY = cam.cy + halfH;
```

If `wrap_world && W > 0`, offset arrays are built:

```
xOffsets = [0]  + optionally push(-W) if minX < 0, push(+W) if maxX > W
yOffsets = [0]  + optionally push(-W) if minY < 0, push(+W) if maxY > W
```

For each creature × each `(ox, oy)` combination, a ghost copy is packed into `instanceScratch` with position `(cx_raw + ox, cy_raw + oy)`. The GPU then receives all copies in a single `gl.drawArraysInstanced` call. No shader tiling: offsets are computed entirely on the CPU, injected as per-instance `a_center` attribute values.

**Number of tiles:** Up to 4 copies per creature (the 4 quadrant cases at corners) when the frustum straddles both axes simultaneously. Practically 1–3 copies in most pans.

**Uniforms:** The disc shader (`DISC_VS`) uses `u_cam_pos`, `u_zoom`, `u_viewport`; camera position feeds the screen-space projection. There is no tile-repeat uniform — tiling is purely instance-data driven.

### How grass and biome are rendered (current behavior)

**Grass:** `renderWorldImpl` lines ~945–974. One `gl.drawArrays(gl.TRIANGLE_STRIP, 0, 4)` over a static `[0,0, 1,0, 0,1, 1,1]` quad. `GRASS_VS` computes `world_pos = a_corner * u_world_size` and projects through `u_cam_pos` / `u_zoom`. The UV `v_uv = a_corner` maps `[0,1]` to the texture. Texture wrap mode: `gl.CLAMP_TO_EDGE` (set once in `initRenderer`, line ~695–696). **Single quad, no repeat.**

**Biome:** `renderWorldImpl` lines ~913–937. Same pattern as grass: one `gl.drawArrays(gl.TRIANGLE_STRIP, 0, 4)` over the identical `[0,1]` corner quad. `BIOME_VS` is structurally identical to `GRASS_VS`. Texture wrap: `gl.CLAMP_TO_EDGE` (line ~648–649). **Single quad, no repeat.**

### What must change to tile grass + biome like creatures

**Option A — extra draw calls (simplest, matches creature approach):**
- After the primary `drawArrays` for grass/biome, issue up to 3 additional draws with shifted `u_cam_pos` (effective camera position offset by ±W). This avoids any shader change.
- Alternatively, the vertex shader could accept a `u_tile_offset` uniform (vec2) and the caller issues 1–4 draws.

**Option B — texture repeat:**
- Change `TEXTURE_WRAP_S/T` from `CLAMP_TO_EDGE` to `REPEAT` and extend the `a_corner` quad geometry beyond `[0,1]` to cover the frustum in world units. Would require non-trivial UV math.

**Minimal change surface (Option A):** `render-gl.ts` only:
1. In `renderWorldImpl`, after grass and biome single-quad draws, compute the same `xOffsets`/`yOffsets` logic (already available at that scope from the creature block, but grass draws happen before it — must be computed early).
2. Loop over `(ox, oy)` pairs and issue one extra draw per non-zero offset with `u_cam_pos` temporarily set to `(cam.cx - ox, cam.cy - oy)` (or equivalently pass a tile-offset uniform).
3. No shader changes needed for Option A.

**Key uniforms involved:** `u_cam_pos`, `u_zoom`, `u_world_size` in both `GRASS_VS` and `BIOME_VS`. Both shaders share identical VS logic, so a single added `uniform vec2 u_tile_offset` would cover both.

## Area 2 — Pan/Zoom Disabled While Paused

### Finding

**The camera controls are NOT gated on `paused` at all.**

**File:** `web/src/camera.ts` — `attachCameraControls()`, lines 5–91.

The function attaches `pointerdown`, `pointerup`, `pointermove`, `wheel`, `touchstart`, `touchmove`, `touchend` directly to the canvas DOM element. There is no `paused` flag, no RAF check, no subscription to sim state. The handlers simply mutate `cam.cx`, `cam.cy`, and `cam.zoom` and call `clampCamera`.

**File:** `web/src/main.ts` — `attachCameraControls` is called once at line 185, before the frame loop. The `paused` variable (line 83) is never read inside `camera.ts`.

**File:** `web/src/main.ts` — `frame()` function (line 304). The RAF loop early-returns only when `!controlI32 || !snapshotBuffer || ...` (boot not yet complete), or when `seq === lastPaintedSeq` (no new snapshot). When paused, `seq` stops incrementing (the worker stops ticking), so `seq === lastPaintedSeq` will be true on every RAF after the first paused frame — **the render loop early-returns and `renderWorld` is never called while paused.**

**Root cause:** Camera mutations go through `cam.cx/cy/zoom` immediately on pointer events, but the frame callback that calls `renderWorld` returns early when `seq === lastPaintedSeq`. Since `seq` never advances while paused, **the canvas never repaints** even though the camera state has changed. Pan/zoom appears broken because the visual output is frozen, not because the input handlers are disconnected.

**Gating condition, exact location:** `main.ts` line 310–315:
```ts
if (seq === lastPaintedSeq) {
  requestAnimationFrame(frame);
  return;          // ← paused: seq frozen → always hits this early-return
}
```

**Fix:** Inside the early-return branch, detect if the camera moved since the last paint and call `renderWorld` with the last-known snapshot data (creatures/grass/biome are still valid SAB views). Or: track `lastPaintedCam` and re-paint on camera change even when `seq` hasn't advanced.

## Area 3 — Missing Top-Right Buttons

### Where the buttons are defined

**File:** `web/src/main.ts` — `installTopBarButtons()`, lines 579–638.

Four buttons are created programmatically and appended to `#top-bar`:
1. `playBtn` — `.topbar-btn`, id `playpause-btn`
2. `restartBtn` — `.topbar-btn`, id `restart-btn`
3. `autoBtn` — `.topbar-btn`, id `auto-restart-btn`
4. `perfBtn` — `.iconbtn`, id `perf-btn` (icon-only, SVG perf glyph)

All are appended via `bar.append(playBtn, restartBtn, autoBtn, perfBtn)` at line 630.

**File:** `web/index.html` — `#top-bar` is a static empty `<div id="top-bar">` at line 29. Buttons are injected by JS at runtime.

### CSS rules for #top-bar

**File:** `web/src/styles.css` lines 110–126:

```css
#top-bar {
  position: absolute;
  top: 8px;
  right: 8px;
  z-index: 5;
  display: flex;
  align-items: center;
  gap: 6px;
  padding: 0;
  background: transparent;
  font-size: 13px;
  pointer-events: none;   /* ← parent is pass-through */
}
#top-bar > * {
  pointer-events: auto;   /* ← children restore events */
}
```

`#top-bar` is `position: absolute` inside `#left-col` (which is `position: relative`, but `#canvas-wrap` is the stacking context sibling). The `z-index: 5` is only meaningful within a stacking context — `#left-col` does not establish one (no `position` other than static, no `transform`, etc.), so the `z-index: 5` on `#top-bar` competes with the z-indexed elements in `#canvas-wrap` (which itself is `position: relative`).

**Potential visibility issue:** `#top-bar` is absolutely positioned inside `#left-col`. `#left-col` is `display: grid` but does NOT have `position: relative` or `position: absolute` itself — it uses the default `position: static`. This means `#top-bar`'s `position: absolute` positions relative to the nearest positioned ancestor above `#left-col`, which is `#app-shell` (`position: fixed`). The `top: 8px; right: 8px` in that context positions the bar at the top-right of the entire fixed shell — which is correct and should be visible.

**However:** if the right rail is open (`#app-shell` NOT `.rail-collapsed`), the `grid-template-columns: 1fr var(--rail-w)` layout gives the left column `1fr` width, and `right: 8px` on `#top-bar` anchors to the right of `#app-shell` (the full viewport right), placing the buttons UNDER the right rail. The buttons are visually obscured by the rail overlay when the rail is open.

**Active-state styling:** The `.topbar-btn.is-active` and `.iconbtn.is-active` classes (styles.css lines 155–158, 254–258) set `color: var(--accent); border-color: var(--accent); background: color-mix(...)`. These are applied to `autoBtn` and `perfBtn` via `refreshHighlights()` / `refreshPlayLabel()`. The `playBtn` gets `.is-active` when paused (label changes to "Play" and button highlights). There is no missing active-state CSS — the rules exist.

**Most likely regression:** `#top-bar` is absolutely positioned relative to `#app-shell` (the `position: fixed` ancestor), with `right: 8px`. When `--rail-w` is non-zero (rail visible), the buttons are at the viewport's right edge, covered by the rail panel. They are visible only when the rail is collapsed. This is a layout conflict, not a CSS visibility bug per se. A secondary risk: if `#left-col` were given `position: relative` at some point, the anchor would shift to the left-column right edge, which would be the correct behavior.

## Area 4 — Zoomed-Out Creature LOD

### Shader files

All shaders are inlined as template-literal strings in `web/src/render-gl.ts`. There are no separate `.glsl`/`.vert`/`.frag` files.

The relevant programs:
- **Body + ring-flash + highlight rings:** `DISC_VS` / `DISC_FS` (lines 40–104)
- **Glow:** `HALO_VS` / `HALO_FS` (lines 117–180)

### Where the "outer ring" (action ring/flash) is drawn

The action ring-flash is NOT drawn in the vertex/fragment shader as part of the body pass. It is drawn as a **separate instanced draw call** using a second scratch buffer (`flashScratch`), packed in the body loop (lines ~1150–1172) and drawn after the body pass (lines ~1253–1262).

Each flash instance has `inner_px > 0` (line 1163: `inner = radiusPx + 2`, `outer = radiusPx + 5`). In `DISC_FS`, the annulus branch is selected when `v_radii_px.y > 0.0` (line 91–94): `if (r * outer < inner) discard; else flat-fill`. This renders a fixed 3px-wide annulus just outside the body, in the tag color.

The **persistent action ring** visible on the body surface (not the flash) is drawn inside `DISC_FS` by the body pass itself, lines 96–103:

```glsl
float ring_t = smoothstep(u_ring_inner - aa, u_ring_inner + aa, r)
             * (1.0 - smoothstep(u_ring_outer - aa, u_ring_outer + aa, r));
vec3 col = mix(body, u_ring_color.rgb, ring_t * u_ring_color.a);
```

Constants: `u_ring_inner = 0.96`, `u_ring_outer = 1.0` (set once at init, lines 530–531). This is a themed `--creature-ring` color (default black @ 0.6 alpha). The ring occupies the outer 4% of the body radius in normalized disc coordinates.

### Where body circle + species color + shading come from

**Species color** (per-creature display color) comes from the packed RGBA8 `u32` in lane 3 of the SAB snapshot. The main-thread unpacks it (`render-gl.ts` lines ~1107–1110):

```ts
const packedColor = idView[base + 3];
const cr = (packedColor & 0xff) / 255;
const cg = ((packedColor >>> 8) & 0xff) / 255;
const cb = ((packedColor >>> 16) & 0xff) / 255;
```

This maps to `a_color` (location 3) in the disc VAO. `DISC_FS` reads it as `v_color`.

**Body shading** (`DISC_FS` lines 96–103): the body branch (`v_radii_px.y == 0.0`) computes radial shading `shade = mix(1.15, 0.85, r)` — brighter at center, darker toward edge — then mixes in the action ring at `r ∈ [0.96, 1.0]`. No texture, no normal map.

**Screen-space size:**

```ts
const rawRadiusPx = radiusWorld * PX_PER_SIZE * cam.zoom;
```

where `PX_PER_SIZE = 2.5` (`render.ts` line 10). This means at zoom=1 a creature with `radiusWorld=1.0` renders as a 2.5 px disc. At `zoom=0.04` (minimum) that's 0.1 px.

### Current LOD mechanism

There is **one LOD threshold** today (lines ~1083–1102):

```ts
const POINT_THRESHOLD_PX = 1.0;
const isPoint = rawRadiusPx < POINT_THRESHOLD_PX;
const radiusPx = isPoint ? 1 : rawRadiusPx;
const innerPx = isPoint ? -1 : 0;   // -1 = flat-dot sentinel
```

When `innerPx == -1`, `DISC_FS` line 87–89 returns `v_color` immediately (no shading, no ring, no AA). This is the "survey zoom flat dot" path.

When `innerPx == 0` (normal body), the full shading + edge AA + body ring logic runs.

The flash annulus and halo are still emitted even for point creatures (no guard against `isPoint` in the flash or halo paths). The halo is gated on `pop <= 8000` (`render-gl.ts` line 1204).

### Controls for the desired LOD behavior

The desired behavior (drop ring at far zoom, show slim ring at near zoom) maps to:

| Zoom range | Desired | How to implement |
|---|---|---|
| Far (body < ~4 px) | Plain species-colored dot, no ring, no flash | Already handled by `isPoint` (flat dot at < 1 px). Extend threshold to ~4 px. |
| Mid (4–12 px) | Slim body ring only, no flash | Skip flash emit when `rawRadiusPx < MID_THRESHOLD`. Reduce `u_ring_inner`/`u_ring_outer` coverage or scale them with zoom. |
| Near (≥ 12 px) | Full body + action ring as slim outer annulus | Current behavior. Make flash annulus thinner (e.g., 1–2 px instead of 3). |

**Exact change surface in `render-gl.ts`:**
1. **Raise point threshold** or add a new "small body" LOD level (e.g., `SMALL_THRESHOLD_PX = 4`) — in the body-pack loop (~line 1083). At `< 4 px`, still draw a disc but omit the flash annulus and halo.
2. **Skip flash emit** when `rawRadiusPx < threshold` — in the flash-packing block (~line 1150). Single `if` guard.
3. **Scale ring constants** — `u_ring_inner`/`u_ring_outer` are set ONCE at init (line 530–531) as constants. To make the ring zoom-adaptive, move them to per-frame `gl.uniform1f` calls in `renderWorldImpl`, driven by `cam.zoom` or `rawRadiusPx`. The FS already uses `fwidth(r)` for AA so the math is correct at any zoom.
4. **No shader source changes needed** for items 1–3; they are uniform/instance-data changes only.
5. If a "slim ring only" LOD (no shading) is wanted at mid zoom, add an `innerPx` value between -1 and 0 or a separate ring-only sentinel. That would require a small DISC_FS change.
