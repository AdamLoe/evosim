# Mission: Profiler Overhaul (v1.7)

## Goal

Refactor the profiler's instrumentation, data model, and display so every measured row carries its own real timer (no rollups), every row name uses a full dotted prefix, the four conceptual trees (frame, tick, nn, grass_step) are surfaced as siblings instead of all jammed under `tick`, and the difference between *wall-clock as observed from the main sim worker* and *sum-of-busy across rayon workers* is structurally explicit.

## Current issues

1. Several rows show `0.00 ms` even though their children show time — `nn`, `nn.build_input`, `nn.proximity`, and the `grass_step` compute-style parents are the worst offenders. Parents currently exist as display-tree shells inferred from dotted-name prefixes, not as real spans.
2. Naming is inconsistent — some leaves use a full dotted prefix (`tick.nn.forward.l1`), some don't (raw `forward_us` in stats). Want every measured row to use the full dotted prefix that matches its placement in the tree.
3. Frame profiling is incomplete — `frame.snapshot.read` exists, but the broader render path (creatures pass, grass pass, the outer RAF callback itself) is uninstrumented.
4. Multithreaded work (NN forward, grass propagation) is mixed into the normal tick tree, which hides the difference between *main sim worker wall-clock wait* and *summed worker CPU*. At pop > 1500 the NN phase wall-time on the sim worker is tens of ms but the sum-across-workers is hundreds — both numbers matter, and the current display only really tells you one.

## Target profiler structure

Four sibling trees, displayed in this order. Every node listed below is a real measurement (its own clock-now timer pair), not a sum-of-children rollup.

```
frame                                ← outer RAF callback wall-clock
  frame.snapshot.read                ← Atomics.load(CURRENT_SLOT) + view construction
  frame.render_world                 ← gl draw calls + uniforms
    frame.render_world.grass
    frame.render_world.creatures

tick                                 ← main sim worker per-tick wall-clock
  tick.grid.rebuild
  tick.nn                            ← LEAF: wall-clock wait for the rayon dispatch
  tick.movement
  tick.graze
  tick.eat_scavenge
  tick.grass_step                    ← LEAF: wall-clock wait for the rayon dispatch
  tick.energy_bookkeeping
  tick.collect_deaths
  tick.handle_births
  tick.bookkeeping_tail
  tick.color_ema

nn                                   ← sum-busy across all rayon workers, per tick
  nn.build_input                     ← parent has its own per-worker accumulator
    nn.build_input.other
  nn.proximity
    nn.proximity.creatures
    nn.proximity.grass
  nn.forward
    nn.forward.l1
    nn.forward.l2
    nn.forward.l3

grass_step                           ← sum-busy across all rayon workers, per tick
  grass_step.dispatch                ← wall-clock of the outer par_chunks / chunks_mut
                                       loop (whichever is active in this build)
  grass_step.row_compute             ← per-worker accumulator over the row_body closure
    grass_step.row_compute.body      ← just the inner cell math, excludes per-row setup
  grass_step.bitset_rebuild          ← bitset regen after the propagation pass
```

| `tick.nn.proximity.{creatures,grass}`     | `nn.proximity.{creatures,grass}`          | Same.                                            |
| `tick.nn.forward`                         | `nn.forward`                              | Same.                                            |
| `tick.nn.build_input.other`               | `nn.build_input.other`                    | Same.                                            |
| `tick.grass_step.compute.par_chunks`      | `grass_step.dispatch` (threaded build)    | par_chunks vs chunks_mut are mutually exclusive — same conceptual node, two impls. |
| `tick.grass_step.compute.chunks_mut`      | `grass_step.dispatch` (non-threaded build)| Same.                                            |
| `tick.grass_step.compute.row_body`        | `grass_step.row_compute`                  | Plain English: "the compute we do per row."      |
| `tick.grass_step.compute.row_body.self`   | `grass_step.row_compute.body`             | Plain English: "just the body of that closure."  |

### Renames the user must sign off on before implementation

The `grass_step` children above are the planner's proposal. If `dispatch` / `row_compute` / `row_compute.body` / `bitset_rebuild` don't match what you'd reach for, surface the alternative in the plan review.

## Important semantics

- `tick.nn` and `tick.grass_step` are **leaves** in the `tick` tree — they each carry one number, the main sim worker's wall-clock wait for the rayon dispatch to finish. They don't have children in the tick tree. The breakdown lives only under the sibling `nn` / `grass_step` trees, with sum-across-workers semantics.
- `nn.total_ms` and `grass_step.total_ms` may be *much larger* than `tick.nn.total_ms` and `tick.grass_step.total_ms` at any non-trivial pop. That's expected — the worker trees sum busy time across rayon workers (which run concurrently), so 8 workers each doing 5 ms of NN forward gives `nn.forward = 40 ms` even though the sim worker only waited 5 ms. **Both numbers matter and the panel must show them as separate trees so neither hides.**
- Parent rows are never computed from their children's rollups. Each parent has its own real timer pair that brackets the work the parent represents. Some parents will end up larger than the sum of their children (loop overhead, setup time, etc.) and that's the diagnostic value of doing it this way — you can *see* the overhead, which a rollup would hide.
- The `frame` tree's outer `frame` node is a real RAII wall-clock span around the whole RAF callback body — so the parent has its own value (not a rollup), and any unaccounted-for time inside the RAF becomes visible as `frame.total - sum(children)`.

## What changes (high-level)

- `src/profiler.rs`: extend the API so the four trees coexist as siblings. Currently `push_root()` only mints a `tick` root; need at least `push_root_named(name)` so the sim worker can mint a `tick` root each tick and the parallel NN / grass code can mint a `nn` / `grass_step` root each tick. Frame tree is TS-side (rendered on main, no Rust involvement).
- `src/world/nn.rs`: replace the `record_under_tick("nn.forward.l1", ...)` accumulator pattern with a parallel-tree approach. Either (a) atomic accumulator nodes get a `record_under_root(root_name, path, dur_us)` flavour, or (b) the per-worker spans bracket the parent operations too (not just leaves) so parents get their own real timer pairs. The mission rules out (a)-only because parent rows can't be rollups; the implementation may end up combining both — atomic accumulators for the leaf measurements, plus real per-worker spans for the parents.
- `src/world/mod.rs`: drop the `tick.grass_step.compute.*` `record_under_tick` calls and surface them under the top-level `grass_step` tree instead. `tick.grass_step` stays as the RAII wall-clock span only.
- `src/world/tick.rs`: the existing in-worker timing in `Brain::forward` and `pick_action_d` keeps the same `clock_now_us_threadsafe()` reads; only the destination tree changes.
- `src/grass.rs`: the existing `par_chunks_us` / `chunks_mut_us` / `row_body_us` / `row_body_self_us` atomic counters get re-routed to the `grass_step` top-level tree under the new names.
- `web/src/sim-worker.ts`: open the `worker.snapshot.write` span as today; nothing else worker-side changes for the profiler.
- `web/src/main.ts`: open the new `frame` outer RAII span at the top of RAF; thread it through to `renderWorld` so the inner spans nest correctly.
- `web/src/render-gl.ts`: open `frame.render_world` + child spans (`frame.render_world.grass`, `frame.render_world.creatures`) inside `renderWorld`. No new uniforms or draw-call changes; instrumentation only.
- `web/src/perf.ts`: extend the TS-side `span()` helper if needed so multiple roots can coexist (currently it assumes one root tree per push window). The four trees merge inside the perf panel for display.
- `web/src/widgets/perf-panel.ts`: the display rewrite — render four stacked tables (one per top-level tree), each with its own header and column layout. Stable ordering: tree by definition; rows within a tree by tree position. Drop any current "infer parent from dotted prefix" code; trust the data shape coming in.

## What does NOT change

- The profiler's on/off toggle (`profile_enable(bool)`) and its main-side checkbox stay as-is.
- The 1 Hz request/reply cadence for `profile_report_json` stays.
- The Rust-side `clock_now_us_threadsafe()` binding (the scope-agnostic `performance.now()` plumbed in v1.6) stays.
- The sim-worker / main-thread / SAB split from v1.6 stays. v1.7 is pure instrumentation + display.

## Display

Four tables, stacked vertically, in the order shown above. Each table has its own section header (`frame`, `tick`, `nn`, `grass_step`). Within each table:

- Columns: `path · total ms · calls · ms/call · share %`
- Rows: indented by dotted-prefix depth (one indent level per dot beyond the tree root).
- Sort: tree-position-stable (the implementation enforces insertion order; no alpha-sort, no by-time sort).
- Empty trees collapse — if `nn` is silent because the profiler just toggled on this frame, render the header + "(no samples yet)" placeholder, not an empty table.

## Non-goals (v1.8+)

- Flame-graph display. (Tables are fine for the foreseeable future.)
- Persisted profile sessions / JSON export.
- Per-tick histograms (current display is rolling-average over the 1 Hz reply window).
- Tracing-style span IDs / parent IDs across the wasm/JS boundary. (Today's tree-name convention is enough.)
- Cross-tab profile diff against a baseline.

## Success criteria

1. With the profiler on at default settings (pop ≈ 1500, TPS = 60), all 4 trees populate every reply window. No `0.00 ms` parent rows anywhere.
2. `nn.forward.total_ms / tick.nn.total_ms ≈ number_of_rayon_workers` (give or take dispatch overhead) — confirms the wall-clock-vs-sum-of-workers distinction is correct.
3. Every node in the four trees has the dotted prefix that matches its position. `grep -r 'record_under_tick\|profile_span!' src/` shows no orphaned legacy names.
4. The four tables render in stacked order in the perf panel; no row is mis-attributed to the wrong tree.
5. `frame.total_ms - sum(frame.*.total_ms)` is small but non-zero at default settings — confirms the outer frame span surfaces unaccounted-for RAF overhead instead of hiding it in a rollup.
