# perf-4 — Threads end-to-end (JS `initThreadPool` + parallel vision + dual golden)

**Status.** Plan ready for implementation. This is the **most complex**
perf piece. One commit, ~120 LOC across Rust + TS + CI + new golden
file. Default-build determinism is preserved (existing
`tests/golden_snapshot_t10000.txt` unchanged). A **new** threaded golden
file is bootstrapped once and pinned thereafter. Implementer: Sonnet.
Self-contained — every command needed for the golden bootstrap is in §7.

**Goal.** Three coordinated changes that together turn the dormant
`cfg(feature = "threads")` codepath on in the browser:

1. **Rust side.** Re-export `wasm_bindgen_rayon::init_thread_pool` so
   the JS glue exposes an `initThreadPool` function. Parallelize
   `VisionPass::run` over `N_CHUNKS = 8` disjoint creature ranges
   (matching the existing v6 §J pattern in `nn_forward_all_chunks`).
   The pre-existing threaded NN path already works; vision is the
   remaining sequential hot path.
2. **JS side.** `await initThreadPool(navigator.hardwareConcurrency)`
   **before** the first `WorldHandle` construction in
   `web/src/main.ts`, behind a `typeof SharedArrayBuffer !== 'undefined'`
   feature-detect.
3. **CI / build.** `wasm-pack build` (both `pnpm build` chain and
   `.github/workflows/ci.yml`) gains `--features threads` so the
   browser artifact has the threaded codepaths. A new CI step runs
   `cargo test --release --features threads --test acceptance` against
   the **new** `tests/golden_snapshot_t10000_threaded.txt`. The
   existing sequential acceptance test continues to run unconditionally
   against the **unchanged** `tests/golden_snapshot_t10000.txt`.

The threaded codepath **may or may not** produce a different post-tick
hash than the sequential codepath. Static inspection of
`src/world.rs:1117–1161` (sequential helpers) vs `351:371–403`
(threaded inlined block) shows the arithmetic is bit-identical (same
variable derivation, same loops, same formulas), and vision is RNG-free
(see §1 D4), so on a static read the two paths look equivalent.
However, parallel `f32` reduction order can differ across rayon chunks
(SIMD reductions or chunk-boundary instruction scheduling inside
`Brain::forward`), so the empirical answer is settled only by running
the bootstrap. The dual-golden file design accommodates **either**
outcome: if the bootstrapped threaded hash matches the sequential one,
the two golden files happen to contain the same value and we can
optionally collapse to one; if they differ, the dual-golden serves its
intended purpose. Either way, each codepath is deterministic against
itself.

## 1. Decisions (pinned)

**D1. Re-export site.** Add `pub use wasm_bindgen_rayon::init_thread_pool;`
to `src/lib.rs` behind `#[cfg(feature = "threads")]`. Single line.
`wasm-bindgen-rayon` is built so that re-exporting its `init_thread_pool`
function from a `#[wasm_bindgen]` crate causes the JS-side glue to emit
an `initThreadPool` export with the signature
`(numThreads: number) => Promise<void>`. No additional Rust wiring is
required (no manual `#[wasm_bindgen]` wrapper — the crate's macro does it).

**D2. JS init placement.** In `web/src/main.ts`, the `initThreadPool`
call goes **inside `main()` between `await init();` (line 124) and the
first construction of a `WorldHandle`** (lines 178 / 200). The
`fromJson` and `new WorldHandle(...)` paths both happen later in
`main()`; placing the init right after `await init()` covers both
branches. The SAB feature-detect wraps the call so SAB-less browsers
fall through to the (existing) single-threaded behavior — the wasm
artifact still has the threaded codepaths compiled in but rayon
silently runs work on the calling thread if `initThreadPool` is never
called (per wasm-bindgen-rayon docs).

**D3. Import statement.** `web/src/main.ts` line 1 currently reads:
```ts
import init, { WorldHandle, creature_stride } from "../wasm/evosim";
```
Becomes:
```ts
import init, { WorldHandle, creature_stride, initThreadPool } from "../wasm/evosim";
```
`initThreadPool` is the JS-side name auto-generated by wasm-bindgen
from the snake-case `init_thread_pool` Rust re-export (D1). The
`evosim.d.ts` file regenerates on every `wasm-pack build --features
threads` so the type is present after the first threaded build.

**D4. Vision is RNG-free → bit-identical parallel.** Confirmed by
reading `src/vision.rs` (lines 1–530): zero `SimRng` references, zero
`rng` parameters, no `rand` imports. Every read is from immutable
shared references (`&CreatureSoA`, `&[Carrion]`, `&SpatialGrid`,
`&Vec<Vec<u32>>`) and every write is to a disjoint
`&mut VisionBuf = &mut [f32; 120]` slot. Parallel `VisionPass::run`
produces **byte-identical** `out` arrays vs the sequential loop. No
sub-RNG plumbing is required for vision. This is the key simplification
that keeps the parallel-vision diff small.

**D5. Parallelization shape for `VisionPass::run`.** Mirror the
existing `nn_forward_all_chunks` pattern (`src/world.rs:351–424`):

- `#[cfg(feature = "threads")]` branch added inside `VisionPass::run`.
- Reuse `crate::world::chunk_ranges(n)` — see D6.
- Build the eight `(lo, hi)` ranges, then `ranges.par_iter()` and for
  each range run the existing `self.fill_one(i, &mut out[i])` over
  `lo..hi`. The challenge is `&mut out` cannot cross threads as a
  single mutable borrow — split `out` into 8 non-overlapping
  `&mut [VisionBuf]` sub-slices first via `split_at_mut` (cascaded) or
  `rayon::iter::IndexedParallelIterator::par_chunks_mut` directly.
- Preferred form: `out.par_chunks_mut(chunk_size)` where
  `chunk_size = n.div_ceil(N_CHUNKS)`. `par_chunks_mut` produces an
  `IndexedParallelIterator` whose `.enumerate()` gives the chunk index;
  the per-chunk closure computes `lo = chunk_idx * chunk_size`,
  `hi = (lo + sub.len()).min(n)`, and runs `fill_one(lo + k, &mut sub[k])`
  for `k in 0..sub.len()`. This is the canonical rayon disjoint-slice
  pattern, equivalent in determinism to the existing NN code (chunks
  iterate in `par_iter` order, all writes are disjoint).
- The `#[cfg(not(feature = "threads"))]` branch is the unchanged
  sequential `for i in 0..n { self.fill_one(i, &mut out[i]); }`.

**D6. `chunk_ranges` visibility.** Currently `fn chunk_ranges(n: usize)`
in `src/world.rs:1189` is module-private. `VisionPass::run` (in
`src/vision.rs`) cannot call it as-is. **The vision path does not need
`chunk_ranges` if it uses `par_chunks_mut`** (D5): `par_chunks_mut`
internally derives equivalent partitioning. To keep the v6 §J fixed
chunking guarantee explicit, the implementer passes
`chunk_size = n.div_ceil(N_CHUNKS).max(1)` so rayon yields **at most
`N_CHUNKS` chunks** in deterministic index order — identical
partitioning to `chunk_ranges`. Vision therefore does **not** require
exposing `chunk_ranges`. The existing NN call site (`nn_forward_all_chunks`)
keeps its current `ranges: [(usize, usize); N_CHUNKS]` API unchanged.
**No new public API on `world.rs`.**

**D7. Build behavior — `pnpm build` always includes `--features threads`.**
Decision pinned: the default `pnpm build` chain builds the threaded
wasm artifact. Rationale: the threaded codepath is a strict superset
of the sequential one (it includes the `cfg(not(feature="threads"))`
fallback branches inside `chunk_ranges` callers? — no, it picks one
branch at compile time; what matters is that the **single shipped
wasm**, when `initThreadPool` is never invoked, runs everything on the
calling thread via rayon's default — see wasm-bindgen-rayon docs).
Browsers without SAB don't call `initThreadPool` (D2 feature-detect),
so they get the same wall-clock behavior they have today — just with
the threaded code paths dormant inside the wasm. One artifact, one
runtime branch. No dual-build complexity.

Implementation: update both `.github/workflows/ci.yml` wasm-pack steps
(lines 30 and 45) to include `--features threads`, and update the
README/docs invocation. The `web/package.json` `build` script
(`tsc --noEmit && vite build`) does **not** invoke `wasm-pack` —
wasm-pack is run separately (CI runs it explicitly, and local dev
runs it manually per README). So `package.json` itself is **not
edited**. The implementer updates the README (lines 23–26) to reflect
the new local-dev invocation:
```bash
wasm-pack build --target web --out-dir web/wasm --release --features threads
```
(Or `--dev` for fast iteration — same `--features threads` flag.)

**Note on flag syntax.** Modern `wasm-pack` (≥ v0.10) accepts
`--features` natively as a top-level flag and forwards it to cargo
internally — no `--` separator is required. The bare form above is the
**correct and only** form used throughout this plan. Do **not** use
`wasm-pack build ... --release -- --features threads`; wasm-pack will
not forward positional args after `--` as cargo flags and will error
with "unexpected argument '--features' found".

**D8. Threaded golden bootstrap env var.** Pin
`EVOSIM_WRITE_GOLDEN_THREADED=1`. Symmetric naming with the existing
`EVOSIM_WRITE_GOLDEN=1` (acceptance.rs:57). Documented in §7 and in
the DECISIONS.md entry (§9).

### 2b. `src/vision.rs` — parallelize `VisionPass::run`

Today's body (lines 50–58) is a 5-line sequential loop. Replace with a
sequential-or-threaded fork. Suggested diff (paste-ready):

```rust
impl<'a> VisionPass<'a> {
    /// Populate `out[i]` for every creature with the post-grid-rebuild state.
    /// `out.len() >= creatures.len()` precondition.
    ///
    /// Sequential by default. Behind `cfg(feature = "threads")` the work is
    /// partitioned into at most `N_CHUNKS` disjoint creature ranges via
    /// rayon `par_chunks_mut` (mirrors the v6 §J chunking used by
    /// `nn_forward_all_chunks`). Vision is RNG-free and writes only to its
    /// own `out[i]`, so the parallel path is bit-identical to the sequential
    /// path (no sub-RNG plumbing required).
    pub fn run(&self, out: &mut [VisionBuf]) {
        let n = self.creatures.len();

        #[cfg(not(feature = "threads"))]
        {
            for i in 0..n {
                self.fill_one(i, &mut out[i]);
            }
        }

        #[cfg(feature = "threads")]
        {
            use rayon::prelude::*;
            // Fixed N_CHUNKS partitioning per v6 §J. div_ceil + max(1)
            // ensures rayon yields at most N_CHUNKS chunks even when
            // n < N_CHUNKS (the tail chunks just have len 0 / 1).
            let chunk_size = n.div_ceil(crate::constants::N_CHUNKS).max(1);
            out[..n]
                .par_chunks_mut(chunk_size)
                .enumerate()
                .for_each(|(chunk_idx, sub)| {
                    let lo = chunk_idx * chunk_size;
                    for k in 0..sub.len() {
                        self.fill_one(lo + k, &mut sub[k]);
                    }
                });
        }
    }
    // ... fill_one and raycast unchanged ...
}
```

**`use` additions.** No top-level `use` change needed — `rayon::prelude::*`
is imported inside the cfg block (matches the pattern in
`src/world.rs:353`). `N_CHUNKS` is already exported by
`crate::constants` (`src/constants.rs:144`).

**Why `par_chunks_mut` over an explicit `ranges` array.** Rayon's
`par_chunks_mut` is a built-in disjoint-slice parallel iterator — it
produces independent `&mut` sub-slices safely. Building a
`[(usize, usize); N_CHUNKS]` ranges array first (NN-style) and then
calling `.par_iter().for_each(...)` would require manually splitting
the `&mut [VisionBuf]` into 8 disjoint sub-slices anyway (cascaded
`split_at_mut` or unsafe pointer math). `par_chunks_mut` is the
idiomatic shortcut for the disjoint-write case and preserves chunk-index
determinism via `.enumerate()`. The NN path uses the manual ranges
form because it needs to **read** from `&self.creatures` while
**writing** to a flat `Vec<(f32, f32, Action)>` reduction; vision's
shape (read shared, write disjoint slice) is precisely what
`par_chunks_mut` is for.

### 2e. `tests/acceptance.rs` — new threaded test gated on `cfg(feature = "threads")`

```rust
/// Threaded acceptance test (perf-4 dual-golden protocol).
///
/// Runs the same 10k-tick scenario as `acceptance_t10000` but with the
/// `threads` feature active (parallel NN forward + parallel vision).
/// Asserts against a SEPARATE pinned golden file. Static inspection of
/// the threaded NN-forward block (src/world.rs:351–424) vs the
/// sequential helpers (src/world.rs:1117–1161) shows bit-identical
/// arithmetic, and vision is RNG-free, so the bootstrapped threaded
/// hash MAY equal the sequential one. If it differs, the source is
/// parallel f32 reduction order across chunks. Either outcome is
/// acceptable; each codepath is deterministic against itself.
///
/// Bootstrap:
///   EVOSIM_WRITE_GOLDEN_THREADED=1 cargo test --release \
///       --features threads --test acceptance acceptance_t10000_threaded
///
/// See docs/plans/perf-4-threads.md §7 for the full bootstrap recipe.
#[cfg(feature = "threads")]
#[test]
fn acceptance_t10000_threaded() {
    const GOLDEN_PATH_THREADED: &str = "tests/golden_snapshot_t10000_threaded.txt";

    let mut w = World::new(SEED);
    let started = Instant::now();
    for _ in 0..TICKS {
        if !w.tick_once() {
            break;
        }
    }
    let elapsed_ms = started.elapsed().as_millis();

    assert!(w.population() > 0, "(a) population must be > 0 at tick {TICKS}");
    assert!(w.live_species_count >= 2, "(b) live_species_count must be ≥ 2");
    assert!(
        elapsed_ms < PERF_BUDGET_MS,
        "(c) threaded sim took {elapsed_ms} ms; budget {PERF_BUDGET_MS} ms",
    );

    let hash = snapshot_hash(&w);

    if std::env::var("EVOSIM_WRITE_GOLDEN_THREADED").is_ok() {
        std::fs::write(GOLDEN_PATH_THREADED, format!("{hash:#018x}\n"))
            .expect("write threaded golden");
        eprintln!("wrote threaded golden snapshot: {hash:#018x}  (tick={})", w.tick);
        return;
    }

    let golden_str = std::fs::read_to_string(GOLDEN_PATH_THREADED).expect(
        "threaded golden file missing; bootstrap with: \
         EVOSIM_WRITE_GOLDEN_THREADED=1 cargo test --release \
         --features threads --test acceptance acceptance_t10000_threaded",
    );
    let golden_str = golden_str.trim();
    let golden: u64 = u64::from_str_radix(golden_str.trim_start_matches("0x"), 16)
        .expect("malformed threaded golden hash");

    assert_eq!(
        hash, golden,
        "(d) threaded snapshot hash mismatch: got {hash:#018x}, golden {golden:#018x}",
    );
}
```

## 3. Integration

**Wasm API surface.** Adds **one** new JS export: `initThreadPool`. It
is a function, not a struct method — does not conflict with
`WorldHandle`, `creature_stride`, or any existing export. Type:
`(numThreads: number) => Promise<void>`. Documented via wasm-bindgen's
auto-generated `.d.ts`.

**JS pollers / hot loops.** Untouched. `pollRail`, `frame`, profiler —
none care about threads.

**Save / hash exposure.** Zero. Threads do not change `SaveV1` (no new
fields) and do not change `snapshot_hash` inputs. The hash differs
between sequential and threaded codepaths **only** because the runtime
arithmetic order differs in the threaded NN-forward branch — exactly
the situation the dual-golden protocol exists to handle.

**Rayon native pool init.** On native (`cargo test --features threads`),
rayon **auto-initializes** its global thread pool on first use. No
explicit init in tests. This is confirmed by reading the existing
`nn_forward_all_chunks` threaded path (`src/world.rs:351–424`): no
`rayon::ThreadPoolBuilder` call appears anywhere in the codebase, and
the threaded path has been compiling+linking under `--features threads`
since v1.0 (Cargo.toml line 38). If native rayon init somehow fails
under cargo-test (extremely unlikely — rayon's been on this contract
since 1.0), the implementer adds a one-time `rayon::ThreadPoolBuilder::new()
.num_threads(8).build_global().unwrap();` at the top of
`acceptance_t10000_threaded` and updates this plan. **Default
expectation: no explicit init needed.**

**Vision call-site changes.** None. `World::run_vision_pass`
(`src/world.rs:1165`) builds the `VisionPass` and calls `pass.run(...)`
exactly as today. The threaded fork is encapsulated inside
`VisionPass::run`.

**`chunk_ranges` reuse.** Not reused for vision (per D6). The NN path's
existing `chunk_ranges(n)` call remains a module-private helper of
`world.rs`. **No `pub` upgrade.**

## 4. Save / hash / determinism

**Save.** No new persisted fields. `init_thread_pool` is a JS-side
runtime call with no Rust-side state. `VisionPass` continues to hold
only references — not serializable, never was.

**Snapshot hash.** Same inputs as today. The dual-golden file exists
in case **the order in which deterministic arithmetic happens** in the
threaded NN-forward path produces a different f32 reduction, not
because of new inputs to the hash. Static analysis suggests the two
paths' arithmetic is bit-identical; bootstrap resolves the question.

**Vision determinism proof (D4 confirmation).**
- `src/vision.rs` has **zero** `SimRng` references (verified by reading
  the full file — only `rng::SimRng` use is inside the `#[cfg(test)]`
  module at line 324 for test harness setup).
- `VisionPass::fill_one` reads from `&CreatureSoA`, `&[Carrion]`,
  `&SpatialGrid`, `&Vec<Vec<u32>>` — all immutable borrows.
- The only mutation is `*buf = [0.0; VISION_LEN]` and per-slot writes
  to `buf[slot..slot+5]` where `buf: &mut [f32; 120]` is the disjoint
  per-creature slot.
- `par_chunks_mut` gives each thread an exclusive `&mut [VisionBuf]`
  sub-slice; threads do not share any mutable state.
- Output is a function of `(i, &CreatureSoA, &[Carrion], &SpatialGrid,
  &cell_to_carrion)` — deterministic, position-independent, no
  reduction order to worry about.
- Therefore: `out[i]` for any creature `i` is bit-identical between
  sequential and parallel runs.

**Threaded NN-forward determinism.** Already proven by the existing
`nn_forward_all_chunks` design (per v6 §J and
`docs/research/perf-parallelism.md` §1): chunks iterate in fixed
`N_CHUNKS = 8` count, results assemble in chunk-index order via
`par_iter().flat_map().collect()`, no RNG draws inside the forward
pass. The pre-existing path is what makes the new threaded golden file
stable across runs.

## 6. Risks

**R1. wasm-bindgen-rayon re-export shape.** D1 pins the canonical
`pub use wasm_bindgen_rayon::init_thread_pool;` re-export pattern, which
is the documented contract for the crate (it ships a `#[wasm_bindgen]`
macro on `init_thread_pool`; re-exporting from a downstream
`#[wasm_bindgen]` crate causes the JS glue to emit the binding). If for
some reason `wasm-pack build --features threads` doesn't produce the
`initThreadPool` JS export, the implementer's fix is to wrap it
manually:

```rust
#[cfg(feature = "threads")]
#[wasm_bindgen]
pub async fn init_thread_pool(num_threads: usize) -> Result<(), JsValue> {
    wasm_bindgen_rayon::init_thread_pool(num_threads).await
}
```

This explicit wrapper makes the export unambiguous but should not be
needed.

**R2. SAB feature-detect false negatives.** Some browsers expose
`SharedArrayBuffer` as a global but lack COOP/COEP isolation, in which
case `initThreadPool` will reject. The `try/catch` around the call (D2)
catches this — the warning logs and the wasm runs sequentially. No
user-visible crash.

**R3. Sequential tests fail under `--features threads` — RESOLVED by
pinned Fix A.** Without mitigation, `cargo test --release --features
threads --test acceptance` would run **all four** tests including
`acceptance_t10000` (sequential golden), but if the threaded NN-forward
code path produces a different post-10k-tick hash the sequential test
will fail.

**Pinned decision: Fix A.** Gate the three default-build tests on
`#[cfg(not(feature = "threads"))]` so they only run in the sequential
build:

```rust
#[cfg(not(feature = "threads"))]
#[test]
fn acceptance_t10000() { ... }

#[cfg(not(feature = "threads"))]
#[test]
fn profile_does_not_change_hash() { ... }

#[cfg(not(feature = "threads"))]
#[test]
fn save_load_step_preserves_determinism() { ... }
```

Under `--features threads`, only `acceptance_t10000_threaded` runs. CI
runs both invocations (one without features, one with) so total
coverage is identical to today. This is a **hard instruction** — the
implementer must NOT defer this decision or pick an alternative. (Fix B
— a separate `tests/acceptance_threaded.rs` file — would also work but
adds a file for no benefit; Fix A wins on diff size.) See also §2e for
the cfg-gating of the `SaveV1` import that becomes unused under
`--features threads`.

**R4. Native rayon thread-pool init under `cargo test`.** Mitigated by
the auto-init contract documented under §3 "Rayon native pool init."
If `cargo test --features threads` panics with
`ThreadPoolBuildError` or similar, the implementer adds an explicit
`rayon::ThreadPoolBuilder::new().num_threads(N_CHUNKS).build_global()
.unwrap();` at the top of the threaded test (once, before any rayon
call). Not expected to be needed; the NN forward path has been
compiling under `--features threads` since v1.0 without any explicit
init code.

**R5. `chunk_ranges` divergence between vision and NN.** D6 documents
that vision uses `par_chunks_mut(chunk_size)` and NN uses an explicit
`[(usize, usize); N_CHUNKS]` array. Both produce the same partition for
the same `n` because both use `n.div_ceil(N_CHUNKS)` as the chunk
size. If a future refactor centralizes chunking, both call sites must
remain bit-identical (else vision and NN would partition creatures
differently in a single tick and the threaded golden would silently
drift). Document this invariant in the doc-comment on `chunk_ranges`
in `src/world.rs:1183` as part of this commit — add: "vision's
`par_chunks_mut(n.div_ceil(N_CHUNKS).max(1))` partition must match
this function's output for all n; do not change one without the other."

**R6. CI second-job rebuild cost.** Adding `--features threads` to
CI's wasm-pack build means a full rebuild from scratch (different cargo
feature set → different target dir). The Swatinem/rust-cache hits
should catch most of it, but expect a one-time ~3–5 min cache miss on
the first push after merge. Acceptable; CI cost is non-blocking.

**R7. wasm-pack flag syntax — RESOLVED.** Modern `wasm-pack` (≥ v0.10,
which is what CI installs via the `init.sh` installer) accepts
`--features` natively as a top-level flag and forwards it to cargo
internally. The correct form throughout this plan is:

```bash
wasm-pack build --target web --out-dir web/wasm --release --features threads
```

(no `--` separator). The separator form
`wasm-pack build ... --release -- --features threads` does **not**
work — wasm-pack errors with "unexpected argument '--features' found".
If the implementer encounters an ancient wasm-pack (< v0.10) that
doesn't support the flag, upgrade with
`curl https://rustwasm.github.io/wasm-pack/installer/init.sh -sSf | sh`
(same command CI uses).

**R8. `initThreadPool` re-export collides with `WorldHandle::new`
constructor.** No — `init_thread_pool` is a free function, not a
`#[wasm_bindgen]` constructor or method. JS imports it alongside
`WorldHandle` from the same module without name collision. Verified by
the import-list shape in `evosim.d.ts` (each `pub use` becomes a
separate top-level export).
