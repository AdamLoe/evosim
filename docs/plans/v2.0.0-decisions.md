# v2.0.0 — Decisions Log

Companion to [`v2.0.0-mission.md`](v2.0.0-mission.md). The mission says
*what we are building*; this doc says *why these choices and not the
alternatives*. Every entry was settled in conversation during plan
drafting and is not yet validated by implementation — treat as draft
rationale.

When v2.0 ships, fold the surviving entries into
[`../decisions/sim.md`](../decisions/sim.md),
[`../decisions/render.md`](../decisions/render.md), and
[`../decisions/cross-cutting.md`](../decisions/cross-cutting.md), then
delete this file.

Format mirrors the rest of `decisions/`: **Decision / Why / Applies to**,
with optional **Alternatives** and **Revisit when**.

## Direction

### Reintroduce a per-creature `Genome`

- **Decision:** Body traits become evolved per-creature floats again,
  reversing Milestone D3 which made every body trait a `const`.
- **Why:** The single-pool brain-only sim has been validated. Body
  evolution is the next axis the user wants to watch.
- **Applies to:** `src/creature.rs` (new SoA column), `src/world/tick.rs`
  (every use of `CREATURE_SIZE`, `MOVE_SPEED_MAX`, upkeep constants).
- **Revisit when:** body traits stop being interesting and the sim is
  bottlenecked on the per-creature memory cost.

### Two modes, one binary toggle

- **Decision:** A construction-time dev setting `species_mode = on|off`
  picks between (a) the current single-pool asexual sim and (b) the new
  species + sexual mating sim. The two never coexist in a single run.
- **Why:** Most v2.0 ideas can be expressed as "config or another
  setting." Emergent drift is the v1 thing worth preserving; faction
  storytelling is the v2 thing worth adding. A single hard switch keeps
  both readable.
- **Applies to:** boot payload, dev-panel construction-only section,
  every code path that branches on action semantics, NN input layout
  composition.
- **Alternatives:** parameterize finer (asexual + species, sexual + no
  species, etc.) — rejected as too many combinations to balance.

### Species mode requires mating mode

- **Decision:** Species cannot run with asexual `Split`. Turning species
  on implies turning mating on; turning species off implies asexual.
- **Why:** Without mating there's no mechanism for species to evolve
  independently — asexual lineages would each become their own line of
  drift, which is what the v1 sim already does without the species
  label.

### Cannibalism stays off (hard rule) — species mode only

- **Decision:** In species mode, `Attack` refuses same-species targets.
  Not learned, not evolved — a sim-side gate. In single-pool mode there
  are **no species**, so the term doesn't apply: `Attack` hits any
  creature, which is exactly the v1 predation mechanic (renamed `Eat`),
  unchanged. So "cannibalism off" is a v2.0-species rule, not a global
  v2.0 rule.
- **Why:** Short networks can drift into "eat anything moving" in a few
  generations. Real species evolve deep anti-cannibalism instincts over
  millennia; our networks aren't deep enough to encode that depth.
  Without a hard gate every species converges to cannibalism. Single-pool
  has no "same species" to protect, so it keeps the existing free-for-all
  predation (watch for predator-runaway now that genome `diet`/`body_size`
  scale attack — a balance item, not a new rule).
- **Applies to:** `tick::eat_or_attack` path under species mode.
- **Revisit when:** brains grow deep enough that anti-cannibalism could
  plausibly evolve and be retained against drift.

## Reproduction

### Mating: contact-radius, NN-initiated, first-found, cooldown-gated

- **Decision:** `Mate` is an NN action gated **entirely by the
  initiator** (a legal pick only when the initiator is off mating
  cooldown AND energy ≥ the mating cost; invalid picks fall through to
  Graze, like Split). On fire, the sim looks for a same-species creature
  within a small `mating_contact_radius` — essentially **touching** (on
  the order of summed body radii), *not* the 20u perception range. The
  **first** same-species creature found within contact wins; no
  nearest-scan (consistent with the "eat = first-valid, not closest"
  decision — the closest-scan was removed for perf). **All cost and
  cooldown fall on the initiator only:** it pays energy (same as
  `split_gift`) and enters the fixed-tick cooldown
  (`mating_cooldown_ticks`, default 200, slider-tunable). The partner
  pays nothing, needs no energy, and is **not** required to be off
  cooldown — it's purely a target.
- **Why:** Requiring contact (not perception-range) makes mating a
  deliberate, physical act and ties reproduction to staying clustered.
  The energy cost keeps it earned; the cooldown prevents tight
  repeat-mating loops. First-found avoids the full nearest-scan the eat
  path already abandoned. Putting cost/cooldown on the initiator *only*
  is a deliberate cold-start concession: requiring both parents to be
  ready-and-fed roughly squares the gating probability, which a clustered
  founder group with random brains rarely clears. One ready initiator
  touching any same-species partner is a much easier event to bootstrap
  from. (Watch item — many initiators can mate one partner in a single
  tick; add a guard if births spike. Tracked in
  [`v2-possible-next-steps.md`](v2-possible-next-steps.md).)
- **Consequence (intended):** a species that disperses past contact
  range stops reproducing and dies out. Selection favors lineages that
  learn to stay together — "stay together or die out" is the design,
  not a bug to fix.
- **Alternatives:** nearest-within-perception (rejected — reintroduces
  the removed closest-scan and makes mating-at-a-distance too easy);
  signal/response handshake (rejected — too much UX surface for v2.0);
  automatic-on-proximity (rejected — removes NN's agency over
  reproduction).

### Crossover mode is a construction-time setting

- **Decision:** Construction-time `crossover_mode` setting picks
  between two policies, applied identically to brain weights and
  genome traits, followed by mutation in both cases:
  - `average` — child slot = elementwise average (midpoint) of parents.
    Homogenizing; relies on geography (distance + biome penalty) to
    differentiate species faster than mating pulls them together.
  - `fifty_fifty` — child slot = 50/50 random pick per slot from
    the two parents. Preserves variance; the standard GA approach.
- **Why:** Both are interesting evolutionary mechanics worth
  researching. One construction switch is cheap; the user wants to
  observe both regimes side by side. Default flipped to `fifty_fifty`
  because it preserves variance and matches the dominant GA literature;
  `average` is available for research into homogenization-with-
  geography dynamics.
- **Tradeoffs:** Per-trait `average` converges species toward the
  founder centroid within 5–6 mating generations unless geography
  separates them. 50/50 pick keeps variance but produces less
  "smooth" trait fields.
- **Known hazard (brain weights) + how we keep it safe:** applying either
  policy to **brain weights** is the classic neuroevolution "competing
  conventions" failure — two trained nets sit in different basins, so
  per-weight blending (and especially `average`) can perform
  worse than either parent. The mitigation is **not** structural (we
  explored and rejected module-aware crossover and prototype-pull — both
  reduce to averaging or are unrealistic). Instead: keep the species in
  the **aligned regime** where per-weight crossover is just Mendelian
  allele-shuffling — **same-species-only mating** (already required),
  **small per-birth brain mutation**, and **frequent within-species
  mating** so recombination dominates drift. In that regime both modes are
  safe-to-mildly-helpful; crossover's real job here is narrative (species
  gene pools), not raw optimization. Full reasoning, the "what makes them
  smart" priority list, and the deferred bets (recurrence; generative
  encoding with dominant/recessive; mutation-only species mode) live in
  [`v2-possible-next-steps.md`](v2-possible-next-steps.md).
- **Revisit when:** playtest shows one mode is strictly dominant, brains
  demonstrably fail to evolve under mating, or we decide single-pool
  should be a mutation-only "get smart" lab (see the fork in next-steps).

### Child spawn = midpoint, no habitable-cell check

- **Decision:** Children spawn at the midpoint of parent positions, even
  if that cell is hostile (deep desert, deep water).
- **Why:** Simple. Hostile-cell spawn means most cross-biome mating
  attempts produce children that die quickly — that's natural selection,
  not a bug.

### Asexual `Split` unchanged in single-pool mode

- **Decision:** Single-pool mode keeps today's `Split` action exactly.
- **Why:** It's the v1 sim we've already evolved. No reason to disturb it.

## Species seeding & identity

### Construction sliders: `starting_species_count` × `_member_count` × `_member_variance`

- **Decision:** Three sliders control mating-mode founder seeding:
  - `starting_species_count` (default 10) — how many species anchors.
  - `starting_species_member_count` (default 10) — founders per species.
  - `starting_species_member_variance` (default 3.0) — spread of the
    non-canonical founders off the canonical first member. Mechanically:
    each extra founder is the canonical genome+brain run through **one
    normal per-birth bucket draw** (same `MutationPolicy` machinery as a
    real child), with that bucket's **rate *and* sigma both multiplied by
    `_member_variance`**. So 1.0 = founders drift exactly like a normal
    child of the canonical member; higher = wider spread. (A future
    refinement could split this into separate rate/sigma multipliers — see
    next-steps.)
- **Why:** Founders need enough internal variance for selection to act
  on, without diluting species identity at tick 0. Reusing the bucket
  machinery keeps founder spread on the same calibrated footing as
  ordinary mutation and keeps the RNG stream deterministic. Three
  orthogonal knobs let the user research each axis independently.
- **Tune note:** 3.0 multiplies an already-calibrated bucket, so it can
  be aggressive — drop it if species read as noise at tick 0.
- **UI gating:** Hidden when `species_mode = off`; in that mode the
  single-pool `founder_count` slider is visible instead. The dev panel
  reacts to the *staged* `species_mode` value, not the running sim's
  mode.
- **Applies to:** world init path; dev-panel construction-only section
  + show/hide logic.

### Founders are pre-adapted to their spawn biome (reversal)

- **Decision:** Anchor points are still placed at **random** across the
  world (no per-species "preferred biome" steering). But the canonical
  founder genome for each anchor is **rolled to suit the biome it landed
  in** — a water anchor seeds high `water_affinity`, a desert anchor high
  `heat_tolerance`, plains anything. Brains stay random.
- **Why:** This reverses the earlier "random founders, let the world
  filter them" stance. That stance is honest evolutionarily *once a
  population exists*, but at tick 0 there is no learned behavior to keep a
  maladapted clump alive long enough to evolve — a water-spawned clump of
  land genomes just dies, taking the whole species with it. Pre-adapting
  founders to where they spawn lets them survive the opening moves;
  selection then acts on drift and on whatever the random brains learn.
- **Alternatives:** random genomes filtered by the world (rejected — too
  brutal at gen 0, compounds the mating cold-start); per-species
  *preferred-biome anchor placement* (still rejected — that scripts the
  map layout; biasing only the genome, not the anchor position, keeps the
  map honest while keeping founders alive).
- **Revisit when:** founders survive comfortably and the gen-0 pre-adapt
  is masking rather than enabling interesting selection.

### Species color: 10 hand-spread saturated hues for v2.0

- **Decision:** Pick well-spaced saturated hues at world init. The
  snapshot carries only `species_id` per creature; the color comes from a
  **polled species→color table** (the same SAB-report mechanism as the
  per-species pop graph) that both the canvas and the Monitor chart read,
  so they never drift. Build the table to be **dynamic** — species added,
  removed, recolored at runtime — even though v2.0 seeds a fixed 10; that
  way V2.1 splits/merges need no protocol change. No split-aware "one
  color becomes two similar-but-distinct" *generator* yet.
- **Why:** Sending `species_id` + a shared table (rather than per-creature
  color bytes) keeps the snapshot lean and single-sources the palette.
  The dynamic shape is cheap now and saves a protocol break later. Splits
  don't exist in v2.0, so the split-aware generator ships with them in
  V2.1+. Chart-side hue reuse is acceptable because typical runs end with
  1–3 surviving species.

### Species names: low priority

- **Decision:** `Species-A..J` is fine for v2.0. Random-name generator
  is deferred.
- **Why:** Names aren't load-bearing for the experience yet; species
  color does the visual identity work.

### Species extinct = extinct (until splits land)

- **Decision:** When a species hits population 0, it stays gone. No
  respawn pod, no founder injection.
- **Why:** New species will arise from splits in V2.1+. In v2.0 the
  question "how do new species appear" has the simplest possible answer:
  they don't.

### Inspector shows species + species history only

- **Decision:** No per-creature parent / grandparent / ancestor chain.
  Inspector displays species ID, species color, and species history
  (parent species — empty in v2.0 since no splits, but plumbed).
- **Why:** Individual-ancestor lookup is cheap to add but expensive to
  display meaningfully (10-generation chain is unreadable). Species
  history is the storytelling primitive that actually matters once
  splits ship.

## World

### `world_size` is a runtime construction setting (default 8× linear)

- **Decision:** `world_size` is a **runtime** construction-time
  setting (not a compile-time constant), default 9600u per axis (8×
  linear / 64× area vs today's 1200u). `wrap_world` is a separate
  construction setting (default `on`). On ⇒ torus; off ⇒ walls clamp
  to `[0, world_size]` and the 4 wall-proximity NN inputs reappear.
- **Why:** The user wants worlds **editable across a wide range** from
  one binary: a tiny fast asexual "screensaver" (colors fighting
  colors, evolving quickly) up to a grand toroidal map of many species
  across biomes. 64× area at the existing pop ceiling (~8k soft, 32k
  hard) is the default sweet spot — ~50–500 creatures per visible
  biome region, the target density for watchable faction dynamics.
  Wrap-toggleable because both are interesting: torus removes the
  wall-camping pathology, walls give a "shore" feature the NN can hug.
- **Cost of runtime size:** grass-grid dims (`world_size / 5`) and
  therefore snapshot-SAB region sizes become **derived from settings
  at boot**, not from compile-time constants. The cross-language
  safety model shifts from "assert equal constant" (`MAX_POP_FOR_SIM`,
  `GRASS_CELL_COUNT`) to "assert worker-reported dims == TS-computed
  dims" before binding typed-array views. Accepted deliberately to
  keep worlds editable.
- **Applies to:** `world_size` (runtime, was the `WORLD_SIZE` const),
  derived grass dims + SAB sizing + boot handshake asserts,
  `SpatialGrid` (wrap-aware queries), every movement path (wrap-aware
  position update), proximity sectors (wrap-aware distance + starburst
  LUT), render frustum cull (wrap-aware visibility), camera min-zoom
  clamp, trails (split across seam), highlight ring.
- **Alternatives considered:** keep world size a constant for v2.0
  (rejected — the user explicitly wants editable worlds, even at the
  cost of runtime SAB sizing); 20× linear default (rejected — too
  sparse at current pop cap); fixed torus only (rejected — walls are
  an interesting evolutionary feature).

### World seed is a construction setting, random default

- **Decision:** A `world_seed` u32 construction slider drives **biome
  generation only**. Default is random per restart, but the user can
  **pin a specific value** to keep the same map across restarts (e.g. to
  isolate a construction-slider's effect). Same seed reproduces a
  byte-identical biome map across rebuilds **of the same build**
  (same-machine determinism — the same guarantee the sim already makes;
  no cross-platform byte-identity is promised or tested).
- **Two seeds, deliberately.** `world_seed` is **separate from the sim
  RNG seed**. The sim is fully deterministic, so a single master seed
  would make an entire run replay identically every time — which we do
  *not* want. Keeping them separate means a pinned `world_seed` fixes the
  *map* while the run still plays out differently each time (the sim seed
  stays independent / random per run). The Wave-1 reproducibility test
  therefore pins only the biome SAB, never the whole run.
- **Why:** Without seed reproducibility, no two maps can be compared and
  no test can pin biome layout. Random default keeps the fresh-page
  experience varied without forcing the user to think about seeds. The
  seed appears in the existing top-left status strip so it's visible
  without opening the dev panel; restart reuses the displayed seed unless
  the user explicitly rerolls.
- **Applies to:** world init path; biome generator; `world_seed` row
  in dev panel; status bar.

### Three biomes: plains, water, desert

- **Decision:** v2.0 ships with `{Plains, Water, Desert}`. Forest,
  swamp, tundra, mountain are deferred.
- **Why:** These three are the minimum that distinguish Grazer
  (plains), Swimmer (water), and Desert Runner (desert) — the three
  species archetypes that genuinely need separate body traits in v2.0.
  The other four biomes need traits we're not shipping
  (cold-tolerance, fertility, humidity) and would dilute the visible
  contrast.

### Static biome map, in its own boot-time SAB

- **Decision:** Biome map is generated once at world init from
  `world_seed`, written to a dedicated `biomeSab`
  SharedArrayBuffer before the worker posts `boot_ready`, and never
  changes during the run. Not in the snapshot SAB.
- **Why:** Dynamic biome shifts and human-editable maps are V2.1+.
  v2.0 doesn't need them to feel like a world. Static-once means the
  3.7 MB biome region doesn't need to be double-buffered into the
  snapshot SAB every tick, saving 7.4 MB of SAB allocation and a
  pointless per-snapshot copy.
- **Applies to:** boot handshake (`biome_sab` added to `boot_ready`
  reply), renderer (samples the biome texture once at boot or after
  worker swap), `shared-memory-and-protocol.md` (third SAB
  documented).

### Coarse 5u-cell grass + biome grid (1920² at default size)

- **Decision:** Replace the 1.25u-cell 960² grass grid with a coarse
  5u grid (`world_size / 5` cells per axis; 1920² at the default
  9600u) for both biome ID and grass density.
- **Why:** Scaling the 1.25u grid to 8× linear → 7680² cells ≈ 59 MB
  per slot. Too much. The coarse 5u grid keeps the existing
  grass-mechanic shape, gives both biome and density in one cell
  lookup, and uses ~3.7 MB per channel at the default size.
- **Consequence — grass *sense* must be retuned:** at 5u cells the
  current `GRASS_PROXIMITY_RANGE = 8u` only spans ~1–2 cells, far too
  few to populate the 8 directional grass sectors meaningfully. Raise
  `GRASS_PROXIMITY_RANGE` (and recompute `LUT_RADIUS`, today hardwired
  to the 1.25u cell) so the sector window stays directional. Required
  Wave 1 retune, not optional.
- **Alternatives considered:** individual grass entities (rejected for
  cost — every blade as a sprite is strictly more expensive at any
  density); sparse density (rejected for cache pathology).
- **Revisit when:** grass dynamics feel too coarse at 5u per cell.

### Dirty-rect grass upload

- **Decision:** The worker tracks which grass cells changed their
  **u8-quantized** value (not raw density), accumulating the dirty
  region across ticks against a `grass_dirty_epoch`. The renderer
  uploads the *union* of changes since its last upload via
  `texSubImage2D` over the accumulated bounding rectangle (or skips
  entirely if empty), records the epoch it consumed, and the worker
  resets accumulation past that epoch. Mipmap regen is skipped when
  the dirty rect is empty. Full-texture upload once on first frame
  after boot or worker swap.
- **Why:** Full-texture upload at the coarse grid + mipmap regen
  extrapolates well over the 16 ms budget. But two things make the
  naive "cells changed this tick" version wrong:
  - **Quantization:** logistic growth nudges *every* nonempty cell
    every tick, so a raw-density dirty set is ~the whole map and saves
    nothing. A cell only needs re-upload when its u8 value flips,
    which at default growth happens every few ticks — keeping the set
    sparse.
  - **Temporal coherence:** RAF is usually slower than the tick rate
    and the snapshot is double-buffered, so many ticks pass between
    GPU uploads. One tick's dirty set under-covers what the GPU is
    missing; the renderer needs the accumulated union since its last
    upload, hence the epoch handshake.
- **Applies to:** `web/src/render-gl.ts` (upload path + epoch ack),
  grass mechanic Rust-side (quantized-change accumulation + epoch),
  control/snapshot SAB (dirty AABB + `grass_dirty_epoch` transport).
- **Tradeoffs:** Adds accumulation + epoch bookkeeping to the grass
  step; expected cheaper than full upload, but requires measurement.
  Simplest correct fallback is full upload — measure before keeping
  the machinery.
- **Revisit when:** the accumulated dirty box routinely covers >50% of
  cells (full upload is then cheaper than tracking).

### Movement penalty, no impassable terrain

- **Decision:** Biomes impose a continuous per-tick movement-penalty
  scalar derived from `(biome, water_affinity, heat_tolerance)`. The
  scalar drives **three effects at once**, each dev-tunable: reduced
  effective move speed, extra per-tick energy upkeep, and a higher
  move-cost multiplier. Nothing blocks movement.
- **Per-biome base severity, water harshest.** Each biome has its own
  base penalty severity (live-tunable: `water_movement_penalty`,
  `desert_movement_penalty`; plains = 0). Water is much harsher than
  desert — a fish on land is far worse off than a rabbit in winter — so
  the severities are not symmetric and must be tunable.
- **Why:** Impassable terrain means collision + pathfinding, which is
  out of scope. A multi-effect, per-biome-weighted penalty is enough to
  make biomes meaningful selection pressure, and keeping the severities
  in dev settings lets the relative harshness be dialed in by playtest
  rather than guessed at compile time.

### Penalty is continuous but survivable

- **Decision:** Penalty applies every tick the creature is in the
  cell, but does not instantly kill — a Plains-adapted creature can
  dash through desert if it has energy.
- **Why:** Lets species do brief incursions / migrations through
  hostile biomes. Without this, the map becomes hard partitions.

## NN inputs / outputs / action set

### NN input layout is derived from construction settings

- **Decision:** The input vector composition is computed at world
  init from the active construction settings. There are no
  "vestigial" inputs preserved for compatibility — every slot earns
  its keep against the current settings. SIMD-pad the result to a
  multiple of 8. Old brains are discarded across any settings change
  (no save/load to migrate).
- **Why:** Inputs that are constant for the entire run of a brain
  collapse to a per-output bias term and waste weights. Settings-
  derived layout means we always train against an honest input
  surface for the current world.
- **Reality / scope (Wave 0):** Input width is **compile-time today** —
  `NN_INPUTS == 32` is hard-asserted in `src/brain.rs`,
  `Brain::forward` takes `&[f32; NN_INPUTS]`, and `build_nn_input`
  writes fixed slot indices. v1.12's `NnTopology` made *hidden layers*
  runtime but left inputs/outputs implicit. So this is a foundational
  refactor, not "plug settings into existing support": input width
  becomes a runtime field of the topology, the fixed input arrays
  become max-sized slices (a `MAX_NN_INPUTS = 48` ceiling — the widest
  case is `wrap off` + `species on` = 43 inputs, padding to 48; an
  earlier draft's 40 dropped the 4 directional biome inputs and was too
  small), and `build_nn_input` becomes a composable offset-computing
  layout.
- **Applies to:** `NN_INPUTS` / `MAX_NN_INPUTS`, `NnTopology`,
  `build_nn_input`, `Brain::founder` / `forward` / `weight_count`,
  `boot_ready` NN topology payload, brain/nn tests.
- **Code anchors:** `src/brain.rs` (the `NN_INPUTS == 32` assert + the
  fixed-array signatures), `src/world/nn.rs → build_nn_input`.

### Wall-proximity inputs only present when `wrap_world = off`

- **Decision:** The 4 wall-proximity slots appear in the NN input
  vector only when `wrap_world = false`. In wrap mode they are
  dropped entirely and the input width shrinks accordingly.
- **Why:** Settings-derived layout principle (above). In a wrapped
  world walls don't exist; carrying always-zero inputs would waste
  weights.

### Per-direction biome-penalty inputs (4 cardinal)

- **Decision:** 4 NN inputs sample biome-derived movement penalty
  one cell to N, S, E, W of the creature. The penalty is computed
  per-creature per-tick from the creature's genome (`water_affinity`,
  `heat_tolerance`) applied against the biome under each sampled
  cell.
- **Why:** A single current-cell `movement_penalty` scalar tells the
  creature what costs it *now*, not what's ahead. A plains-adapted
  creature heading toward a desert needs an antecedent signal to
  learn "stay away." Four cardinal directions is the smallest
  representation that gives directional terrain awareness without
  bloating the input vector.
- **Alternatives:** 8-direction biome sectors (rejected for v2.0 —
  doubles the input count for marginal additional signal);
  per-sector grass-input multiplier by biome penalty (rejected —
  conflates grass yield with terrain cost, harder to learn).
- **Revisit when:** playtest shows creatures fail to learn directional
  terrain avoidance from 4 inputs.

### Current-cell `movement_penalty` retained alongside directional inputs

- **Decision:** Both the 4 directional biome-penalty inputs and a
  single current-cell `movement_penalty` scalar are present.
- **Why:** The directional inputs are predictive; the current-cell
  scalar is the immediate "what does moving cost me right now"
  signal. Both are cheap; both encode different timesteps; the brain
  uses them differently.

### Bias slot (constant 1.0) retained

- **Decision:** Keep one input slot pinned to 1.0 as a classical NN
  bias slot. Distinct from any "action-set indicator" or
  "mode flag" inputs (which are dropped, see below).
- **Why:** A bias-learning constant gives every hidden unit a
  learnable threshold offset. Standard practice; cheap; pays for
  itself.

### Drop the action-set indicator slot

- **Decision:** The previous draft's "action-set indicator NN input
  slot" (reading "is this run in species mode?") is dropped.
- **Why:** It's constant across every decision a brain ever makes;
  it collapses to a per-output bias term and wastes weights. The
  portability argument doesn't hold either: a brain selected against
  one action[2] semantic doesn't suddenly do well in the other
  because of one constant signal. With settings-derived input
  layouts, mode-dependent inputs (16 vs 8 creature sectors) carry
  the mode information implicitly.

### Action set is `{Graze, Attack, Split | Mate}`

- **Decision:** Three actions. The third slot is `Split` in single-pool
  mode and `Mate` in species mode, chosen at construction time.
- **Why:** Today's action[2] is `Split`. Replacing the slot's meaning
  per mode keeps the SAB layout stable and the brain output shape
  unchanged.

### Eat renamed to Attack

- **Decision:** The `Eat` action is renamed to `Attack` in both modes.
  Single-pool: any neighbor (today's semantics). Species: other-species
  only.
- **Why:** "Attack" reads correctly once the species gate exists. In
  single-pool mode it's the same mechanic with a clearer verb.

### Movement output stays continuous (`vx, vy`) — discrete dropped

- **Decision:** No `movement_output` setting. Velocity output stays the
  current continuous `(vx, vy)`. A discrete N/S/E/W option was floated and
  cut.
- **Why:** The readability argument ("they all migrate east") didn't
  justify a new setting, a decode path, and the extra balance surface.
  Continuous is what the sim already does and is the only encoding v2.0
  ships.

### NN proximity inputs split into 16 sectors in species mode

- **Decision:** In species mode, replace the 8-sector unified creature
  proximity with two 8-sector blocks: nearest same-species per sector,
  nearest other-species per sector. In single-pool mode the unified
  8 sectors remain (no second block).
- **Why:** Creatures need to discriminate species at perception time to
  make sensible Mate / Attack decisions. Two parallel sectors is the
  smallest representation that does it. Density-per-sector (a second 16
  inputs) is deferred — ship the simpler version first. In single-pool
  mode the discrimination doesn't exist, so the extra 8 slots aren't
  carried.
- **Note on the proximity early-bail:** the starburst scan's
  "all sectors lit ⇒ bail" optimization (`decisions/sim.md`) now lights
  16 sectors instead of 8, and a mono-species clump never lights the
  other-species block. Judged acceptable: at the coarse `HASH_CELL`
  (~5u) the starburst visits far fewer cells than today, and the new
  density is ~64× sparser, so a full-range walk is cheap. If profiling
  later disagrees, bail the two blocks independently or cap the
  other-species scan range.

## Body traits (the 6-trait genome)

### Six traits: body_size, max_speed, metabolism, diet, water_affinity, heat_tolerance

- **Decision:** Per-creature `Genome` carries six continuous floats in
  `[0, 1]`. Rescaled at use site.
- **Why:** This is the minimum trait set that distinguishes the
  Grazer / Hunter / Swimmer / Desert species archetypes against the
  3-biome world. Each trait does real work in at least one mechanic.
- **Alternatives:** the 12+ trait set in the original ChatGPT plan
  (rejected — too many for v2.0; many traits had no mechanic to
  express them in).
- **Revisit when:** new biomes ship and need new trait axes (forest →
  social/fear, tundra → cold-tolerance, etc.).

### Dropped traits: social, fear, aggression, cold, humidity, fertility, photosynthesis

- **Decision:** Not in v2.0.
- **Why:** Either there's no biome to express them in (cold, humidity),
  or they duplicate work done by `diet` + `metabolism` (aggression,
  social), or they introduce a new energy channel that destabilizes
  balance (photosynthesis).

### Traits as continuous floats, not quantized buckets

- **Decision:** `body_size: f32 ∈ [0, 1]`, not `body_size: u8 ∈ {0..4}`.
- **Why:** Floats are honest about drift. Buckets read more cleanly to
  the eye but they hide the very thing the sim is supposed to expose —
  small differences accumulating over generations.

### Trait mutation sigma = chosen-bucket sigma × 0.3

- **Decision:** Body traits mutate off the **same per-birth bucket
  draw** as the brain (one bucket sampled per child from
  `MutationPolicy`), but the trait step uses that bucket's `sigma`
  scaled by `trait_mutation_sigma_multiplier` (default 0.3). Same
  bucket, scaled sigma — not an independent draw. (There is no single
  "brain_sigma"; mutation is 8 buckets each with their own sigma, so
  the multiplier applies to whichever bucket the birth drew.)
- **Why:** Phenotype should drift slower than brain. Brain weights are
  what the creature chooses with; body traits are what the world
  selects on. Sharing the bucket draw keeps a child's brain and body
  mutation correlated and keeps the RNG stream order deterministic and
  easy to reason about.

### body_size scales sprite + repulsion, not collision

- **Decision:** Larger creatures look larger and push others away more
  forcefully. No collision (matches today's no-collision model).
- **Why:** Collision adds physics complexity that's out of scope.
  Repulsion approximates "big creatures own more space."

## Render & UI

### Snapshot SoA carries render-only fields, packed compactly

- **Decision:** The per-creature genome lives in `CreatureSoA`
  sim-side and **does not ride the snapshot SAB**. The snapshot carries
  only what the renderer reads: position, body size (radius),
  single-pool display color, stable id, the action ring-flash state, and
  (mating mode) `species_id`. Prefer compact binary encodings over
  per-channel f32s — single-pool color as one u32 RGBA8 lane, ring-flash
  + `species_id` bit-packed.
- **The stride does not grow — it stays 32 B / 8 lanes.** Today's 8 lanes
  are `x, y, radius, color_r, color_g, color_b, id_lo, id_hi`. The packed
  v2.0 set is `x, y, radius, color_u32, id_lo, id_hi, packed_u32` = 7
  lanes, padded back to 8. So `CREATURE_STRIDE = 8` and the creature SAB
  region size are unchanged; only the **grass + biome** regions become
  settings-derived. The renderer's id/color offsets shift within the
  stride and need a decode update, but the `CREATURE_STRIDE` guard value
  is untouched.
- **Why:** The snapshot is a render feed, not a state dump. The
  inspector already reads full genome via the separate
  `creature_inspect_json` path, so traits never need to cross in the
  hot per-tick SoA. Packing keeps the stride bump small, which keeps
  both the per-tick snapshot write and the per-flip interpolation Map
  rebuild cheap. An earlier draft feared a 32 B → 64 B stride doubling
  from putting genome in the snapshot; render-only + packed avoids it.
- **Applies to:** `WorldHandle::write_snapshot_to`, the snapshot SoA
  byte layout (`shared-memory-and-protocol.md`), renderer instance
  pack + id/ring decode (`web/src/render-gl.ts`), the
  `CREATURE_STRIDE` guard.
- **Tradeoffs:** Packed encodings are less human-readable in a memory
  dump; the decode lives in the renderer. Worth it for bandwidth.

### Action-EMA color deleted

- **Decision:** Remove the per-creature R/G/B EMA color tracking
  (today's `color_r/g/b` SoA columns).
- **Why:** Body color in v2.0 is owned by species identity (species
  mode) or genome (single-pool). Action information moves to the ring
  flash.

### Body color = species color (mating) or genome-derived hue (single-pool)

- **Decision:** In species mode every creature paints with its
  species's color. In single-pool mode color is derived from genome
  (proposal: hue from `diet`, saturation from `body_size`, value from
  `max_speed` — implementation can refine).
- **Why:** Species need readable identity. Single-pool needs visual
  variance to show the new genome dimension.

### 5-tick outer-ring action flash

- **Decision:** When a creature performs an action, an outer ring
  pulses in a color for the next 5 ticks. Blue = created a child (mate
  initiator), teal = just born, yellow = attacked, red = killed, green
  = grazed.
- **Why:** Replaces the action information that the EMA color used to
  carry. Ring flash is transient so the body color stays readable for
  species identity.

### Biomes render as cell color for v2.0

- **Decision:** Biome layer is drawn as flat per-cell color sampled
  from the boot-time `biomeSab`, under the grass texture.
- **Why:** Simple to ship. Textured / height-shaded biomes are V2.1+.

### No minimap, no event log, no timeline

- **Decision:** Cut from v2.0.
- **Why:** Scope. None are load-bearing for "10 species visibly own
  regions."

### Zoom-out is the v2.0 survey tool; lower the min-zoom clamp

- **Decision:** Instead of a minimap, allow the camera to zoom out
  further than today's `0.5` clamp (tuned for the 1200u world) so the
  user can survey a large/editable world from one view. A creature that
  would render sub-pixel is drawn as a **min-1px point** in its display
  color (skip the disc shading) so species territories stay visible from
  the survey view instead of vanishing.
- **Why:** With editable/large worlds you need *some* way to see the
  whole thing — and to see *where the factions are*, not just the
  terrain. A minimap / species heatmap is the right long-term answer
  (V2.1+, see next-steps), but zoom-out + 1px points is nearly free and
  good enough for v2.0. The earlier `[0.5, 16]` clamp existed because
  below 0.5 the 1200u world turned to noise — a non-issue when the point
  is a bird's-eye survey and bodies clamp to a visible minimum.
- **Applies to:** `clampCamera` min-zoom + the instance-pack point-size
  floor (`web/src/render.ts`, `web/src/render-gl.ts`).

### Per-species pop graph in Monitor tab (mating mode)

- **Decision:** Monitor's existing single pop line becomes per-species
  lines (overlaid) in species mode, using the canvas hues directly.
  Per-species counts are **aggregated sim-side and requested from the
  wasm layer** via a polled SAB report (same mechanism as the profile
  / NN-stats reports), not packed into the fixed 20-byte snapshot
  header.
- **Why:** The single most informative artifact in the whole UI for
  watching a species sim. A polled report avoids widening the hot-path
  snapshot header for data the chart only needs a few times a second.
  Color reuse with the canvas is acceptable because typical runs end
  with 1–3 surviving species.
- **Applies to:** a new `WorldHandle` report method + control-SAB
  epoch/len slots (mirror `nn_worker_stats_json`), `web/src/widgets`
  Monitor.

## Population balance

### Keep the global population cap

- **Decision:** `MAX_POP_FOR_SIM` and the soft `max_population` slider
  both stay exactly as today (32k hard, 8k default soft).
- **Why:** The cap is a SAB-sizing invariant. Removing it cascades into
  the protocol. At 64× area + 8k pop the cap rarely binds anyway;
  no reason to retune it for the new scale.

### Tune mechanics to avoid the cap binding

- **Decision:** Make reproduction cost more (energy gift + cooldown) so
  population doesn't routinely smash the cap and trigger random culls.
- **Why:** A binding cap is a sim-quality signal. The random cull kills
  carefully-evolved lineages indiscriminately.

### Linear vegetation suppression under high pop — V2.1+

- **Decision:** Defer the "vegetation thins linearly as pop grows"
  mechanic to V2.1+.
- **Why:** Ship base mating-cost balance first; layer the suppressor
  only if the cap still binds in playtest.

## Removals

### `full_grass_on_init` slider deleted

- **Decision:** Drop the slider and its plumbing.
- **Why:** Vestigial under the new coarse-grass-grid model. World init
  uses biome-driven grass seeding instead.

### Curriculum reserved slider slots (`_reserved_curriculum_17..20`) removed

- **Decision:** Drop the four reserved slots in `try_set_slider`.
- **Why:** They've never been used; v2.0 already breaks the control-SAB
  slider layout elsewhere (NN input width, new + removed slider names), so
  the backward-compat reason for keeping them goes away. (Note: the
  *creature* snapshot stride is unchanged — see the snapshot decision —
  it's the slider/NN surface that breaks.) v2.0 invalidates every
  persisted localStorage slider state from v1 — handled by the settings
  schema version below.

### Settings schema version (`major.minor`) gates localStorage migration

- **Decision:** Stamp the persisted settings blob with a `major.minor`
  version. On load: a **minor** mismatch (new keys shipped) merges the
  missing keys from defaults and keeps the user's existing values; a
  **major** mismatch (structurally incompatible — what v2.0 is) **resets
  to defaults**. v2.0 bumps the major version; bump minor on any ordinary
  settings change thereafter.
- **Why:** v2.0 renames/removes sliders and changes the control-SAB
  layout, so old localStorage can't be trusted. A version stamp makes the
  reset deterministic and gives every future settings change a cheap,
  non-destructive migration path (minor bump) instead of silently
  carrying stale or missing keys.
- **Applies to:** `web/src/settings.ts` (the persisted blob + load/merge
  path).
