## 2. Stage-2 Wave Plan

### Seam rule (enforced)

Stream 2b reshapes the control SAB (adds camera lane) and snapshot slot
(adds window metadata). Stream 2c is the TS consumer of those fields (reads
the window, writes the camera lane values through to the renderer). A SAB-layout
change and its TS consumer CANNOT be fully parallel because 2c cannot write
meaningful render code until the window metadata shape that 2b defines is
locked. The hub's "(2b + 2c coupled)" notation means they serialize internally
in a Rust-first order within the same wave, not that they run independently.

### Waves

| Wave | Streams | Parallel? | Rationale |
|------|---------|-----------|-----------|
| 1 | **2a** (GrassPyramid core) | n/a — solo | Foundational. All other streams read the pyramid. No Rust stream can advance without this. Lands first, main tree, one agent. |
| 2 | **2b** (snapshot protocol + camera SAB lane) | n/a — solo | Depends on 2a (reads pyramid). 2b owns the entire protocol surface: control_sab.rs, wasm_api.rs write_snapshot rewrite, sim-bridge.ts SlotLayout, main.ts camera write, sim-worker.ts window compute. Run gen-bindings; CI must pass before wave exits. |
| 3 | **2c** (render LOD) + **2d** (biome tint) | YES — parallel | Both depend on 2b's completed SlotLayout and window metadata. Disjoint edit regions: 2c owns the grass texture path in render-gl.ts; 2d owns the biome path in wasm_api.rs + render-gl.ts biome upload. They share render-gl.ts at the file level but not at the function level. Assign one agent per stream; each gets a scope fence (see §3). |
| 4 | **2e** (mip sensing, gated) | SKIP or solo | Last, optional, behavioral. Depends on 2a (GrassPyramid API) but is otherwise disjoint from waves 2–3 (does not touch render-gl.ts, sim-bridge.ts, main.ts, or control_sab.rs). If skipped, Stage 2 is complete at wave 3. If shipped, one agent, main tree. |

### Why 2c and 2d can parallelize in wave 3

- 2c edit region: `render-gl.ts` grass path (`initRenderer` grassTex allocation,
  `renderWorldImpl` grass upload block lines ~979-987, `GRASS_VS`/`GRASS_FS`
  shaders, `grassTexDim` guard, UV transform uniforms, zoom→LOD selection).
- 2d edit region: `src/wasm_api.rs` write_snapshot biome append (after 2b's
  rewrite), `render-gl.ts` biome upload block (lines ~942-945), `biomeTex`
  path, `BIOME_FS` shader if biome colors become texture-driven.
- Zero function-level overlap in render-gl.ts: grass and biome paths are
  separate `if` blocks within `renderWorldImpl`.
- The only file 2c and 2d truly share is `render-gl.ts` — and even there the
  grass vs biome sections are at different lines with no shared state mutation.

### Why 2b and 2c must NOT run parallel

2b defines:
- `CTRL_CAMERA_*` constant names and slot indices (control_sab.rs)
- Window metadata field layout in the snapshot slot header (wasm_api.rs / sim-bridge.ts)
- `SlotLayout` shape change (grassCellCount → win_w × win_h)

2c reads ALL of these in order to build the UV transform and windowed upload.
Starting 2c before 2b finalizes the metadata schema guarantees integration
failures.

### Why 2e can parallelize with waves 2–3 in principle, but is staged last

2e only touches: `src/world/nn.rs`, `src/world/proximity.rs`, `src/constants.rs`
(MAX_NN_INPUTS), `src/world/mod.rs` (maybe). None of these files overlap with
waves 2–3. Technically 2e could run alongside wave 3 — but it is gated,
behavioral, and skippable. Hub ordering (last, optional) stands.

## 4. Per-Stream What-to-Build

### 2a — GrassPyramid core

1. **Struct** `GrassPyramid` in `src/grass.rs` (or a sibling `grass_pyramid.rs`
   re-exported from `grass.rs`):
   - `level_dims: Vec<usize>` — per-level dim computed as `d_L = d_{L-1}.div_ceil(2)`, stored starting at L1
   - `levels: Vec<Vec<u8>>` — owned L1+ buffers (L0 is implicit; callers pass `&density: &[AtomicU8]`)
   - No `AtomicU64` inside the struct; refresh is single-threaded, level-sequential
2. `GrassPyramid::new(dim: usize) -> Self` — compute full level chain down to 1×1, allocate zeroed `Vec<u8>` per level L1+. Assert passed density slice is `dim×dim`.
3. `GrassPyramid::refresh(&self, density: &[AtomicU8], active_tiles: &[AtomicU64], tiles_per_axis: usize)` — gather pass:
   - Full recompute at default scale is acceptable (`O(N × 1/3)`)
   - For large-scale correctness: dirty-subtree walk keyed off `tile_active` / `tile_dirty` bitsets (dirty base tile → dirty L1 parent → ...)
   - Per-level loop: L1, L2, ... ; each parent averages 1–4 in-bounds children from L−1; u8 rounding (add half before shift); edge-clamp at ragged borders (model: existing `.min(dim)` convention in `grass.rs:449`)
4. `GrassPyramid::sample(density: &[AtomicU8], dim: usize, x: f32, y: f32, level: usize, wrap: bool) -> f32` — mirrors `GrassGrid::bilinear_sample`: `rem_euclid` for wrap, clamp/ghost for walled. NEVER naive `(x/cell) as usize`.
5. `viewport_window` helper (or iterator equivalent) for Consumer 1/2 window extraction: given `(origin_x, origin_y, w, h, level)` → yields the `w × h` u8 bytes row-major.
6. Add `pub pyramid: GrassPyramid` field to `GrassGrid`; initialize after `density` in `GrassGrid::new_with_capacity`.
7. In `World::step()` (`src/world/mod.rs`): add an explicit numbered step block immediately after the `grass_step` profiler rollup closes (after line ~959): `self.grass.pyramid.refresh(&self.grass.density, &self.grass.tile_active, self.grass.tiles_per_axis)`.
8. **Native tests** (`cargo test --lib`): non-pow2 averaging (1920×1920, 3×3 odd); per-level dims via `div_ceil(2)`; bounded-error vs reference; wrap + walled `sample` correctness; `viewport_window` stays in bounds.

## 5. Open Questions for Lead

The lead has delegated decision authority (2026-06-02 log). These questions must
be decided before the relevant wave launches. The orchestrator should log the
decision in the hub's orchestration log, not ask the lead live.

### Q1. Mip sense band layout (blocks Wave 4 / 2e)

**Spec recommendation:** 3 bands (near/med/far) × 8 sectors = 24 grass inputs,
replacing the current 8. But 3 bands × 8 sectors = 24 slots; the widest active
layout (walled + species = 40 current inputs) → 40 − 8 + 24 = 56 > `MAX_NN_INPUTS`
= 48. Even 2 bands: 40 − 8 + 16 = 48 — exactly at the ceiling for walled worlds,
with no margin. The spec says "tune later."

**Synthesis recommendation:** Start 2e with **2 bands** (near/far × 8 sectors =
16 grass inputs). This fits every world config within the current `MAX_NN_INPUTS`
= 48 ceiling (walled+species: 40 − 8 + 16 = 48 exactly). If the behavioral A/B
in Stage 3 shows 3 bands is materially better, raise `MAX_NN_INPUTS` to 56 at
that point. Decouples the ceiling-raise from the 2e implementation.

**Decide:** 2 bands (no ceiling raise needed) vs 3 bands (must raise `MAX_NN_INPUTS`
to 56 before 2e compiles for walled worlds).

---

### Q2. Trilinear vs nearest mip sampling in the renderer (blocks Wave 3 / 2c)

**Spec recommendation:** Trilinear is "optional … to avoid LOD popping on zoom."
No firm recommendation; framed as a cost/quality tradeoff.

**Synthesis recommendation:** Ship **nearest-mip first** in 2c. Wire the
texture-parameter path so trilinear can be enabled by changing one
`texParameteri(TEXTURE_2D, TEXTURE_MIN_FILTER, LINEAR_MIPMAP_LINEAR)` call and
uploading the second level — no shader restructure needed. Trilinear review
deferred to Stage 3 feel-tune.

**Decide:** nearest first + trilinear-ready architecture, OR trilinear from day 1.

### Q3. Biome channel: snapshot-channel vs standalone biome mip (blocks Wave 3 / 2d)

**Spec recommendation:** Snapshot biome channel (mode-downsampled window baked
alongside the grass window in the slot). Named as the chosen design, described
as "cleaner because it piggybacks on the window that already has to exist."

**Synthesis recommendation:** Confirm **snapshot biome channel** as the 2d
implementation target. The standalone biome mip would require a separate refresh
struct, separate TS upload path, and separate texture, with no reuse of the 2b
window machinery. The snapshot channel reuses the same window origin/dims/mip
level that 2b already computes — zero new protocol.

**Decide:** snapshot biome channel (confirmed) or standalone biome mip (reversal).

### Q4. Upload budget axis, margin size, and LOD-selection curve (blocks Wave 2 / 2b)

These three values are coupled: the LOD formula uses the budget; the margin
determines how often the window must refresh.

**Spec recommendation:** Budget example = 2000². Margin = "generous." LOD
formula = "coarsest mip whose visible span ≤ upload budget." No hard numbers.

**Synthesis recommendation:**
- **Budget axis: 2048** (power-of-two, texture-friendly, ~4 MB at R8, within
  the current full-texture size so no regression at default scale).
- **Margin: 25% on each side** → published window = `viewport × 1.5` (clamped
  to world bounds). A full-viewport pan in any direction stays covered for ≥1
  tick without a new window.
- **LOD formula:** `mip = floor(log2(visible_cell_span / budget_axis))` clamped
  to `[0, pyramid.max_level()]`. `visible_cell_span = (world_size / cam.zoom) /
  GRASS_CELL_SIZE`. Both the worker (Rust) and the renderer (TS) use this formula;
  the slot header's `mip_level` field is the ground truth — the renderer trusts
  what the worker published.

**Decide:** accept these three defaults, or specify different values.
