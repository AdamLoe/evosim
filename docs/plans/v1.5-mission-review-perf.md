# v1.5 Mission Review — Performance, Rendering, Threading (R2)

Reviewer scope: perf / rendering / threading. Out of scope: NN architecture, color encoding, curriculum, dev panel UX, evolution dynamics.

## TL;DR

The mission's perf strategy is **directionally correct** but rests on several **load-bearing magic numbers that don't survive arithmetic**. The headline R8 + dirty-rect grass upload is a clean win, *especially* because — contrary to the mission's framing — the renderer is **already WebGL2** as of commit `1f5692e`. The actual render-path change is small.

The grass-sector NN-input cost estimate (the most novel perf claim in the mission) is **off by roughly 4×** at the AABB-count level and by an unbounded factor on LUT size. The optimization stack still gets to "comfortable" but with a much thinner margin than implied — and the ≤2 ms budget at 1000 creatures is plausible only if the skip-empty optimization works as advertised, which is regime-dependent.

The `N_CHUNKS 8 → 16` change is cheap and safe, but the mission overlooks that rayon's pool size is set elsewhere (`wasm-bindgen-rayon` initThreadPool) and that 16 chunks on a 1000-creature pop means **62 creatures per chunk** — small enough that rayon's per-task overhead starts mattering for the sub-millisecond passes.

**Verdict: ship it, but rewrite the perf-budget section before committing to the implementation order. Several of the "comfortable" claims are wrong by integer multiples.**

- **Medium concerns:** 6
- **Low concerns:** 4
- **Missing items:** 5

### The R8 + Canvas2D question (the headline)

**Answer: not a problem — the renderer is already WebGL2.** The user's framing ("renderer is currently Canvas2D!") is out of date by exactly one commit (`1f5692e feat(render): WebGL2 instanced renderer + sim restart button`). `/home/adamg/evosim/web/src/render.ts` is now ~40 lines of camera math; the actual draw path is `/home/adamg/evosim/web/src/render-gl.ts`. The grass texture is **already** uploaded with `texImage2D` / `texSubImage2D` and currently uses `R32F` (see `render-gl.ts:348` and `:351`). Switching to `R8` and adding a sub-rect upload is a ~10-line change touching only `render-gl.ts` and one new wasm getter — there is no foundational WebGL migration hiding inside this mission item.

The mission's claim about R8 + `texSubImage2D` should be cleaned up to reflect this: it's not *introducing* WebGL, it's *narrowing* the existing per-frame R32F upload from "whole texture every frame" to "dirty rect with 4× smaller pixels." That reframing matters because it justifies the cost as roughly free instead of as a significant new dependency.

## Strengths

### S1. The R8 + dirty-rect plan is correct and cheap (given current state)

Today:
- Grass cells: 14_400
- Texture format: R32F (4 bytes/cell)
- Per-frame upload: 14_400 × 4 = **57.6 KB**
- Uploaded *every frame* via `texSubImage2D(...gl.RED, gl.FLOAT, density)` from `render-gl.ts:351`

After v1.5 grass scale-up *without* R8 + dirty-rect:
- Grass cells: 230_400 (16×)
- Naive R32F whole-frame upload: 921 KB/frame × 60 FPS = **55 MB/s** upload bandwidth

After v1.5 *with* R8 + dirty-rect:
- R8 = 1 byte/cell → 230 KB whole-frame worst case
- Dirty rect = typically a small fraction; even uploading 50% of cells gives 115 KB/frame = 6.9 MB/s
- Mission target: ≤25 MB/s — comfortably under

The mission's choice to do **both** R8 *and* dirty-rect (rather than pick one) is correct. R8 alone gets you to 13.8 MB/s on whole-frame upload — meeting the budget — but dirty-rect alone with R32F is fragile because a single propagation tick can dirty a high-fraction rect (see C3). Combining them gives margin in both axes.

`gl.R8` + `gl.RED` + `gl.UNSIGNED_BYTE` is standard WebGL2 and requires no extension. The fragment shader needs no change — `texture(u_grass, v_uv).r` still returns normalized `[0, 1]`.

### S2. Skipping empty cells is the single most important grass-sector optimization

The mission's trick #2 (`if density == 0 { continue; }`) is what makes the perf budget tractable. Once it kicks in, the cost per cell scales with **live grass density** rather than with cell count. At default initial seed 100/14_400 (0.7%) with propagation rate 0.001, density spreads slowly — the 95% skip rate cited in the mission is plausible for the early-game regime.

Bumping `initial seed N` to 8000 of 230_400 (3.5%) only modestly changes this. After propagation runs for some time, "live cells" expand from seeded centers; the fraction of cells with density > 0 plateaus somewhere between 5% and 30% depending on slider tuning. See C4 for the worst-case analysis.

### S3. Single hot scratch buffer for 8 accumulators is correct

Trick #5 — reusing a `[f32; 8]` scratch — costs zero allocations and stays in registers / L1. This is what the `pick_action_d` pattern already does for `input_buf` / `hidden_buf` / `output_buf` (see `world/nn.rs:57-59`). Following the same pattern is right.

### S4. Parallelizing across creatures via existing `N_CHUNKS` is the right architecture

Trick #4 — riding the existing chunking — is correct. The grass-sector read is read-only against `grass.density`, so it joins NN forward and vision in the same `par_chunks_mut` pattern. No new synchronization machinery needed. Detail: the grass-sector compute is most naturally folded *into* `build_nn_input`, which is already inside the par_chunks_mut closure (`world/nn.rs:53-85`) — so the parallelism is essentially free.

### S5. Curriculum subsystem is perf-neutral

Worth noting because the implementation order puts it between the threading bump and the NN landing: a smoothstep + a multiplication per creature per tick is sub-microsecond at 1000 creatures. No concern.

### S6. `creatures_buffer` impact is unchanged

`creatures_buffer()` is still called only when the inspector / highlight ring path needs per-field reads (see `render-gl.ts:402` — only invoked when `highlightMap.size > 0`). The main creature draw uses `pack_render_buffer()` which is GPU-instance-layout-ready. v1.5 doesn't change the stride (still 10 floats); the color overhaul (action-EMA) replaces what's *stored* in the existing R/G/B slots, not the buffer shape. No work needed.

### S7. The implementation order is sane

Putting grass scale-up last is correct — the new grass-sector NN inputs scale with cell density, so any cost surprise compounds with both #5 and #6. Landing #5 first means you measure the new brain in isolation, then add the grass scale.

### S8. Brain forward is faster, not slower (uncosted by the mission)

Mission notes weight count is unchanged at 2,808. What's *not* noted: NN_INPUTS drops from 112 to 32, which means the SIMD chunk count drops from 14 to 4 in the input projection. The hidden layer is 48 instead of 24, but `48` is still 6 SIMD chunks. Net: **brain forward should be measurably faster** per creature, even with two hidden layers, because the input-projection matmul dominates. Mission could safely commit to "brain forward total tick cost ≤ today's" — useful negotiating room for the new grass-sector cost.

## High concerns

### H1. Grass-sector cell count is off by ~4×

> "iterate cells in a 40×40 unit AABB at 1.25u cells (~256 cells)"

A 40×40 unit AABB at 1.25u cells is **32×32 = 1024 cells**, not 256. Even after circle-clipping (the cells outside Euclidean range are skipped by `dx²+dy² > r²`), the count is `π/4 × 1024 ≈ 804` cells. The mission's 256 figure looks like it assumed a 20×20 unit AABB (32×32×0.25 = 256-ish) — possibly a half-vs-full-diameter mix-up.

Knock-on effects:
- "1000 creatures × 256 cells × ~50ns per atan2 ≈ 13ms" becomes **~50 ms** with the correct cell count. The motivation for the LUT is *stronger*, not weaker.
- "5ns per cell × 256 cells × 1000 creatures ÷ 16 workers ≈ 80μs per tick" becomes **~320 μs per tick** at the same per-cell cost. Still under the 2 ms target, but the margin shrinks from 25× to 6×.
- The skip-empty optimization (S2) is the only thing that keeps the budget tractable. See C4 for the regime-dependent math.

**Recommendation:** rewrite the budget paragraph with the corrected cell count. Add an explicit dependency on the empty-skip rate so the budget can be verified empirically once shipped.

### H2. LUT size estimate is unphysical

> "Table is fixed-size (~1 KB for 20-unit range at 1.25u cells = 33×33 entries)"

33 × 33 = 1089 entries. For the entry to encode (sector_id: 0-7) **and** an inverse-square weight, you need at minimum:
- `u8` sector_id (1 byte) + `f32` weight (4 bytes) → **5 bytes/entry × 1089 = 5.4 KB**

Pack into `u16` (3 bits sector, 13 bits quantized weight): **2 bytes/entry × 1089 = 2.2 KB**. Still not 1 KB.

Could be reduced via symmetry exploitation (octant fold: only 1/8 of entries distinct), but that adds a branch per cell — kills the L1-friendly hot path the LUT exists to provide.

**Impact:** the mission's "1 KB" framing is meaningless to the actual implementation. **5 KB still fits in L1 happily** — the optimization works. But the magic number is wrong and should be replaced with realistic numbers so future readers don't try to over-pack the structure based on a stale spec.

**Recommendation:** spec the LUT as `[(u8 sector, f32 weight); 33*33]`, document the 5.4 KB size, and note that the entire LUT fits within a single CPU L1 cache (typically 32 KB) with room for `density[..]` working-set residency.

### H3. The "comfortable ≤2 ms" claim ignores cache / memory bandwidth

The 5 ns/cell claim is for arithmetic ops in the L1 hot loop. The **real bottleneck for grass-sector compute is memory traffic on `grass.density`**, not ALU.

Math:
- `density` field: 230_400 × 4 bytes = **921 KB** (Vec<f32>). Bigger than L2 on most consumer chips (~512 KB – 1 MB) but smaller than L3.
- Per creature, you read ~800 cells (4 bytes each) = 3.2 KB of density data.
- 1000 creatures × 32 cache lines (one per row of a 32×32 box, since rows are non-contiguous: each row jumps 480 cells = 1920 bytes in memory) × 64 bytes = **2 MB / tick** raw cache-line traffic.
- At ~30 GB/s consumer single-core memory bandwidth: 2 MB / 30 GB/s = **67 μs**.

That's net-positive — same order of magnitude as the corrected arithmetic cost — but it means the "≤2 ms at 1000 creatures" budget is dominated by the *AABB scan itself*, not by any of the 5 optimization tricks past the skip-empty one. The remaining 4 tricks compress arithmetic that isn't the bottleneck.

**This isn't an objection — it's just to say the optimization theater is on a smaller stage than implied.** The first three of the five tricks (skip-empty above all, then LUT, then no-sqrt) likely deliver ~80% of the speedup; parallelism and scratch buffer get smaller wins than expected.

**Recommendation:** keep all 5 optimizations, but reorder the priority. Empty-cell skip is the only one that actually moves the dominant cost; ship it first and measure before adding LUT.

### H4. Mission has no measurement plan or roll-back trigger

The success criterion is "Grass renders at 16× density without dropping below ~16ms/frame at 1000 creatures." That's a frame-rate target, not a tick-cost target — and the frame budget (16 ms = 60 FPS) is the *total* of:
- Rust tick cost
- `creatures_buffer()` / `pack_render_buffer()` / `grass_buffer()` JS↔wasm crossings
- Texture upload
- GPU draw
- Browser composite

Today's tick budget at pop ~1000 with `--features threads` is *unknown to the mission*. Without that baseline, the "≤2 ms grass-sector" target floats in vacuum.

**Recommended addition:** before shipping #6 (grass scale-up), capture the current tick breakdown via `profile_report_json()` at pop=1000. Then explicit budgets per pass:
- Vision: today ≤ X ms → target ≤ X ms (unchanged)
- NN forward: today ≤ Y ms → target ≤ 0.7Y ms (32 vs 112 inputs)
- Grass-sector input (new): ≤ 2 ms (today: zero)
- Grass-step: today ≤ Z ms → target ≤ 16Z ms (linear scaling — see C1)
- Whole tick: today ≤ T ms → target ≤ T + ~3 ms

If grass-step alone exceeds budget at 16× cells, the mission needs an out (see C1).

## Medium concerns

### C1. GrassGrid::step at 16× cells is ~16× slower; mission doesn't say so

`GrassGrid::step` is a scalar nested loop over every cell (`grass.rs:54-101`). At 14_400 cells it's cheap (~50 μs based on memory math: 14_400 × 5-cell-reads × 4 bytes = 288 KB, runs in L2). At 230_400 cells:
- 230_400 × 5 reads × 4 bytes = **4.6 MB** of read traffic per step
- Spills out of L2 (possibly L3 on small CPUs), runs at memory bandwidth
- Estimate: 4.6 MB / 30 GB/s ≈ **150 μs single-threaded**, plus ~230 KB writes

Still tolerable — under 1 ms — but the mission's "Sim code unchanged" claim is glib. At extreme propagation rates the step function could become observable. The fix is trivial (parallelize the outer `for iy` via `par_chunks_mut` on `self.scratch`) but it's the kind of thing that bites you 3 weeks after merge.

**Recommendation:** add a 2-line `par_chunks_mut` pattern around the row loop in `grass.step` as part of the v1.5 grass landing. Each row writes `s[c]` only from reads of `d[c]` and *adjacent rows* of `d[..]` (immutably borrowed), so the row split is safe. About a 5-line change to `/home/adamg/evosim/src/grass.rs`.

### C2. Dirty-rect bookkeeping isn't specified

Mission says "Rust tracks the bounding rect of changed cells per tick" without sketching the structure. Three valid implementations with very different costs:

1. **Single bounding rect (`(x0,y0,x1,y1)`):** cheapest to track (4 int updates per cell change). Worst case: one corner cell + one opposite-corner cell changed → bounding rect = whole texture. *Anti-pattern when consumption is scattered.*

2. **Per-row dirty bits (`[u8; 480]` bitset):** 480 bytes. Upload row-by-row, batching contiguous dirty rows. Robust under scattered changes. Single `min(dirty_row)..max(dirty_row)` upload also works (1024 bytes upload instead of 230 KB if only 4 dirty rows).

3. **No tracking — whole-frame upload at R8:** 230 KB/frame, well within budget. Simplest code; only loses if you exceed bandwidth on slower machines.

The mission picks (1) implicitly. **At post-graze + post-propagation, the dirty rect is almost guaranteed to cover most of the world.** 1000 creatures spread across a 600×600 world dirty rects in dozens of disjoint regions; the bounding rect is essentially the whole texture.

**Recommendation:** start with option 3 (whole-frame R8). It's 230 KB/frame worst case, comfortably under the 25 MB/s budget. Add per-row tracking (option 2) only if measurement shows it matters. Single bounding-rect (option 1) is a trap — code complexity of tracking without the bandwidth wins.

### C3. Where is grass-density change tracked? In `step()` AND in `consume()`

Two distinct mutation sites in `grass.rs`:
- `consume()` (called per creature per tick from `tick.rs::graze`): drops density on individual cells.
- `step()` (called once per tick): rewrites essentially every cell with non-trivially-different values (propagation moves density across cell boundaries).

After every `step()`, *every cell with grass is dirty*. So dirty-rect tracking is meaningful only if grass occupies a small region of the world (early game). Once grass has propagated across the whole world (mid-game with default settings, more so with high propagation rate or 8000 initial seeds), the dirty rect *is* the world rect.

This isn't fatal — R8 alone keeps you in budget — but it means "dirty-rect uploads" should be marketed as an early-game / low-grass optimization, not a general win.

### C4. Skip-empty optimization performance band

Best case (early game, sparse seeded grass):
- 50 seeded cells of 230k = 0.02%
- Empty-skip rate: 99.98%
- Per creature: ~0.2 non-empty cells per box scan
- Total cost: 1000 × 0.2 × ~50 ns = **10 μs/tick** (essentially free)

Mid game (steady-state propagation, ~20% coverage):
- ~46k cells with density > 0
- Empty-skip rate: 80%
- Per creature: ~160 non-empty cells per box scan
- Total cost: 1000 × 160 × 50 ns ≈ **8 ms / tick** — *exceeds* the mission's 2 ms budget

Worst case (saturated propagation, ~50%+ coverage):
- Empty-skip rate: ~50%
- Per creature: ~400 non-empty cells per box scan
- Total cost: 1000 × 400 × 50 ns ÷ 16 workers ≈ **1.25 ms/tick** — back in budget thanks to parallelism

So the **2 ms target holds in best and worst case but breaks in mid-game densities**. Counterintuitively this is because the per-cell cost is *non-zero* in the empty-skip path too (you still pay for the `if density == 0` test and the cache-line read).

**Recommendation:** add a "fast path" beyond skip-empty: **maintain a per-row "any cell non-empty" bitset on `grass.density`**, regenerated cheaply during `step()`. The grass-sector scan can then skip whole *rows* in O(1) per row instead of O(cells/row). Adds ~480 bytes of state, eliminates the cache-line read on empty rows.

### C5. `N_CHUNKS` 8 → 16: real but not free upside

User's machine has 20 cores; jumping to 16 chunks utilizes more of them. Concerns:

a. **Rayon's thread pool size is set elsewhere.** In `wasm-bindgen-rayon`, the pool is initialized via `initThreadPool(n)` from JS. Need to confirm `main.ts` currently spawns ≥16 workers, else 16 chunks just queue on 8 threads. Quick `grep -rn initThreadPool web/src` would resolve. (See open question 1.)

b. **Per-chunk overhead matters at small populations.** At pop = 100, chunk size = 7 creatures. Rayon's task-spawn overhead per chunk is ~1 μs; 16 chunks of 7 creatures each = 16 μs of overhead for ~70 μs of NN work = 23% overhead. The current 8 chunks of 13 creatures has ~11% overhead at the same pop.

c. **False sharing on the output columns.** The NN path does `vx_local[..n].par_chunks_mut(chunk_size).zip(vy_local[..n]...)` — writes to three separate `Vec<f32>`. At chunk_size = 7 (pop = 100), each chunk writes 28 bytes per column < 64-byte cache line. Adjacent chunks share cache lines, causing inter-thread coherence traffic. **At chunk_size ≥ 16, this disappears.** So 16 chunks is fine at pop ≥ 256 (16 × 16) but worse than 8 chunks at pop < 128.

**Recommendation:** make `N_CHUNKS` dynamic on pop with floor at 4 and ceiling at `min(16, worker_count)`. Specifically: `chunks = clamp(pop / 32, 4, min(16, worker_count))`. The "32 creatures per chunk" rule of thumb keeps cache-line ownership clean. Alternatively, accept the user's "16 is fine" pragmatism but document the small-pop regression.

### C6. Worker-utilization widget should count actual work, not chunk presence

> "active = chunks that actually had work"

`chunk_ranges(n)` produces `(0,0)` ranges when `n < N_CHUNKS` (verified in `world/nn.rs::chunk_ranges` invariants). So `min(pop, N_CHUNKS)` correctly captures non-empty chunks. But "active" in the perf sense should be "chunks dispatched to a different thread than 0". Rayon's `par_chunks_mut` decides this dynamically based on the work-stealing scheduler — at very small chunk sizes, rayon may execute everything on the calling thread.

This is mostly a labeling concern: the widget should say "chunks: A/B" or "chunks scheduled / chunks available" not "active workers / total workers". The latter implies thread-level introspection that rayon doesn't easily expose.

**Recommendation:** rename the metric; document that A reflects non-empty work units, not actual thread dispatch.

## Low concerns

### L1. R8 quantization is mathematically safe but might be visually flat

R8 quantizes density to 256 levels. The grass shader does `texture(u_grass, v_uv).r` as alpha; the renderer uses `gl.NEAREST`. With current filtering, adjacent cells get visibly distinct shading — that's a feature for legibility. With future `gl.LINEAR`, R8 might band noticeably at low densities.

No action for v1.5; flag for future when the shader graduates.

### L2. `grass_buffer()` cost will change shape under R8

Currently:
```rust
pub fn grass_buffer(&mut self) -> js_sys::Float32Array {
    self.grass_buf.clear();
    self.grass_buf.extend_from_slice(&self.inner.grass.density);
    unsafe { js_sys::Float32Array::view(&self.grass_buf) }
}
```

After R8 you need a `Uint8Array` view. Either:
- Keep `density: Vec<f32>` and quantize to `Vec<u8>` per frame (extra 230 KB pass per frame), or
- Store as `Vec<u8>` and dequantize for NN sampling (changes the math everywhere `bilinear_sample` is called).

The first option is simplest and still fits the 2 ms grass-render budget. The 230 KB per-frame quantize at memory bandwidth ≈ 8 μs. Negligible.

New wasm getter for dirty rect: `grass_buffer_dirty(out_rect: &mut [u32; 4]) -> Uint8Array` or similar. Mission should call this out explicitly so the JS/Rust API contract is clear.

### L3. Memory math for the cumulative wasm-heap impact

Current grass memory: `density (Vec<f32>) + scratch (Vec<f32>)` = 14_400 × 4 × 2 = **115 KB**.

After v1.5: 230_400 × 4 × 2 = **1.84 MB**.

Plus possibly:
- R8 mirror for upload: 230 KB (`Vec<u8>`)
- Per-row "any non-empty" bitset (C4): 480 bytes — negligible
- Dirty-rect bounding box: 16 bytes — negligible

Total grass-related heap growth: **~2 MB**. Comfortable for wasm32 (4 GB limit), but worth noting if other systems also grow.

Wasm heap visibility in the perf widget would be helpful — already exposed via `memory.buffer.byteLength`. Cheap to add.

### L4. `pack_render_buffer` doesn't change but cull rate matters more

At 16× grass density, more creatures spend more time visible (since grass-driven settlements form). The frustum-cull-rate inside `pack_render_buffer` holds up regardless because it's already O(N) per frame. The *render-buffer fill rate* may increase (more visible creatures per frame at the same pop) — could marginally bump per-frame instance buffer upload from a few KB to ~80 KB at pop 1000 fully on-screen. Still trivial.

## Missing items (gaps in the mission)

### M1. No mention of `wide::f32x8` width for the new 48-hidden layer

The brain uses `wide::f32x8` for SIMD matmul. Hidden 48 = 6 SIMD chunks ✓. Input 32 = 4 ✓. Second hidden 24 = 3 ✓. All multiples of 8 ✓. But this should be explicitly checked at compile-time via the same `const _: () = assert!(NN_HIDDEN % 8 == 0)` pattern in `brain.rs`. Currently the assertion is for NN_INPUTS and NN_HIDDEN.

**Add:** const assertions for the new layer widths so any future change to architecture trips at compile time.

### M2. No grass-sector benchmark in the test suite

The mission proposes a hot path that costs ≤ 2 ms at 1000 creatures. There's no `cargo bench` setup in the project (verified: no `[[bench]]` in Cargo.toml, no `criterion`). The 2 ms target is therefore unverifiable without manual instrumentation.

**Add (out of scope as a hard ask, but worth flagging):** at minimum a `#[test]` that constructs 1000 creatures with seeded grass and asserts the grass-sector pass completes in < some envelope (10 ms for debug, 2 ms for release). Cheap; catches regressions.

### M3. No specification of what happens to `NN_GRASS_PATCH_OFFSET` / 5×5 patch

The 5×5 grass patch (current NN inputs [80..105]) is being replaced by `grass_density × 8`. The old `bilinear_sample` call inside `build_nn_input` (called 25× per creature) disappears. Net cost savings: 1000 × 25 × ~15 ns ≈ **375 μs/tick** — not in the mission's accounting. This is a free win you can subtract from the new grass-sector cost.

### M4. `prev_energy` snapshot — still needed?

Mission's new self-state inputs don't include `energy_delta`. Current NN tracks `prev_energy` and snapshots it after NN forward (`world/mod.rs:199`). If the new inputs don't use it, the per-tick `copy_from_slice` of `prev_energy[..n]` (1000 × 4 = 4 KB) can be deleted. ~5 μs/tick saved.

### M5. Mission omits the test-suite impact

Tests currently assert `NN_INPUTS=112`, `NN_VISION_LEN=72`, slot offsets, etc. (see `world/nn.rs:359-373`). A grep would find ~10-20 hardcoded constants that need updating. Worth scoping into implementation step #5.

## Open questions

1. **What does `wasm-bindgen-rayon` initThreadPool currently use?** If `navigator.hardwareConcurrency`, 20 cores → 20 threads, and N_CHUNKS=16 leaves 4 idle. If hardcoded to 8 (matching old N_CHUNKS), then bumping N_CHUNKS to 16 does nothing until the JS init also changes. Quick verify before committing.

3. **Does the user prefer "always-conservative budget that ships day 1" or "ambitious budget with a planned v1.5.1 patch if it doesn't pan out"?** The mission reads as the latter — fine, but the rollback trigger should be explicit (H4).

Grass texture is currently `R32F` uploaded via `texSubImage2D` every frame. Switching to `R8` is a ~10-line edit to `web/src/render-gl.ts` + a new wasm getter. No foundational WebGL migration hidden inside this mission.
